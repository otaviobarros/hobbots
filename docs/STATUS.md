# Status

What Hobbots does today, split into what has been proven end to end and what has not. Each item has the date it last changed and the issue that tracks it. A proven item links its [evidence record](evidence/README.md), which names the commit and setup it ran on.

Hobbots is an early build. Only macOS on Apple silicon has been checked by hand. Linux, Windows and Intel Macs have not.

## Not proven yet

Built, but not proven end to end, or proven only in part.

- **2026-11-08 · Hobs commit without setting an identity themselves.** Every hob that may commit is told before its first commit, in its system prompt and again in every resumed session, that Hobbots sets who its commits are made as and that it runs `git commit` without `-c user.*`, `--author` or identity variables, whether its commits are made as the user's Git config, the identity given to Hobbots or its own bot. Proven in the runtimes' unit tests and the commit contract every supported runtime runs (`[TC-OR-1213-01]`, `[TC-OR-1213-02]`). ([#622](https://github.com/otaviobarros/hobbots/issues/622), [evidence](evidence/2026-11-07-charm-actions-end-to-end.md#gaps))
- **2026-11-07 · Skills from `~/.agents/skills` are read-only, and stay out of backups and exports.** Hobbots only reads that folder, so a skill from it changes only there: the web app, the desktop app, the API and hob proposals are refused, and Make a copy gives an editable Hobbots skill with the same files. A backup holds none of its files and an export leaves it out under "Not exported"; after a restore the folder is read again, a pin on a revision it no longer has moves to its current one, and a skill gone from the folder is named in the restore summary and not delivered. Verified through the hub on SQLite and in the browser with the fake runtime; the packaged app and a real runtime are not proven yet. ([#1139](https://github.com/otaviobarros/hobbots/issues/1139), [evidence](evidence/2026-11-07-agents-skills-read-only.md))
- **2026-11-07 · Skill sets: how each runtime loads skills that share files.** [ADR 029](decisions/029-skills.md) now decides skill sets: a plugin, or a repository folder of skills that share files, comes in as one entry of the library, with one revision for its whole content, and is mounted whole so a skill's links to the set's shared files and to its other skills resolve. Probed with stand-in models and agent-engineering v0.5.0: Claude Code 2.1.311 and 2.1.319 load each set as its own plugin, list its skills as `<set>:<name>` and read the shared files from the base folder a skill gives, but load the first plugin's skill when two share a bare name; Codex 0.166.0 and 0.167.0 list a set's skills from its folder as an extra root, by their own names, and follow the same links, the `skill` item's path picking between two of one name. Since built: importing a set, one revision for the whole set, holds, mentions in both forms, delivery through the Hobbots adapters on both runtimes, exports and Diagnostics. The contract suites passed with a set mounted on Claude Code 2.1.311 and Codex 0.166.0 and 0.167.0, and agent-engineering v0.5.0 imported from Git as one set of nine skills. The Skills page now shows a set too: an import shows a plugin as one set with its skills and shared files, the library lists it as one row, its page lists its skills, their uses and the files they share, a skill of it opens read-only with Make a copy, which brings the set's files it links to, and a hob's skills list turns one of its skills off. Proven in the browser against the hub on SQLite with the fake runtime, and Make a copy for each of agent-engineering's nine skills; no real model ran. ([#1143](https://github.com/otaviobarros/hobbots/issues/1143), [evidence](evidence/2026-11-07-skill-sets-probe.md), [delivery](evidence/2026-11-07-skill-sets-delivery.md), [screens](evidence/2026-11-07-skill-sets-screens.md))
