# API, MCP and real-time events

**Decided:** Effect v4 typed HTTP API, schemas/typed errors, persisted events delivered with Effect Stream/SSE, and scoped MCP agent tools. The event envelope, journal and reconnect protocol follow [ADR 013](../decisions/013-event-journal.md); other endpoints and payload schemas below are design contracts to finalize, not implemented APIs.

The browser and Electron submit commands to the same application services. Command areas include agent configuration, threads/prompts, Quests/tasks/delegations, inbox messages/acknowledgements, cancellations, approvals, executor registration and authorized artifact inspection. HTTP handlers validate input and identity; domain services validate authority and transitions.

Hobbots MCP exposes only permitted agent coordination capabilities: delegate, inspect assigned work, send correlated messages, wait for results and request cancellation/status. Credentials bind to an agent/execution and delegated scope. User administrative operations, credential management, human approval grants, administrative deletion and computer lifecycle operations are not exposed through agent-issued credentials. This excludes Hobbots control-plane administration; authorized workspace file operations remain subject to their separate resource/tool policy.

## Event envelope

**Decided** ([ADR 013](../decisions/013-event-journal.md)). Every journaled event has an event ID, a gap-free per-installation `sequence` (the cursor), a per-type `schemaVersion`, `type`, `occurredAt`, correlation IDs (agent, thread, message, and later Quest, task, delegation, attempt, executor and runtime session as relevant), a `causationId` and a `HobbotsEvent` payload. The event is written in the same transaction as the change it describes. Validate inputs at boundaries; redact secrets before persistence.

Event families cover agent/thread/message creation and streaming; turn stop and message queueing; Quest/task lifecycle; delegation request/acceptance/message/result; execution start/output/outcome; tool start/output/completion; approval request/resolution; executor connect/disconnect. Inbox acknowledgement/consumption and responsibility closure must also be observable. Names beyond those in ADR 013 are drafts and versioned before implementation. Approval requests are journaled as `ApprovalRequested` and `ApprovalResolved` (version 1), each carrying the whole request. `GET /api/threads/:threadId/approvals` lists a thread's requests, `GET /api/approvals` lists the Inbox's (every pending request and the 200 most recently decided or expired ones, oldest first), `GET /api/approvals/:approvalId` reads one request as it is now, whatever its state, and `POST /api/approvals/:approvalId/decision` takes Approve once or Deny with the request's action digest, an optional reason and, to approve a high-risk (`onceOnly`) request, `confirmed`. Every route but health and pairing answers only an approved device, as a user session, and refuses anything else with `401 DeviceRequired` or `401 DeviceRevoked` ([permissions](permissions.md#agent-control-plane-exclusions)). `GET /api/devices` lists every device, the hub's window first, revoked ones included, and `POST /api/devices/:deviceId/revoke` revokes one (`409 CannotRevokeWindow` for the hub's window). A Revoke is journaled as `DeviceRevoked` (version 1), carrying the device and never a token, and the event stream closes the revoked device's open connections when it sees it. `PATCH /api/remote-access` takes `paused` for Pause remote access and Resume; the status carries `paused` and the problem `paused`. A thread's brain and its runtime sessions travel in `ThreadUpserted` (version 2), and from version 3 its `archivedAt`, so archiving and restoring reach every client live, and a reply's runtime and model in `MessageUpserted` (version 4); older entries decode with no brain, no sessions, not archived and no recorded runtime ([ADR 017](../decisions/017-switching-brains.md)).

Three events are transient: they are not journaled and have no cursor. `MessageDelta` carries the text offset it starts at so clients apply it idempotently. `TurnStarted` and `TurnEnded`, each carrying `threadId` and `agentId`, are sent as `turn` frames when a turn joins the hub's running turns and once it has left them, after its runtime exited. Each is published only after the change, so a read of `GET /api/activity` made on receiving it already reflects it (or a later change, such as the next queued message starting). A turn that ends before it joins the running turns gets only `TurnEnded`. They are not replayed, since the running turns live in the hub's process and a restart ends them all; a client reads `GET /api/activity` again on every `Ready` instead. A reply's steps (thinking and tool calls, each `running`, `awaiting`, `done`, `failed`, `denied`, `unfinished` or `uncertain`) are part of the message: each change saves the reply and journals its `MessageUpserted`, so steps replay on reconnect and stay once the reply ends. A tool step carries the tool, the policy operation and its targets, and a denied one the reason and who refused it: the policy, the user answering an Ask, or the sandbox. A finished tool step carries what its call printed, or its error, redacted: the whole output when it fits in 16 KiB, else its first and last 8 KiB, cut between lines where it can, with the number of bytes left out. When Claude Code saves a command's output to a file because it is too large to return inline, Hobbots reads that file (only inside the runtime's configuration folders, never through a link, and up to 64 MiB) so the step and its log hold the whole output, not Claude Code's excerpt. The hub then keeps the whole redacted output as the step's log, which `GET /api/threads/:threadId/messages/:messageId/steps/:stepId/log` serves as plain text; a step whose output was shown whole has none. A tool call is saved as `running`, with its `startedAt`, before it runs. A tool call still running when its turn ends (a crash, a restart, a stop or a runtime failure) becomes `uncertain`: it may or may not have taken effect, Hobbots never runs it again, and Continue, and every later turn in the thread, tells the runtime to check it before repeating it. A briefing for another brain always lists it, past its usual limit on tool steps. Any other step still under way, thinking or a call awaiting approval, becomes `unfinished`. Neither is revived by Continue. Streamed text is rebuilt on resume from the message row, which is checkpointed at most once a second while a reply streams.

What a Task did, for the Workbench ([ADR 023](../decisions/023-workbench.md)), is journaled as `CommandRecorded` (a command's record, each time it changes), `FileChangesRecorded` (a folder's changes on an Attempt as a scan found them, with the ids of changes a later scan dropped) and `FolderScanned` (a start or end scan, written after the changes it found), each version 1 and each naming its Task. `GET /api/attempts/:attemptId/activity` reads an Attempt's commands, file changes, scans and the Task's artifact references, and the hob of each other Attempt a change was shared with (`sharedWithHobs`), with a stream cursor as the Task reads have, so a client applies the events after it. `GET /api/attempts/:attemptId/commands/:commandId/log` serves a command's log as plain text, and `GET /api/attempts/:attemptId/contents/:contentId` a kept version of a file, only when one of that Attempt's records names it; anything else, details cleared past retention included, is `404 ActivityDetailNotFound`. `GET /api/attempts/:attemptId/files` lists the files the Attempt made or touched for the Files tab: its file artifact references and the files its changes left, each with its preview kind, its size, whether it is the same, changed since, unchecked (still the size the Task left, but too large to compare) or gone, and the SHA-256 of what it holds now (none when it is gone or larger than the 64 MiB the hub serves, which is measured but never read), and only those inside the hob's folders now. The Files tab versions a preview's URL by that hash, so a preview left open loads each new version, and reads the list again when the person comes back to the window. `GET /api/attempts/:attemptId/files/:fileId` serves one of them as it is now, through no link: a preview with the media type of an image, a PDF or plain text (text redacted, then cut to 1 MiB at a line break), or with `?download=1` the file itself as `application/octet-stream`. A file whose name marks it as secret, a gone file and any id the listing does not name are `404`. A command's output as it runs is the transient `CommandOutput`, sent as a `command-output` frame with the Attempt, Task, command, the offset it starts at and the redacted text, once the turn knows its Attempt. Claude Code reports a command's output only when it ends, so its commands have no such frames. The web client reads an Attempt's records again whenever one of its records is journaled, cancelling a read already on its way, and on every new sync generation, when a read that began before the generation is read again.

Exports ([ADR 026](../decisions/026-backup-export-diagnostics.md#export)) emit no events. `POST /api/exports` takes a scope (`Thread`, `Hob` or `Everything`) and a destination folder on the hub, writes `Hobbots export <what> <date>` inside it with `README.md`, a Markdown file per thread and per Task tree, the copied file artifacts under `files/` and `export.json`, and answers with the folder and its counts. Every string is redacted. A destination that is not a folder on the hub, or that is inside a folder a hob works in or the default workspace, is `400 InvalidFolder`, and nothing is written. A failed write deletes what it wrote and answers `500 ExportFailed`. `GET /api/exports/destination` offers the hub user's Downloads folder, or their home folder without one.

## Reconnect protocol

Journaled events are SSE frames whose `id` is the cursor; transient frames carry no `id`. A client resumes with `Last-Event-ID` (or `?after=` on a first connection). Every connection starts with a `Ready` frame: resumed connections replay every entry after the cursor in sequence order, then send the current text of each streaming reply, then continue live without a gap. A missing, foreign-epoch or expired cursor gets `resumed: false`, and the client refetches its queries as the snapshot. A fresh `Ready` starts a new sync generation: the client discards earlier responses, revisions and tombstones and refetches. Within a generation every entity carries a `revision` (the sequence of its last change); a query response replaces its query's membership and is overlaid with the newer upserts and tombstones received since the generation began, so neither a delayed response nor a missed deletion leaves stale state. `GET /api/events` serves this stream as a plain Effect HTTP route beside the typed API, since the typed API's SSE responses cannot send the `retry: 1000` hint or the comment-line keep-alive sent every 15 seconds. Journal entries are kept for 7 days and at least the latest 10,000. Only events authorized for that client are streamed; keep secrets and inaccessible artifact content out of events.

The desktop app's main process follows the same stream, so the menu-bar icon and the request notifications work with every window closed, and an idle app sends no requests. It resumes after the last cursor it received, like the browser, and every `Ready` makes it read the Inbox and the hobs at work again. After that it reads the Inbox again on `ApprovalRequested` and `ApprovalResolved`, and the hobs at work again on each `TurnStarted` and `TurnEnded`. `GET /api/activity` reports a hob working while one of its threads has a turn running, until the turn's runtime has exited, so a hob whose reply just ended still shows working while its runtime shuts down. Since the turn events are published only once the running turns changed, one read per event is enough; a read that did not answer is made again until one does, on a doubling wait capped at 30 seconds. The open stream is its sign that the hub is alive. When the stream ends, stays silent past three keep-alives, or cannot connect, it checks the hub and tries again, waiting longer after each failed try, up to 30 seconds. The hub logs successful reads (GET and HEAD below 400) at Debug, which its default `Info` level leaves out, and logs writes and failures at Info. `HOBBOTS_LOG_LEVEL=Debug` shows every request.

Typed domain failures include runtime unavailable, permission denied, invalid transition, stale version, timeout, executor disconnected and uncertain external outcome. Normalize useful failure categories without erasing vendor evidence. Each connection buffers at most 1,000 frames; a client that falls further behind is disconnected and resumes from its cursor. Disconnecting an observer does not cancel work.

SSE is server-to-client observation. Commands and human approval decisions use authenticated request paths. The stream and every route need an approved device; [ADR 021](../decisions/021-devices-and-remote-access.md) decides the device cookie, the bearer token and the origin rules. Decide executor transport contracts before network-enabled implementation.


## Operational observability

Observability and troubleshooting are release scope, with Effect tracing / OpenTelemetry for cross-agent execution and delegation traces. Keep that integration behind an internal observability boundary; exact SDK versions, exporter/backend, retention and any opt-in telemetry policy remain open. Correlate Quest/task/delegation/attempt/executor IDs so a stalled response or failed continuation can be explained without exposing secret-bearing prompts or credentials. [ADR 026](../decisions/026-backup-export-diagnostics.md) names the IDs that follow a Quest and decides Diagnostics and its redacted report. Product telemetry transmission is not authorized by this documentation artifact.

A hob's backpack ([ADR 019](../decisions/019-hob-backpack-and-continuations.md), [backpack contract](inbox.md#records)) is journaled as `BackpackItemRecorded`, in the same transaction as the change that made the item and right after its events, and `BackpackItemChanged` for every later step (both version 1, each carrying the whole item). `GET /api/backpack`, `GET /api/agents/:agentId/backpack` and `GET /api/quests/:questId/backpack` read the open items, those not yet resolved or failed, highest priority first and then oldest first, with a stream cursor as the Task reads have. `GET /api/blockers` reads the items whose blocker waits for you, with the same cursor, and `POST /api/blockers/:itemId/decision` retries or dismisses the blocker numbered in its payload ([blockers](inbox.md#blockers)). Questions that climbed every lead wait for you: `GET /api/questions` reads them, oldest first, each with the Task it asks about and the same cursor, and `POST /api/questions/:questionId/answer` sends your answer back down the chain, journaled as `QuestionAnswered`. `POST /api/tasks/:taskId/notes` leaves your note on a Task for its nearest lead ([ADR 018](../decisions/018-tasks-and-quests.md#rules)); its payload's `key` is the command's idempotency key and becomes the note's id, so sending it again changes nothing, and the note is journaled as `NoteLeft` (version 1) with the Message item it makes. A Task whose top Task has ended refuses a note, and a question about ended work no longer waits for you or takes an answer. A question still open when its Task is cancelled or fails is withdrawn, journaled as `QuestionWithdrawn` (version 1) with the whole Question. All three are for user sessions only (PE-006). `GET /api/agents/:agentId/history` reads one page of a hob's History ([ADR 018](../decisions/018-tasks-and-quests.md#screens)), with the same cursor. It takes the reader's IANA `timeZone`, which decides where each day starts, and optionally `filter` (`all`, `work`, `you` or `quest`), `days` (1 to 31, 3 by default) and `before`, the `before` of the page above it. A page holds whole days, newest first, each with its events, and says how many earlier days are left. An unknown time zone is a `400`, and an unknown hob a `404 AgentNotFound`. `GET /api/tasks/:taskId/ledger` reads a Task's [responsibility ledger](inbox.md#responsibility-ledger), with the same cursor. The Quest tab's controls, for approved devices only, are `POST /api/tasks/:taskId/cancel`, `POST /api/quests/:questId/cancel`, `POST /api/tasks/:taskId/retry` and `POST /api/tasks/:taskId/reassign` with `{ agentId }` ([orchestration](orchestration.md)). Each answers with the Task's tree and a cursor taken after the change was recorded; a cancel's later confirmed or unresolved outcomes arrive as `TaskStateChanged`, and a refusal is a `409 TaskNotControllable` with its reason. A retry or a reassignment journals its `TaskStateChanged` with `control`, `Retried` or `Reassigned` with the hob that had the Task and its Delegation as it now is; the field is optional, so the event stays version 1. A completion that consumes the items its turn carried journals their `BackpackItemChanged` after its own events.
