# Chat and camps

**Decided, not built** ([ADR 037](../decisions/037-chat-and-camps.md)). Until the slices in milestone v0.0.5 land, the [conversations contract](conversations.md) describes what runs. This contract is the shape the slices build: records, their states, and the rules each must keep. How state changes and events flow is in the [state and events contract](state-and-events.md).

## Channels

A channel is a chat or a camp. The UI says chat or camp and never channel; the code keeps `Channel`.

| Field | Meaning |
| --- | --- |
| `kind` | `chat` or `camp` |
| `goal` | A camp's goal; null for a chat |
| `private` | A private camp keeps nothing in memory: capture skips what was written while it was private, and any message or Attempt that had an entry then, even once it is public again, and a `memory_save` from it is refused. It still reads the memory brief |
| `origin` | The channel and chapter a camp came from, or null |
| `state` | `ChannelLifecycle`: open, archived, superseded |

- Each hob has exactly one open chat, held by a partial unique index. Built in [#1375](https://github.com/otaviobarros/hobbots/issues/1375), with the fields above and [ChannelLifecycle](machines/channel-lifecycle.md). A hob whose chat is archived has none until its next message there opens one, and a chat restored while another is open comes back as a camp.
- **Make a camp** (`POST /api/agents/:agentId/camps`) writes a camp with its title, goal and `private`, and journals `CampMade`, in one transaction. Built in [#1376](https://github.com/otaviobarros/hobbots/issues/1376).
- **Start fresh** (`POST /api/channels/:channelId/start-fresh`) moves the chat to superseded and opens a new one whose `origin` is the old chat, in one transaction that journals `ChatStartedFresh`. It moves the chat's open work: the Tasks you asked for there that are not over, with their trees and Quests, and every backpack item held for it that is not resolved, each journaled as `BackpackItemChanged`. Each Task, open question in their trees, reminder and item the chat's turns carry is recorded once as a `CarriedOver` row (the ADR's `CarriedItem`). The new chat's first turn is told what was carried over, and the dispatcher delivers what waited there once. It is refused, as an archive is, while a reply runs or waits, while an approval waits, or for a retired hob, and for a channel that is not its hob's open chat. A superseded chat is read-only for good and listed with the hob's archived channels. Built in [#1376](https://github.com/otaviobarros/hobbots/issues/1376).
- Both take a key that becomes the new channel's id: the same request sent again returns what it did, and a key that names another channel is refused (`ChannelKeyReused`). Make a camp keeps what it was asked under its key (`camp_requests`), so the request still matches after the camp is renamed.
- **Web** ([#1378](https://github.com/otaviobarros/hobbots/issues/1378)). The sidebar lists every hob's chat under Direct messages and its camps under Camps, pinned first, each with its unread count; Make a camp is the + beside Camps (ADR 039, The sidebar; [#1469](https://github.com/otaviobarros/hobbots/issues/1469)). `#/hobs/:hobId/chat` opens the hob's open chat, or, while it has none, the empty chat whose first message opens one; every way into a hob's chat goes there, and there is no New channel. The chat's header leads with the hob's name over "Your chat with" it; a camp's leads with its title over its hob and its goal. The ⋯ menu offers Make a camp, and Start a fresh chat on the open chat; Rename and Pin are for camps. Make a camp asks for a name, a goal and Private, and says the hob's memory always comes along. Start fresh lists what comes along, read from `GET /api/channels/:channelId/carry-over`, with how many items move; the old chat's address then opens the new chat, on every device, unless a search result points into it. Each sheet is a reducer over a union of its steps (STD-REACT-029), in `apps/web/src/components/camps/`, and keeps its key across a try again, so a request whose answer was lost is not made twice.
- Migration (0095): each hob's most recent open channel becomes its chat; its others become camps with their titles. A skill trial stays a camp.
- Slice: [#1362](https://github.com/otaviobarros/hobbots/issues/1362).

## Members

Who is in a direct message or a camp ([ADR 039](../decisions/039-shared-camps.md#members)): a person or a hob, one `ChannelMember` row per channel and actor.

| Field | Meaning |
| --- | --- |
| `channelId`, `actor` | The channel and who is in it, a person (`user`) or a hob; unique together |
| `role` | `owner` for the person whose channel it is, `member` for everyone else |
| `state` | [Member](machines/member.md): active, left, removed |
| `joinedAt`, `addedBy` | When they joined and who added them |
| `readRevision` | How far they read the channel, the revision of the newest message they saw; a hob's stays null. Unread counts, the unread line and catch-up read it ([#1454](https://github.com/otaviobarros/hobbots/issues/1454)) |
| `mutedUntil` | Until when they muted the channel, or null |

- A channel stored for the first time starts with two members, in the same transaction: the person whose session made it, as `owner`, and its hob, both added by that person. Start fresh gives the new chat the old chat's members. Each is journaled as `ChannelMemberAdded` in the same transaction, after the events that make the channel.
- A direct message (a chat) keeps exactly its person and its hob: adding anyone else is refused (`MemberRefused`, `direct-message`). A camp takes more, journaled as `ChannelMemberAdded`; one who left or was removed comes back, journaled as `ChannelMemberChanged`.
- A hob that retires leaves every channel it is active in, and comes back to every channel it left when it returns, each journaled as `ChannelMemberChanged` in the same transaction as its `AgentUpserted`.
- Migration (0114): every channel gets its owner, with the channel's read marker, and its hob, already left for a retired hob. Built in [#1453](https://github.com/otaviobarros/hobbots/issues/1453).
- **Read markers are per person** ([#1454](https://github.com/otaviobarros/hobbots/issues/1454)). Whether a channel is unread is not part of the channel, which every device of every person sees alike: `GET /api/unread-channels` answers `UnreadChannels`, the channels where a hob wrote since the asking person's own `readRevision`, with `through`, the newest journal sequence the read could see. The web adds every reply that ended after `through`, and reads the list again on a person's `ChannelMemberChanged` and on a chapter that splits, merges or moves. `PUT /api/channels/:channelId/read` moves only the asking person's marker, journaled as `ChannelMemberChanged`, and answers their member row, or null when it did not move. A chapter that splits, merges or moves keeps each person who had read the channel read, and one who had not unread. Catch-up reads the asking person's marker.
- Migration `20261114004500_member_reads` moves each owner's marker forward to the channel's one last time and drops the channel's, and takes `unread` out of every journaled channel (`ChannelUpserted` 6, `CampMade` 3, `ChatStartedFresh` 3, `ChapterMoved` 2). `pnpm --filter @hobbots/server member-reads <copy>` is its dry run on a copy of a hub's data folder: it prints each channel's unread replies by the channel's marker, migrates the copy and prints them again by the owner's row, and fails when any channel differs.

### Mentions

A message's @mentions ([ADR 039](../decisions/039-shared-camps.md#who-answers)) are `Message.mentions`: the hobs and people it names, in the order first named, each once. Built in [#1455](https://github.com/otaviobarros/hobbots/issues/1455).

- `mentionsIn(text, roster, scope)` in `@hobbots/domain` is the one name matcher. A mention is `@` and a name from the roster, matched without regard to case, longest name first. An `@` inside a word, such as an email address, mentions nobody, nor does one in a range of `scope.skip`. The domain reads no Markdown: persistence's `markdownCode` finds the code with a CommonMark parser (`mdast-util-from-markdown`), so code blocks, fenced or indented, in quotes and list items, and code spans are skipped exactly as the spec defines them.
- The repository parses a message in the transaction that stores its final text: as it is sent, or when a reply ends. Text is parsed once: `messages.mentions_through` says how much was, so renaming a hob later changes nothing stored. A reply still streaming keeps what it had: none on its first turn, and after Continue, the mentions of the text it kept. When it ends again, only the text past `mentions_through` is read, and its mentions join after the others. The roster is every hob and person of the hub, not only the channel's members, so a mention of a hob outside a camp is kept for who answers to refuse.
- Mentions of you are yours alone. `ChannelMemberRepository.unreadMentions(actor)` counts, per channel the person is an active member of, the messages that mention them past their own read marker. Their own messages, notes to self and a lead's quiet progress never count.
- Migration (20261114003022): `messages.mentions` is JSON, empty for messages from before, and `messages.mentions_through` is how much of the text was parsed, in UTF-16 code units.

## The floor

Each answer a hob owes a conversation is a `TurnRequest` ([ADR 039](../decisions/039-shared-camps.md#one-hob-speaks-at-a-time)), written in the transaction that stores the message that caused it, one per hob `answerersFor` names, in that order. A conversation is a channel's main line or, once they come, one of its threads.

| Field | Meaning |
| --- | --- |
| `channelId`, `rootMessageId` | The conversation: null `rootMessageId` for the main line |
| `hobId` | The hob that owes the answer |
| `messageId`, `causedBy`, `cause` | The message that caused it, its author, and why (`mention`, `reply`, `relay`, `only-hob`, `lead`) |
| `relayDepth` | 0 for a person's message; a hob's mention adds one to its own turn's depth |
| `state` | [TurnRequest](machines/turn-request.md): waiting, paused, speaking, answered, passed, dropped |
| `replyId`, `droppedBy` | The reply of the turn that took it, and who stopped it |
| `passReason` | Why its hob passed: written while it speaks, once the hob calls `pass`, and kept once `passed` |
| `queuedAt`, `position` | Floor order: the causing message's revision, then its place among that message's requests |

- `ChannelRun` is one run per conversation, in memory. When its floor is free it gives it to the oldest waiting request whose hob takes work (the message Send now picked first), or the dispatcher delivers backpack work.
- Who takes the floor is decided in one place: `decideFloor` (`packages/domain/src/floor.ts`) reads a `FloorSnapshot` (the floor's phase, whether the channel is open or held after a restore, its requests, Send now's pick, and per hob whether it takes work, is a member, is held, and has work or routine progress waiting) and returns one `FloorAction`: `Idle`, `Start` a request (with the dispatch's work riding along when it `carries`), `Dispatch` a hob's backpack work, or `Continue` with that work as the prompt. The channel runner's `advance(line)` reads the snapshot under the line's lock and performs the action, and every path that moves the floor calls it: a message you send, a turn's or a dispatch's end, a wake, removing a queued message and Send now. Continue on a reply you stopped is the one turn started beside it. The line's lock is the admission lock of the hob the channel belongs to (`withChannelLock`); a member's turn is read again once it is registered. Built in [#1549](https://github.com/otaviobarros/hobbots/issues/1549). The request moves to `speaking` in the transaction that saves its turn's reply, together with its queued message's start, and is `answered` when the turn ends. The run publishes the hob speaking and the hobs next (`ChannelRunChanged`).
- A person's message is stored and shown at once. It is queued while a turn runs or a request waits, and starts with its first request's turn; a message several hobs owe is the prompt of each later turn.
- Stop drops the speaking request and the requests its turn caused, and keeps those a person caused. Stop all (`POST /api/channels/:channelId/stop-all`) drops every request still owed; a queued message left with nothing owed leaves the queue as said. Each dropped request records who stopped it. Removing a queued message drops what was owed for it.
- A hob asked to answer that has nothing to add calls `pass` with a reason (`packages/agents/src/pass-tool.ts`), a hub tool every chat turn is offered on every runtime. When its turn ends, `passTurnRequests` ends its speaking requests `passed` with the reason and removes the reply in one transaction, journaled `TurnPassed`, and the floor moves on as after a reply. A pass is refused once the turn wrote text or ran a call other than a read or a hub tool no policy decides, and when the hob is the only one asked as the channel's only hob. The reason is written when the hob calls `pass`, so a restart passes a turn the hub stopped before it ended, unless its stored reply holds text or work. The removed reply's usage and configuration version move to `passed_turns`, which Usage and the instructions check read. Migration (20261114215332): `turn_requests.pass_reason` and `passed_turns`. Built in [#1462](https://github.com/otaviobarros/hobbots/issues/1462).
- At start, a request that was speaking is answered by its interrupted reply, which Continue resumes, and the waiting requests start again in their order: the queue is the records.
- Migration (20261114003401): each queued message gets a waiting request for its channel's hob. Built in [#1461](https://github.com/otaviobarros/hobbots/issues/1461).
- Hobs talking to hobs: a hob's reply saved complete that @mentions other active member hobs of the camp owes each one a `relay` request, written in the transaction that saves it (`upsertMessage`), so a restart cannot lose it, whichever path saved it: a turn, a continued reply or a carried backpack. Its depth is one more than the deepest request its turn spoke for, 1 for a turn nobody asked for. A request deeper than `HOB_RELAY_BUDGET` (3, in `turn-request.ts`) is written `paused` (`relayStateFor`), so the floor never gives it a turn. A reply whose turn was stopped, or that a lead kept quiet, relays nothing, and a reply relays once. The run publishes the hobs a paused relay is between (`ChannelRunStatus.paused`), and the chat shows "Hobs paused, waiting for a person" with Let them go on (`POST /api/channels/:channelId/go-on`), which moves the paused requests to `waiting` at depth 1 and journals one `RelayBudgetReset`. A person's next message there drops them instead, recording who wrote. Built in [#1463](https://github.com/otaviobarros/hobbots/issues/1463).
- Who a turn belongs to is its `Speaker` (`packages/agents/src/speaker.ts`): the channel, the line, the hob that holds the floor, the reason its request records, and whether that hob is the one the channel belongs to or a member. A turn's prompt, brief, skills, pack and tools read the hob from it, and the run publishes it as `speaking`. A message's author is its `actor`, read through `authorOf` and `replyHobOf`. A channel's `ownerHobId` only says which hob the channel belongs to: its owner, its lock and its own default answerer (STD-ARCH-021). Built in [#1549](https://github.com/otaviobarros/hobbots/issues/1549).

## Chapters

| Field | Meaning |
| --- | --- |
| `channelId`, `number`, `title` | Where it is and what it is about |
| `summary` | One line, written by the chapter summary projector when the chapter rests, and again after a split or a merge changes its messages |
| `startedAt`, `endedAt` | When it ran |
| `movedTo` | The camp it moved to, or null |
| state | `ChapterState`: live, resting, moved |

- Exactly one chapter per channel is live, its last, held by a partial unique index. Every message has a `chapterId`: a new message joins the live chapter as it is stored, and a queued one again as it starts. The database refuses a message without one. A channel stored for the first time starts its first chapter in the same transaction, journaled as `ChapterStarted`. A read channel carries its `liveChapterId`, worked out when it is read. Built in [#1379](https://github.com/otaviobarros/hobbots/issues/1379), with [ChapterState](machines/chapter-state.md).
- The hob ends a chapter with `start_chapter` on every runtime ([#1381](https://github.com/otaviobarros/hobbots/issues/1381)). You split with Split here on a message and merge with Merge with previous on a divider ([#1382](https://github.com/otaviobarros/hobbots/issues/1382)), through `GET /api/channels/:channelId/chapters`, `POST …/chapters/split` (the new chapter's id is the request's `key`) and `POST …/chapters/:chapterId/merge`. Both answer the channel's chapters afterwards; a refusal is `ChapterChangeRefused` with its reason. Clients follow the chapter events. The hub starts chapters on its own as well ([#1557](https://github.com/otaviobarros/hobbots/issues/1557)): the chapter break projector, `ChapterBreaks` in `packages/agents/src/chapter-breaks.ts`, reads each message a person sends to an open chat and, when the hub's brain judges it opens a new topic, or under No AI when it follows `CHAPTER_BREAK_IDLE_MINUTES` (180) of idle chat, splits the live chapter there with the id `<message id>:break`, titled by the brain or by the message's first words. It is never at a chapter's first message. The next turn starts a new session from the pack on every runtime, since sessions are keyed by chapter.
- The commands are `ChapterService.startChapter`, `splitChapter` and `mergeChapters` in `packages/agents/src/chapters.ts`, each refused on an archived or superseded channel. Their rules are the pure `planStart`, `planSplit` and `planMerge` in `@hobbots/domain`, run in the transaction that writes the result and journals one event: `ChapterStarted`, `ChapterSplit` or `ChapterMerged`. Starting and splitting take the new chapter's id as their idempotency key; a merged chapter's id is remembered, so merging it again changes nothing.
- Start ends the live chapter, which rests, and refuses an empty title or a live chapter with no message yet. Split cuts a chapter at one of its messages, not its first: the messages from there on make a new chapter right after it, live when the one it came from was. Merge brings a chapter's messages into the chapter before it, which keeps its id and title and is live when the merged one was. Both number the chapters again from 1.
- A runtime session belongs to one chapter and one hob: `RuntimeSession` is keyed by channel, chapter, runtime and hob ([ADR 039](../decisions/039-shared-camps.md), [#1464](https://github.com/otaviobarros/hobbots/issues/1464)), and `liveSession` gives the one a hob's turn resumes. Each hob in a channel resumes only its own session, and a hob that has not spoken in the live chapter starts a new one from the context pack. Migration 20261114005209_hob_sessions gave every earlier session its channel's hob. ADR 039 also keys a session by thread, which is not built yet. A turn in a new chapter, after a start, a split of the live chapter or a merge into it, starts a new session in place of the old chapter's, which is never resumed, on Claude Code, Codex and every runtime alike. A new chapter's session starts from the context pack ([#1380](https://github.com/otaviobarros/hobbots/issues/1380)), and a brain switch is briefed with the live chapter's transcript alone. A merge into the live chapter makes it live again with a new session: each session records how many chapters had been merged into its chapter when it started (`chapterMerges`), and `liveSession` resumes it only while that matches `Channel.liveChapterMerges`. So a session a turn under way records after the merge, from a read before it, is never resumed, with no lock shared between the turn and the merge. The merge also drops the sessions the chapter held. A split or merge also drops the channel's briefing checkpoint and the summaries of the chapters whose messages it changes, and gives the messages it moves the revision of its event, so a client holding an older version takes the new one; a channel you had read stays read.
- Moving a chapter into a camp re-parents it with its messages, decisions, artifacts, open questions and the quests it started, in one transaction, and leaves a stub. A running quest moves whole.
- Migration (0099): each channel gets one live chapter holding its history, started when the channel was made, with no title; every message joins it, and every session the channel keeps belongs to it and goes on being resumed.
- Slices: [#1363](https://github.com/otaviobarros/hobbots/issues/1363), [#1364](https://github.com/otaviobarros/hobbots/issues/1364).

## Records

Each is written in the same transaction and journal as the message that made it, and carries an explicit `actor`.

| Record | Key fields | States |
| --- | --- | --- |
| Decision | text (at most 500 characters), actor, channelId, chapterId, sourceMessageId, supersededBy | [DecisionState](machines/decision-state.md): active, superseded; a changed decision is kept, crossed out |
| Artifact | kind (code, page, doc, email, image, PR, file), title, latestVersion, origin | a registry over what Attempts and Quests record; copies nothing |
| Brief | channelId, text, writtenBy (the hub), source (brain or rule), basis cursor, revision | one per channel, rewritten by the brief projector at chapter ends and quest steps; no lifecycle, the rule `briefChange` says when a rewrite writes |
| CampSuggestion | channelId, chapterId, reason codes and counts, the camp's suggested title and goal | pending, open, kept, accepted, expired; at most one per chapter |
| CarriedOver (the ADR's CarriedItem) | fromChannelId, toChannelId, ref (Task, question, reminder or backpack item), label | written once by Start fresh |
| Claim | scope (sequence, path, branch), repository, key, holder Task, actor | [Claim](machines/claim.md): held, contested, taken, released. A number is unique in its folder of a repository for good; an open path or branch once per Task |

A note to self is a message role that never wakes the dispatcher.


### For you

One list per person of what is theirs to act on ([ADR 039](../decisions/039-shared-camps.md#cards-every-channel-shares)), topped by "While you were away". Built in [#1456](https://github.com/otaviobarros/hobbots/issues/1456); the screens that show it are [#1470](https://github.com/otaviobarros/hobbots/issues/1470).

- `GET /api/for-you` answers `ForYouRead`: the stream cursor, then `ForYou` for the person whose device asks, read from the session's user, never a fixed owner. It is worked out by the pure `forYouOf` in `@hobbots/domain`, with no model call.
- **Items.** Each `ForYouItem` names who it is `for` (an actor) and when it started waiting, and the list is oldest first: `Mention` (a message that mentions you past your read marker, by the same rule as the unread-mention count), `Question` (a Task's question that climbed every lead), `HubQuestion` (the hub's own, for its owner), `Approval` and `Review` (an artifact waiting for review). Questions, approvals and reviews go to their decider, `deciderOf`: the person who asked for the work, else the channel's owner member, else the hub's owner (`hubOwner` in `@hobbots/agents`). No record names a requester yet, so today it is the channel's owner.
- **While you were away** lists, for each channel you are an active member of with news, `ChannelAway`: your marker and the changes since it, the latest change first. It is the same `awaySummaryOf` catch-up uses, so both list the same mentions, decisions and changed artifacts for the same records and read marker, and both leave out what you wrote yourself. A Quest waiting on approvals and questions says it needs you only to the channel's decider (`AwayInput.decides`); every member still hears when it ends. Catch-up gained `Mentioned`, a message that mentions you.
- Persistence reads it in a few queries across your memberships (`ForYouRepositoryLive`): the messages that mention you, the decisions and artifacts past your marker, and the Quests of channels whose summaries changed since; then every pending approval, waiting question and artifact waiting for review, with each channel's owner.
- The tray, the Inbox page and catch-up still read their own sources until #1470 moves the screens onto this list.

### The camp sheet, notes, pins and catch-up

Built in [#1387](https://github.com/otaviobarros/hobbots/issues/1387).

- **The camp sheet.** A camp's header has This camp, which opens its sheet beside the chat (`apps/web/src/components/camp-sheet/`): Overview with "Where we are" (`GET /api/channels/:channelId/brief`), the Quests started there with their progress strips, its chapters and its settings; Decisions, newest first, where you add one, change one, which records a new decision that crosses the old one out, or cross one out, and a crossed-out one stays with what changed it; Artifacts, one row per artifact at its latest version, filtered by kind, each opening to where it is, who made it and the message it was made at; and Mine, your pins and notes to self. Every list is the hub's, read again on its event (`DecisionRecorded`, `DecisionSuperseded`, `ArtifactRegistered`, `BriefWritten`, `MessagePinned`, `MessageUnpinned`) after cancelling a read on its way (STD-REACT-012).
- **Private from now on** ([#1377](https://github.com/otaviobarros/hobbots/issues/1377)). The Overview's Private camp switch calls `PUT /api/channels/:channelId/private`, and says that what memory captured before stays. Capture stops from the next change on, as the private-camp rule reads `private` when each entry is captured; nothing captured before is removed. A chat has no such setting (`409 ChannelNotCamp`).
- **Notes to self.** `POST /api/channels/:channelId/notes` writes a message with the `note` role, by you, under the client's `key`, which becomes its id: the same note sent again returns it, and a key that names anything else is refused (`409 MessageKeyReused`). It is written under the hob's lock, so it takes its place in the channel's order, and it wakes no hob. No hob reads one: every transcript a turn, a pack, a continuation, memory capture, the chapter and brief projectors or `read_message` reads leaves notes out (`hobReads`), and notes count toward no camp suggestion. The composer's Note to self writes one; the transcript shows it in a dashed box, under "Note to self · only you".
- **Pins.** `PUT /api/channels/:channelId/messages/:messageId/pinned` pins or unpins a message of the channel, kept in `message_pins` (migration 0107) apart from the message, so pinning leaves the message's revision and the channel's unread state as they are; a pin follows its message into a camp, and goes with it. `GET /api/channels/:channelId/pins` lists them, the newest first. A message's ⋯ menu has Pin and Unpin, with Split here where it can start a chapter.
- **Catch-up.** `GET /api/channels/:channelId/catch-up` is worked out by the pure `catchUpOf` from your own read marker, your member row's `readRevision`, and the channel's records: the replies that landed since, routine progress left out, the first of them, when you last read, and up to `CATCH_UP_MAX` (6) changes, what waits on you first, then the newest, with how many more there were. Your own decisions, uploads and notes are left out. The chat reads it at each visit to an unread chat, opening it or bringing its window to the front, before it marks the channel read, and shows "New since you left" before the first unread reply with "While you were away" until you fold it. Each visit reads its own catch-up, even after the chat view mounts again. A catch-up that cannot be read keeps the channel unread and offers Try again, or Skip, which marks it read.
- **The suggestion card.** A chat's open camp suggestions show as a card after its transcript, with why in chips. Make it a camp opens Make a camp with the chapter coming along, a switch you can turn off, which moves the chapter into the new camp; Keep it in my chat keeps it and says it won't come back. A chat chapter's ⋯ menu has Make a camp from this chapter.

### Decisions and artifacts

Built in [#1383](https://github.com/otaviobarros/hobbots/issues/1383): `Decision` and its [DecisionState](machines/decision-state.md) machine in `packages/domain/src/decision.ts`, `Artifact` and the registry's rules in `artifact.ts`, the store in `packages/persistence/src/records.ts` and `artifact-rows.ts` (migration 0101), and `Records` and `record_decision` in `packages/agents/src/records.ts`.

- **`record_decision`** is a hub tool on every runtime that serves hub tools, Claude Code, Codex and the fake one alike, offered to a turn that writes a reply in a chat or camp. It takes the decision's `text`, a `key` and, for a decision that changes an earlier one, `replaces` with its id. The decision is recorded by the hob, from the reply, in the reply's chapter, redacted as everything the journal holds is. A text over 500 characters, an empty one, or a closed chat or camp is refused, and nothing is written. The same key with the same input returns the first decision; with another input it is refused.
- **Replace and cross out.** A decision is never edited. A new one that replaces an earlier one crosses the old one out in the same transaction, which points at the new one. You can record a decision in the app, replacing one or not, and cross one out with nothing in its place. The routes are `GET` and `POST /api/channels/:channelId/decisions` and `POST /api/channels/:channelId/decisions/:decisionId/cross-out`. A crossed-out decision is kept and listed, and never comes back.
- **Artifacts.** The registry is filled in the transaction that journals what it indexes, by a pure rule as backpack items are: a Task's results as it completes (a file by its path, a link by its URL, a text by its id), an Attempt's settled changes that left a file, and the files a finished reply's tool steps wrote. Each artifact is one row in its chat or camp, by where it is, at its latest version: every record that made or changed it counts once, and the same record again changes nothing. Its kind comes from its name or URL: code, page, doc, email, image, a pull request, or another file. `GET /api/channels/:channelId/artifacts` lists them, the most recently changed first.
- **Reviews.** Built in [#1422](https://github.com/otaviobarros/hobbots/issues/1422): each artifact's review, held by its [ArtifactReview](machines/artifact-review.md) machine, waits for you until you review or dismiss it, once, with when and by whom (migration 0105, which gave every stored artifact a waiting review). `POST /api/channels/:channelId/artifacts/:artifactId/review` with `{ outcome: "reviewed" | "dismissed" }` settles it; the same review again answers it unchanged, and one settled the other way is refused (`409 ArtifactReviewChangeRefused`). A new version keeps its review. When a moved chapter's artifact joins the camp's at the same place, a review settled on the moved one is carried over to one still waiting, journaled as `ArtifactReviewSettled` with the move; one the camp already settled keeps its own, since a settled review is final. The move recounts the Quests whose Tasks made the artifacts it moved. The GitHub Charm asks GitHub every five minutes, with the sign-in of the hob that made it, how each pull request still waiting stands, and reviews one GitHub reports merged or closed, by `{ kind: "hub", id: "github" }`; asking GitHub happens before the command, never inside it. The camp sheet's Artifacts tab tags each artifact waiting for you To review; opening one says where its review stands, and who settled it and when, with Mark reviewed and Dismiss while it waits. `ArtifactReviewSettled` reads the camp's artifacts again.
- **Versions and the viewer.** Built in [#1434](https://github.com/otaviobarros/hobbots/issues/1434): every file is kept at one canonical place. A Task's result given by a relative path is resolved against its Attempt's folder (where it changed a file at that path, else the first folder it scanned), and `complete_task` stores the placed absolute path. Before this, a member that returned `social.md` and also wrote it made two rows; migration 0108 moves each stored file to its one place and merges two rows of one camp there, as a moved chapter's artifact joins the camp's (the newer fields, a name a record gave, a settled review carried over), and fixes the find index and each Quest's ready-for-review count. Each record that saw an artifact says which version it made, which Attempt's work it is and when the hub saw it, and the records of one Attempt are one version. `GET /api/channels/:channelId/artifacts/:artifactId/versions` lists them newest first, how the artifact is shown (document, diff, page, image, link or none) and where each version's contents are: kept by the Attempt, read now (the latest version of a file), or not kept. `GET …/versions/:version` serves one version's bytes, read only: what the hub kept, or the file as it is now, only inside the folders of the hob whose camp it is in, never through a link out of them nor a file named as a secret's, text redacted as a turn's tool output is and cut to the preview size (`404 ArtifactContentUnavailable` with the reason). The camp sheet's Artifacts tab previews each row (its first lines, an image's thumbnail), shows only the kind filters the camp has, and opens an artifact drawn by its kind, in the sheet or a full viewer: a document rendered with its source a click away, code as a diff against the version before, a page in a frame without scripts or network, an image, a link as a card, with its older versions to pick from.
- **Events.** `DecisionRecorded`, `DecisionSuperseded`, `ArtifactRegistered` and `ArtifactReviewSettled`, version 1, each with the whole record. An `ArtifactRegistered` journaled before reviews reads as waiting.
- **Authors.** Every message names its author: you (`{ kind: "user", id: "owner" }`, the hub's one person until shared camps) or the channel's hob, set as the hub stores it. Migration 0101 gave every stored message and every journaled `MessageUpserted` and `MessageQueued` one, and the database refuses a message without one. Decisions, artifacts and claims carry theirs.
- **The pack.** `RecordPackSource` gives the context pack `Records.activeDecisions` and `Records.artifactsOf`, so a new chapter's first session starts from the decisions that hold, newest first, and the artifacts index, and never from a crossed-out decision ([#1380](https://github.com/otaviobarros/hobbots/issues/1380)).
- **Chapters.** A split moves the decisions and artifacts of the replies it moves to the new chapter, and a merge moves all of the absorbed chapter's into the one it joins, in the transaction that moves their messages.
- **Find.** `GET /api/find?q=&in=&kind=` finds decisions, artifacts and chapters by every word typed, from the find projector's index, beside the settled messages that say them, in one chat or camp or, with no `in`, everywhere but private camps. Each row is checked against where its record is now, so a record moved since it was indexed, such as into a private camp, is left out until the projector catches up, and a decision's state is read live. A crossed-out decision is found and marked. `POST /api/find/ask` answers a question from the records that match it on the hub's brain, citing each by the message it came from; under No AI, or when the brain gives no usable answer in time, it returns the matches with the reason, and the Find box lists them in the answer card. Ask matches any word of the question, so it can find records that Find, which needs every word, does not. Both emit no events ([#1386](https://github.com/otaviobarros/hobbots/issues/1386)).

### Camp suggestions and moving a chapter

Built in [#1385](https://github.com/otaviobarros/hobbots/issues/1385): `CampSuggestion` and its [CampSuggestionState](machines/camp-suggestion-state.md) machine in `packages/domain/src/camp-suggestion.ts`, the pure move in `chapter-move.ts`, the store in `packages/persistence/src/chapter-moves.ts`, `camp-suggestion-rows.ts` and `camp-suggestions.ts` (migration 0104), and `CampSuggestionService` and the `CampDrift` projector in `packages/agents/src/camp-suggestions.ts`.

- **Moving a chapter.** `POST /api/channels/:channelId/chapters/:chapterId/move` moves a chapter into an open camp of the same hob (`{ _tag: "camp", campId }`) or a new one (`{ _tag: "new", key, title, goal, private }`), in one transaction: its messages, the decisions and artifacts recorded in it, its open questions, approvals and tool records, and the quests started in it with their open backpack items, and the approvals, web use and hob proposals their Tasks' turns made outside any reply. A running quest moves whole, and its `QuestSummary` names the camp from the move's transaction on. The chat keeps the chapter as a stub, `moved` with the camp it went to, and the chapter becomes the camp's live one: a new camp's empty first chapter takes it, and otherwise the camp's live chapter rests and the moved one follows it. Moving the chat's live chapter starts a new one there. Every session of both channels is dropped, since the records they started from moved, so both next turns start a new session from their pack, whichever chapter moved. A moved step's full tool log stays readable from the camp: the step names the channel its log was kept under (`loggedIn`). A client moves the messages it already holds to the camp's chapter at the move's revision, cancels any transcript read already on its way, and reads both transcripts and chapter lists again. A move while either channel has a reply under way or an approval its reply waits on is refused (a party member's approval waits in its own Task's session, so it moves with its quest instead) (`409 ChapterMoveRefused` with `reply-running`), as are a closed channel, a target that is not an open camp of the hob, a moved chapter and an empty one. The same move again answers with the first one. It is journaled as `ChapterMoved` (version 1: both channels, the stub, the chapter as it landed and each channel's chapters afterwards).
- **Which quests.** A top Task started in a chat or camp records the chapter it was started in (`tasks.chapter_id`, migration 0104), kept up to date by splits, merges, Start fresh and moves.
- **Suggestions.** A pure rule in the transaction that journals a chat's records raises a suggestion for its live or resting chapter once it reaches any named threshold: `CAMP_SUGGESTION_DECISIONS` (5), `CAMP_SUGGESTION_ARTIFACTS` (4), `CAMP_SUGGESTION_QUESTS` (2) or `CAMP_SUGGESTION_MESSAGES` (80 settled messages). Its reasons are codes and counts. A chapter gets one suggestion at most, held by a unique index, so a suggestion you kept in the chat never comes back. The drift projector can raise one too (see [state and events](state-and-events.md)). A suggestion is raised `pending` ([#1557](https://github.com/otaviobarros/hobbots/issues/1557)): the same projector asks the hub's brain whether its chapter holds one topic, and offers it with the camp's `title` and one-line `goal` the brain suggests, journaled as `CampSuggestionOffered`. Under No AI, or on a fallback, the title is the chapter's own and there is no goal; the rule finds several topics where the chapter holds an idle gap. A chapter that holds several is never offered: the suggestion is withdrawn (expired), the chapter's last topic splits off at the line the brain names or the last gap, and that part is raised again on its own counts, all in the split's transaction. Any split, by you or by the hub starting a chapter, does the same for the part, and withdraws the cut chapter's pending suggestion when the thresholds it was raised for went with the part. A split the hub judged, to name a suggestion or to start a chapter, carries the chapter and revision it judged and is refused as `chapter-changed` when either moved, and is judged again; a suggestion raised before its chapter held a line is named once a message arrives. An offer or withdrawal judged from a chapter whose revision moved since (a split, merge, new chapter or summary) is left pending and named again. Make a camp prefills the title and goal, or the chapter's own title for a suggestion with none (migration 20261114193617_camp_suggestion_names). Moving the chapter accepts its suggestion; merging the chapter away, closing the chat or Start fresh expires it. `GET /api/channels/:channelId/camp-suggestions` lists the open ones, and `POST /api/channels/:channelId/camp-suggestions/:suggestionId/keep` keeps one in the chat (`409 CampSuggestionChangeRefused` for one settled otherwise or not there). They are journaled as `CampSuggested`, `CampSuggestionOffered`, `CampSuggestionKept`, `CampSuggestionAccepted` and `CampSuggestionExpired` (version 1), each with the whole suggestion; the `title`, `goal` and `pending` state were added compatibly.
- **Not built yet.** The chat's chapter list keeps the moved chapter's stub, but its transcript leaves a moved chapter out, so the stub does not show there yet. The suggestion card and Make a camp from a chapter are built ([#1387](https://github.com/otaviobarros/hobbots/issues/1387)), above.

## The context pack

Built in [#1380](https://github.com/otaviobarros/hobbots/issues/1380). `buildPack(records, budget)` in `packages/agents/src/context-pack.ts` is pure and deterministic. It makes a new runtime session's starting context, on every runtime, from:

1. the memory brief (its own budget, ADR 028), sent beside the pack as before and counted against its budget,
2. in a shared channel, who is here and why the turn runs ([#1465](https://github.com/otaviobarros/hobbots/issues/1465)),
3. the camp brief, as the brief projector last wrote it ([#1384](https://github.com/otaviobarros/hobbots/issues/1384)),
4. active decisions,
5. the channel's open work: the Quests under way in it, from their `QuestSummary`, then its open Tasks with their last step, the questions in them still waiting for an answer, and the backpack items its turns carry, as Start fresh would carry them,
6. what Start fresh carried, until the hob first replies in the new chat,
7. the artifacts index,
8. one line per resting chapter,
9. the live chapter's turns before the prompt, each under its author's name.

Each part has a share of the budget (`PACK_BUDGET`: 12,000 tokens, counted as four characters a token), and the shares add up to it. The pack never goes over its budget, even when the briefs and the active decisions alone would.

- **Which session.** A turn with no session to resume in its live chapter starts from the pack: a new chapter's first turn, a turn after a split or merge of the live chapter, and a brain switch, whose pack replays the live chapter. A resumed session hears only what other brains wrote in the live chapter since it last replied (ADR 017).
- **Several hobs** ([ADR 039](../decisions/039-shared-camps.md#the-context-pack-with-several-hobs), [#1465](https://github.com/otaviobarros/hobbots/issues/1465)). The transcript names every speaker: "Marina (person)", "Quill (hob)", and "You" for the hob's own replies. `makePackPeople` in `packages/agents/src/pack-people.ts` reads the names from the members, the users and the hobs. A shared channel, with more than one hob or more than one person, also gets the members part: "## Who is here", the hob's own name, why the turn runs ("Leo mentioned you.", "You are the only hob here.") and the active members, the reason kept when the list is cut. A direct message gets none, since it says nothing the hob does not know. The reason is the floor's `TurnRequest` cause when a turn is handed one; until then `turnReasonOf` works it out from the prompt with `answerersFor`. A resumed session that missed what others said, another hob's reply or people's messages no hob answered, hears it as "## Since you last spoke": the messages since its hob last spoke in the line, each under its author's name, within the live chapter's share, the oldest counted with the ids of the newest of them for `read_message`, and the reason when another actor asked it. Otherwise a resumed session hears only what its own hob wrote on other brains, as before. The memory brief is always the turn's own hob's (ADR 028): a hob never reads another member hob's.
- **Memory in a shared channel** ([ADR 039](../decisions/039-shared-camps.md#memory-in-a-shared-channel), [#1466](https://github.com/otaviobarros/hobbots/issues/1466)). Capture sends a channel's session to each hob's own memory, as that hob, tagged with the channel by the session's start. A hob's memory keeps its own replies and their tool steps, the Quests it led and the work that woke it, and a person's message only once that hob took a turn on it: the reply's `promptId` names the message, which capture reads with `MemoryCaptureLog.messages` and sends before the reply, with its author as `(from user <id>)`. A message written before capture last started from the journal's head (`memory_capture.since_at`) is never kept, since capture cannot know whether its camp was private then. Another hob's replies, and a message no hob answered, reach no hob's memory. The author of a reply (`Message.actor`) names whose memory it goes to, not the channel's hob. Archiving a channel, Start fresh or making a camp private ends its session in every hob's memory, and a private camp's entries reach none of them, as before.
- **Over budget**, the parts with a fixed share are cut at it: the briefs at their share, and the parts that never drop silently fitted to theirs. What the others leave goes first to the live chapter, then the artifacts, then the resting chapter lines, so they trim in ADR 037's order: resting chapter lines, the oldest artifacts, the live chapter's oldest turns. Each trim leaves one line saying what was left out.
- **Active decisions and open work never drop silently.** Decisions: the newest in full while every older one still fits by title, newest first; past that, the newest titles and a count. Open work: what does not fit is counted.
- **A last turn too large for its share** is carried as its start and end with `[… N characters left out. Read the rest with read_message, message_id <id>.]` ([#1381](https://github.com/otaviobarros/hobbots/issues/1381)).
- **Resting chapters.** Each is one line with the summary the projector wrote. Until it has, the pack writes the plain one in its place (how many messages, and the first of yours), so a new chapter's first turn never runs without the last chapter's summary.
- **The summary projector.** `ChapterSummaries` reads the journal after its cursor in `projector_cursors`, and gives each chapter that came to rest its one-line summary (at most 280 characters), asked of the hub's brain with the plain summary as its rule, so under No AI it is the plain one. It writes each through `ChapterStateMachine`'s `Summarize`, journaled as `ChapterSummarized`, with the cursor, in one transaction.
- **The brief projector.** `CampBriefs` reads the journal after its own cursor in `projector_cursors` and writes the brief of each chat or camp where a chapter ended, a split or merge changed the chapters, or a Quest took a step (it started or ended, a Task in the channel ended, completed, failed or cancelled, a step or a member's Task with no Quest of its own included, or a milestone was reached). It asks the hub's brain (task `brief`) with the channel's goal, decisions, artifacts, open work, chapter summaries and the live chapter's last messages; its rule is the plain brief: the goal, the decisions that hold and what the channel made, newest first, with a count of what does not fit. Under No AI the plain brief is written and no model is called. The projector cuts every brief at its share of the pack (`CAMP_BRIEF_MAX`, 2,000 characters less the heading), so the pack carries it whole. It writes each through the rule `briefChange`, journaled as `BriefWritten`, with the cursor, in one transaction: a brief from no further along the journal than the stored one, or one that says the same, writes nothing. When the brain was asked and gave no answer that decodes (`HubDecider` answers `fallback`), or none within two minutes, a brief the brain wrote stays in place; one the rule wrote, or none yet, takes the plain one. When nothing the plain brief would say holds any more, such as after the last decision it named was crossed out, the brief is cleared to empty text and the pack carries none. A turn only reads the brief that is there, so a slow brain never holds it up. `GET /api/channels/:channelId/brief` reads it for the camp sheet ([#1387](https://github.com/otaviobarros/hobbots/issues/1387)).
- **Private camps.** A camp's pack reads only its own chapters and its own brief, so a private camp's summaries and brief reach no other camp's pack, and memory capture takes nothing from `ChapterSummarized` or `BriefWritten`.
- **`PackReport`** records each part, its share and size in tokens, and what it trimmed. Each pack a turn reads is logged with it, and `PackReports` keeps the last one per channel for the Focus chip. `GET /api/dev/channels/:channelId/pack`, served only by a hub run from a checkout, shows it with the pack the next new session would read.
- **The Focus chip** ([#1382](https://github.com/otaviobarros/hobbots/issues/1382)) reads `GET /api/channels/:channelId/focus`: the report `PackReports` kept of the channel's last new session (`last-turn`), or, when it kept none, as after a restart, the report of the pack the next new session would read (`next-session`). The client groups the parts into rows and shows the sizes as the report has them; it never measures anything itself.
- Slice: [#1363](https://github.com/otaviobarros/hobbots/issues/1363).

## Quests in camps

- A quest belongs to the channel that started it (`Quest.channelId`, `Task.channelId`). Its updates and questions land there: each backpack item for its lead is carried by the channel of the quest's top Task, so its lead's next turn about it runs in that chat or camp ([#1389](https://github.com/otaviobarros/hobbots/issues/1389)). A quest started outside any chat has no channel, and is routed as before.
- A quest moves with the chapter that started it, in the move's transaction, and a running one moves whole: its Tasks, its Quests, its open backpack items, and what its Tasks' turns made outside any reply (a member's approvals, web use and hob proposals). A crash midway leaves it where it was. Its next update, question or result then lands in the camp. A member's session that started before the move still asks in the right place: a request asked outside any reply is written in the channel its Task is in at that moment, and a decision saved after a move names the channel the request is in now, both read in their own transaction. Start fresh moves a chat's open quests the same way.
- A quest opens as a channel in its camp's sheet. ADR 027's records stand; its lanes layout is retired. Built in [#1390](https://github.com/otaviobarros/hobbots/issues/1390), in `apps/web/src/components/quest-sheet/`:
  - **The quest pill.** A camp's header counts its own quests under way from their `QuestSummary`: "2 quests · 1 ready for review · 1 needs you". It opens the camp's sheet, whose Overview lists the quests; a row opens its quest in the same sheet, with Back to the camp. A chat's quest opens in a sheet of its own from its ticket or header button, with no Back. The quest in the sheet is in the address (`?quest=`), so a link opens it.
  - **The quest's pane.** Its title, how far it is, each hob's work (its Tasks, your notes passed on and its cards), then the quest's channel: your request and the lead's plan, what you sent while it ran with its steer receipt, the lead's replies while it ran (a quiet one stays out), notes the lead passed on, and each member Task's result or failure, oldest first. Its composer writes to the lead in the quest's chat or camp, so a message sent while the work runs gets a receipt as in the chat. The chat's and camp's unread dot is the unread marker; the quest adds none of its own.
  - **The Workbench.** Show the work, or a hob's work, opens the quest's Workbench beside the chat (`?quest=&tab=`), with Back to the quest and Close; the chat folds away beside it as before.
- `QuestSummary` on the hub feeds the quest pill, the sidebar and Home. Built in [#1373](https://github.com/otaviobarros/hobbots/issues/1373): `QuestSummary` and its fold `questSummaryOf` in `packages/domain/src/quest-summary.ts`, the rows in `packages/persistence/src/quest-summary-rows.ts` (migration 0104).
  - **What it says.** Its Quest's lead, channel, parent Quest and state; how many Tasks under the Quest's own Task take each tone (`needs`, `working`, `waiting`, `done`, `problem`, `idle`, as `workTone` maps a Task's state); how many things need you while it runs (each question that climbed every lead and each pending approval on its Tasks, its own included, and each Task under it that failed, as the quest ticket counts them); and how many things are ready for review: the registered artifacts of a kind you review (`pr`, `doc`, `page`, `code`) that its completed Tasks, its own included, made, by a result they returned or their Attempts' file changes, and that still wait for your review, each once.
  - **When it changes.** A pure fold over the Task tree, run in the transaction of every change whose events touch the tree: a Task created or moved, a Quest started or ended, a question asked, escalated, answered or withdrawn, an approval requested or decided, an artifact a Task made registered or its review settled, a chat started fresh, which moves its Quests' channel, and a chapter moved into a camp, which moves the Quests started in it. Each summary that says something new is written with its `QuestSummaryChanged`, after the change's own events and what they call for; one that says the same is neither written nor journaled. No projector is involved, so a client never sees a Task's change without its Quest's summary.
  - **The snapshot.** `GET /api/quest-summaries` lists every active Quest's summary, and `?channelId=` every Quest followed in that chat or camp, ended ones included, with the stream cursor. The web client renders it ([#1374](https://github.com/otaviobarros/hobbots/issues/1374)): the quest pill, the quest's pane, the ticket, the finished banner, a hob's page and Home read their counts from it, the pill shows what is ready for review, and a `QuestSummaryChanged` replaces a Quest's summary when its revision is newer.
- Slice: [#1365](https://github.com/otaviobarros/hobbots/issues/1365).

### Quests as work threads

[ADR 041](../decisions/041-quests-as-work-threads.md) replaces the Quests above step by step. Step 1, built in [#1596](https://github.com/otaviobarros/hobbots/issues/1596), adds the new record beside them; in code it is `WorkQuest` until [#1602](https://github.com/otaviobarros/hobbots/issues/1602) retires the old one.

- **The record.** `WorkQuest` and its [WorkQuest](machines/work-quest.md) machine in `packages/domain/src/work-quest.ts`, kept in `work_quests` (migration 20261116004540) by `WorkQuestRepositoryLive` in `packages/persistence/src/work-quests.ts`. It holds its title, goal, "Done when" lines, optional expected day and repository, its owner, who asked for it (the actor of the turn request its starting reply answers, or the hob itself when none does), its state (`active`, `waiting`, `done`, `stopped`), and once done its result and what it made. A conversation (a channel's main line, or a reply thread once those come) runs at most one Quest that is active or waiting, held by a partial unique index.
- **The tools.** `start_work` and `finish_work` (`packages/agents/src/work-quests.ts`) are hub tools every chat turn is offered on every runtime that serves hub tools, Claude Code, Codex and the fake one alike. `start_work` takes a title, a goal, the "Done when" lines and an optional `expected_by` day and repository, and starts the Quest where the hob is talking; a second running Quest there is refused as `busy`. `finish_work` takes a result and what the work made and moves the hob's own running Quest to done. Each is written with its journal entry in one transaction, and the same reply calling again gets the same Quest back and journals nothing. A Codex session started without them is not resumed.
- **The card.** `apps/web/src/components/work-quest/` shows the Quest as one living card under the reply that started it, and a finished one leaves one line under the reply that finished it. `GET /api/channels/:channelId/work-quests` lists a channel's Quests, oldest first.
- **Moves and passes.** A Quest moves with the chapter its starting reply moves in, journaled `WorkQuestChanged`, and a move that would bring a running Quest into a camp that runs one is refused with `quest-running`. A reply a Quest started or finished from is kept when its hob passes, since the card hangs from it.
- **Who answers and stays.** The owner of a Quest running in the main line answers a message that mentions nobody, as a running Quest's lead does, cannot be removed from the camp while it runs, and holds its chapter where the camp it would move into does not admit them. A new session's context pack lists each running Quest with its goal and "Done when" lines first in its open work.
- **Not yet.** Waiting, waking, stopping and reopening are machine rules only until reply threads ([#1484](https://github.com/otaviobarros/hobbots/issues/1484)) wire them.

## The claims register

Built in [#1388](https://github.com/otaviobarros/hobbots/issues/1388): `Claim` and its machine in `packages/domain/src/claim.ts`, the register in `packages/persistence/src/claims.ts` (migration 0098), and `claim` with the Task tools on every runtime.

- **`claim`** is a Task tool. It records a claim for the Task the hob works on, and in a chat with no Task yet it starts one, as `plan_steps` does. A claim names a folder of the hob's, inside a Git repository. The repository is known by its `origin` remote, so two clones or worktrees share their claims. The named folder is resolved, links and `..` taken as the kernel walks them, before it is checked against the hob's folders, and a hob given part of a repository claims paths and numbered folders only inside that part.
- **Sequences.** A `sequence` claim is the next number in a folder whose files start with one: migrations, ADRs, or any other numbered files. The hob names the folder whose files the numbers count, such as `docs/decisions`. The hub reads that folder on the repository's default branch as the clone has it (`origin`'s HEAD, else `origin/main`, else `main`), without running Git, and hands out one past every number `main` and the register hold. A number the hob already uses is kept when it is free; otherwise the hub settles on the next free one and says so. Concurrent claims take the journal's head in turn, so each gets its own number.
- **A released number is never handed out again** (decided in #1388). Reusing it would keep numbers dense, but a number seen in a closed branch would then mean two things. A number is unique in its folder of a repository for good, released or not.
- **Paths and branches.** A pure rule in the claim's transaction finds clashes with every other Task's open claim in the same repository: the same branch, or a path that is the other or inside it, comparing whole names. The new claim and each held claim it clashes with become contested. Each lead involved gets a `claim-clash` backpack item: the nearest lead still at work above the Task, or its owner when nobody leads it. Neither Task is stopped. A claim of the same path or branch by the same Task again changes nothing. It calls no model.
- **Release.** A Task's claims are released in the transaction that ends it, completed, failed or cancelled, at any depth; a contested claim that clashes with nothing left goes back to held. A retry that reopens a failed Task does not bring its claims back, and the retried Task may claim the same paths and branches again.
- **The Heads-up.** A chat or camp shows a Heads-up for each group of open claims that clash, when a Task of its own holds one of them: who holds each side, on which path or branch, a note when a side's work is in another chat or camp, and who claimed last, as "Spotted by the hub". It sits in the transcript where the last of those claims was made, and goes once the clash is gone. `GET /api/channels/:channelId/clashes` reads them from the register (`ClaimRegister.clashesIn`, the groups `clashGroups` finds); the client reads them again on each Claim event. It calls no model ([#1390](https://github.com/otaviobarros/hobbots/issues/1390)).
- **Take over** ([#1449](https://github.com/otaviobarros/hobbots/issues/1449)). You take over a Task's files and branches from its hob's ⋯ menu in the quest (`POST /api/tasks/:taskId/take-over`, user sessions only). Its open claims become `taken`, with you as their actor, each with its own `ClaimTakenOver` event, in one transaction; the Task's hob gets one `claims-taken` backpack item naming them, and its Task keeps running. From then on the hub refuses any hob's write to a taken path, from any clone or worktree of the repository, a push of a taken branch and a commit while it is checked out, before the policy decides the call, on every runtime: `CallSteering.takenByYou` checks what each call writes (`callWrites` reads the files a file tool or patch changes, the absolute paths a command line writes, its pushes and its commits), and the refusal tells the hob why. A push whose words do not name its branches, such as `git push --all`, is refused while the repository has any taken branch, and one of the checked-out branch is read as that branch. A Git command that may rewrite the working tree or move a branch, such as `git reset` in any mode, `git switch`, `git clean`, `git stash` or `git branch -f`, or any subcommand not known to leave both alone, is refused while the repository (or a `--work-tree` it names) has anything taken, since which files or branches it reaches is not read from the line. So `git switch taken && git commit` is refused too. A Charm's push, such as the GitHub Charm's `github_push`, is checked by the hub action pipeline before it asks and again just before it is sent. A native call you approved is checked again once you approve it, and a path is read with its links followed before each `..`, and also as the entry it names in its folder, so deleting a link inside a taken folder is refused; paths are matched without regard to case, as on a case-insensitive volume. A relative path a command line writes is joined to the folder it is written from. A write a command hides, such as a path in a variable or a file a script writes, is not read from the call; the sandbox refuses it for a taken path (next item), and a branch moved that way is a known gap ([#1569](https://github.com/otaviobarros/hobbots/issues/1569)). A taken claim stays yours while another Task's new claim on it is contested, until you give it back or its Task ends, when it is released.
- **Taken claims in the sandbox** ([#1537](https://github.com/otaviobarros/hobbots/issues/1537)). The call-level check is the clear early refusal; the OS sandbox holds the rest for taken files. When a hob's turn starts, its access (`ToolAccess.taken`, from `makeTakenPlaces`) lists each path you took over by absolute path, as claimed and where its links land, in every worktree of the repository it was claimed in, the main one and each linked one still on disk, as Git lists them in the Git folder they share (the claim keeps that folder's real path, `claims.git_folder`), where it lies in or around the hob's folders. No folder is walked to find the repository's copies ([#1578](https://github.com/otaviobarros/hobbots/issues/1578)): with nothing taken it costs one query, and with something taken a worktree listing per repository. A read of access that needs only the folders, as accepting a message does, leaves the taken places out (`HobTools.access` with `{ taken: false }`). A separate clone of the repository, and a path claimed before Git folders were kept, are held by the call-level check alone, a known gap like branches. Claude Code's and Codex's sandboxes close all of them to writes (`SandboxScope.taken`, added to `denyWrite` as literal paths), and the fake runtime refuses a scripted command's writes there as the sandbox would. So a test script, a variable or an interpreter cannot write a taken file. A taken branch is held by the call-level check alone: Git keeps every branch of a repository in the same files, so a path sandbox can only close all of them or none, and a branch moved through a script or a config refspec is a known gap, left for [#1569](https://github.com/otaviobarros/hobbots/issues/1569). A hard link to a taken file made before the takeover is a checked limit ([permissions](permissions.md#policy-presets)). A takeover lands on turns already running too: the claims handler reviews every running turn, and one whose access now closes a path its sandbox left open, not one already closed or inside a folder already closed (`takesMore`, part of `narrows`) stops, a chat reply as interrupted and a Task's session with "Stopped because you took over files its commands could write" (a step fails with it, a member's Task waits), so what it was running cannot write there; the next turn starts with them closed. Give back and the Task's end widen access, which applies from the next turn.
- **Give back** ([#1538](https://github.com/otaviobarros/hobbots/issues/1538)). While a Task has claims you took over, its hob's ⋯ menu offers Give back next to Take over (`POST /api/tasks/:taskId/give-back`, user sessions only). `ClaimRegister.giveBack` is the one place a claim stops being taken before its Task ends: in one transaction each taken claim of the Task takes the claim machine's `GiveBack` event (yours only) and goes back to `held`, or to `contested` when another Task's open claim clashes with it now (a held claim of another Task that clashes is contested too, with `ClaimContested`), with the hob that owns the Task now as its actor and its own `ClaimGivenBack` event; the hob gets one `claims-given-back` backpack item naming what it may write again. The write check reads the register on every call, so it stops refusing at once, on every runtime. Claims belong to the Task, not to its hob, so a Reassign after Give back hands them over with the Task and the new hob may write to them. Give back on a Task with nothing taken changes nothing. Taking over a hob's live browser waits for its own decision ([#382](https://github.com/otaviobarros/hobbots/issues/382)).

## The hub's brain

One model for the hub's own judgments, chosen in Settings and onboarding, extending ADR 028's memory model. It writes briefs and summaries and judges topic drift and quest clashes in meaning, only in projectors, through `HubDecider`. Under No AI every judgment falls back to its rule ([#1367](https://github.com/otaviobarros/hobbots/issues/1367)).

- **Settings.** `MemorySettings` in `@hobbots/domain` is the brain: provider, model, effort and fallback, with a model per task. The hub's own tasks are `brief`, `chapters` and `judgments`, beside the memory tasks; a settings file saved before them reads each as `same`. `hubTaskModel` says which model a task asks for, or `none` under No AI.
- **The port.** `HubDecider` in `@hobbots/agents` takes a `Judgment`: the task, the question, the input, a `Schema` of the choices and the caller's rule. It returns a `Decided`: the choice, a confidence from 0 to 1, and who made it: the brain, the rule (no brain is chosen for the task), or the rule as a `fallback` (the brain was asked and gave no answer that decodes), so a caller such as the brief can keep what the brain wrote before. `HubDecider.rules` answers every judgment with its rule.
- **The brain.** `HubBrainDecider` in `@hobbots/memory` runs each judgment as one turn through the hub's model endpoint, on Claude Code or Codex, with no tools and no session. It reads the settings on every judgment, so a change applies to the next one. A runtime that cannot run it passes it to the `other` fallback; a reply that does not decode, or none at all, leaves the rule as a `fallback`. The endpoint counts these turns for Usage, since the memory engine never sees them.
