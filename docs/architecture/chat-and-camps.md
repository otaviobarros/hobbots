# Chat and camps

**Decided, not built** ([ADR 037](../decisions/037-chat-and-camps.md)). Until the slices in milestone v0.0.5 land, the [conversations contract](conversations.md) describes what runs. This contract is the shape the slices build: records, their states, and the rules each must keep. How state changes and events flow is in the [state and events contract](state-and-events.md).

## Threads

A thread is a chat or a camp. The UI says chat or camp and never thread; the code keeps `Thread`.

| Field | Meaning |
| --- | --- |
| `kind` | `chat` or `camp` |
| `goal` | A camp's goal; null for a chat |
| `private` | A private camp keeps nothing in memory: capture skips what was written while it was private, and any message or Attempt that had an entry then, even once it is public again, and a `memory_save` from it is refused. It still reads the memory brief |
| `origin` | The thread and chapter a camp came from, or null |
| `state` | `ThreadLifecycle`: open, archived, superseded |

- Each hob has exactly one open chat, held by a partial unique index. Built in [#1375](https://github.com/otaviobarros/hobbots/issues/1375), with the fields above and [ThreadLifecycle](machines/thread-lifecycle.md). A hob whose chat is archived has none until its next message there opens one, and a chat restored while another is open comes back as a camp.
- **Make a camp** (`POST /api/agents/:agentId/camps`) writes a camp with its title, goal and `private`, and journals `CampMade`, in one transaction. Built in [#1376](https://github.com/otaviobarros/hobbots/issues/1376).
- **Start fresh** (`POST /api/threads/:threadId/start-fresh`) moves the chat to superseded and opens a new one whose `origin` is the old chat, in one transaction that journals `ChatStartedFresh`. It moves the chat's open work: the Tasks you asked for there that are not over, with their trees and Quests, and every backpack item held for it that is not resolved, each journaled as `BackpackItemChanged`. Each Task, open question in their trees, reminder and item the chat's turns carry is recorded once as a `CarriedOver` row (the ADR's `CarriedItem`). The new chat's first turn is told what was carried over, and the dispatcher delivers what waited there once. It is refused, as an archive is, while a reply runs or waits, while an approval waits, or for a retired hob, and for a thread that is not its hob's open chat. A superseded chat is read-only for good and listed with the hob's archived threads. Built in [#1376](https://github.com/otaviobarros/hobbots/issues/1376).
- Both take a key that becomes the new thread's id: the same request sent again returns what it did, and a key that names another thread is refused (`ThreadKeyReused`). Make a camp keeps what it was asked under its key (`camp_requests`), so the request still matches after the camp is renamed.
- **Web** ([#1378](https://github.com/otaviobarros/hobbots/issues/1378)). The open hob lists its Chat, then its camps (pinned first), then Make a camp, under its name in the expanded sidebar, each with its unread dot. `#/hobs/:hobId/chat` opens the hob's open chat, or, while it has none, the empty chat whose first message opens one; every way into a hob's chat goes there, and there is no New thread. The chat's header leads with the hob's name over "Your chat with" it; a camp's leads with its title over its hob and its goal. The ⋯ menu offers Make a camp, and Start a fresh chat on the open chat; Rename and Pin are for camps. Make a camp asks for a name, a goal and Private, and says the hob's memory always comes along. Start fresh lists what comes along, read from `GET /api/threads/:threadId/carry-over`, with how many items move; the old chat's address then opens the new chat, on every device, unless a search result points into it. Each sheet is a reducer over a union of its steps (STD-REACT-029), in `apps/web/src/components/camps/`, and keeps its key across a try again, so a request whose answer was lost is not made twice.
- Migration (0095): each hob's most recent open thread becomes its chat; its others become camps with their titles. A skill trial stays a camp.
- Slice: [#1362](https://github.com/otaviobarros/hobbots/issues/1362).

## Members

Who is in a direct message or a camp ([ADR 039](../decisions/039-shared-camps.md#members)): a person or a hob, one `ThreadMember` row per thread and actor.

| Field | Meaning |
| --- | --- |
| `threadId`, `actor` | The thread and who is in it, a person (`user`) or a hob; unique together |
| `role` | `owner` for the person whose thread it is, `member` for everyone else |
| `state` | [Member](machines/member.md): active, left, removed |
| `joinedAt`, `addedBy` | When they joined and who added them |
| `readRevision` | How far they read the thread, the revision of the newest message they saw; a hob's stays null. Unread counts, the unread line and catch-up read it ([#1454](https://github.com/otaviobarros/hobbots/issues/1454)) |
| `mutedUntil` | Until when they muted the thread, or null |

- A thread stored for the first time starts with two members, in the same transaction: the person whose session made it, as `owner`, and its hob, both added by that person. Start fresh gives the new chat the old chat's members. Each is journaled as `ThreadMemberAdded` in the same transaction, after the events that make the thread.
- A direct message (a chat) keeps exactly its person and its hob: adding anyone else is refused (`MemberRefused`, `direct-message`). A camp takes more, journaled as `ThreadMemberAdded`; one who left or was removed comes back, journaled as `ThreadMemberChanged`.
- A hob that retires leaves every thread it is active in, and comes back to every thread it left when it returns, each journaled as `ThreadMemberChanged` in the same transaction as its `AgentUpserted`.
- Migration (0114): every thread gets its owner, with the thread's read marker, and its hob, already left for a retired hob. Built in [#1453](https://github.com/otaviobarros/hobbots/issues/1453).
- **Read markers are per person** ([#1454](https://github.com/otaviobarros/hobbots/issues/1454)). Whether a thread is unread is not part of the thread, which every device of every person sees alike: `GET /api/unread-threads` answers `UnreadThreads`, the threads where a hob wrote since the asking person's own `readRevision`, with `through`, the newest journal sequence the read could see. The web adds every reply that ended after `through`, and reads the list again on a person's `ThreadMemberChanged` and on a chapter that splits, merges or moves. `PUT /api/threads/:threadId/read` moves only the asking person's marker, journaled as `ThreadMemberChanged`, and answers their member row, or null when it did not move. A chapter that splits, merges or moves keeps each person who had read the thread read, and one who had not unread. Catch-up reads the asking person's marker.
- Migration `20261114004500_member_reads` moves each owner's marker forward to the thread's one last time and drops the thread's, and takes `unread` out of every journaled thread (`ThreadUpserted` 6, `CampMade` 3, `ChatStartedFresh` 3, `ChapterMoved` 2). `pnpm --filter @hobbots/server member-reads <copy>` is its dry run on a copy of a hub's data folder: it prints each thread's unread replies by the thread's marker, migrates the copy and prints them again by the owner's row, and fails when any thread differs.

### Mentions

A message's @mentions ([ADR 039](../decisions/039-shared-camps.md#who-answers)) are `Message.mentions`: the hobs and people it names, in the order first named, each once. Built in [#1455](https://github.com/otaviobarros/hobbots/issues/1455).

- `mentionsIn(text, roster, scope)` in `@hobbots/domain` is the one name matcher. A mention is `@` and a name from the roster, matched without regard to case, longest name first. An `@` inside a word, such as an email address, mentions nobody, nor does one in a range of `scope.skip`. The domain reads no Markdown: persistence's `markdownCode` finds the code with a CommonMark parser (`mdast-util-from-markdown`), so code blocks, fenced or indented, in quotes and list items, and code spans are skipped exactly as the spec defines them.
- The repository parses a message in the transaction that stores its final text: as it is sent, or when a reply ends. Text is parsed once: `messages.mentions_through` says how much was, so renaming a hob later changes nothing stored. A reply still streaming keeps what it had: none on its first turn, and after Continue, the mentions of the text it kept. When it ends again, only the text past `mentions_through` is read, and its mentions join after the others. The roster is every hob and person of the hub, not only the thread's members, so a mention of a hob outside a camp is kept for who answers to refuse.
- Mentions of you are yours alone. `ThreadMemberRepository.unreadMentions(actor)` counts, per thread the person is an active member of, the messages that mention them past their own read marker. Their own messages, notes to self and a lead's quiet progress never count.
- Migration (20261114003022): `messages.mentions` is JSON, empty for messages from before, and `messages.mentions_through` is how much of the text was parsed, in UTF-16 code units.

## The floor

Each answer a hob owes a conversation is a `TurnRequest` ([ADR 039](../decisions/039-shared-camps.md#one-hob-speaks-at-a-time)), written in the transaction that stores the message that caused it, one per hob `answerersFor` names, in that order. A conversation is a thread's main line or, once they come, one of its reply threads.

| Field | Meaning |
| --- | --- |
| `threadId`, `rootMessageId` | The conversation: null `rootMessageId` for the main line |
| `hobId` | The hob that owes the answer |
| `messageId`, `causedBy`, `cause` | The message that caused it, its author, and why (`mention`, `reply`, `relay`, `only-hob`, `lead`) |
| `relayDepth` | 0 for a person's message; a hob's mention adds one to its own turn's depth |
| `state` | [TurnRequest](machines/turn-request.md): waiting, paused, speaking, answered, passed, dropped |
| `replyId`, `droppedBy` | The reply of the turn that took it, and who stopped it |
| `queuedAt`, `position` | Floor order: the causing message's revision, then its place among that message's requests |

- `ThreadRun` is one run per conversation, in memory. When its floor is free it gives it to the oldest waiting request whose hob takes work (the message Send now picked first), or the dispatcher delivers backpack work. The request moves to `speaking` in the transaction that saves its turn's reply, together with its queued message's start, and is `answered` when the turn ends. The run publishes the hob speaking and the hobs next (`ThreadRunChanged`).
- A person's message is stored and shown at once. It is queued while a turn runs or a request waits, and starts with its first request's turn; a message several hobs owe is the prompt of each later turn.
- Stop drops the speaking request and the requests its turn caused, and keeps those a person caused. Stop all (`POST /api/threads/:threadId/stop-all`) drops every request still owed; a queued message left with nothing owed leaves the queue as said. Each dropped request records who stopped it. Removing a queued message drops what was owed for it.
- At start, a request that was speaking is answered by its interrupted reply, which Continue resumes, and the waiting requests start again in their order: the queue is the records.
- Migration (20261114003401): each queued message gets a waiting request for its thread's hob. Built in [#1461](https://github.com/otaviobarros/hobbots/issues/1461).

## Chapters

| Field | Meaning |
| --- | --- |
| `threadId`, `number`, `title` | Where it is and what it is about |
| `summary` | One line, written by the chapter summary projector when the chapter rests, and again after a split or a merge changes its messages |
| `startedAt`, `endedAt` | When it ran |
| `movedTo` | The camp it moved to, or null |
| state | `ChapterState`: live, resting, moved |

- Exactly one chapter per thread is live, its last, held by a partial unique index. Every message has a `chapterId`: a new message joins the live chapter as it is stored, and a queued one again as it starts. The database refuses a message without one. A thread stored for the first time starts its first chapter in the same transaction, journaled as `ChapterStarted`. A read thread carries its `liveChapterId`, worked out when it is read. Built in [#1379](https://github.com/otaviobarros/hobbots/issues/1379), with [ChapterState](machines/chapter-state.md).
- The hob ends a chapter with `start_chapter` on every runtime ([#1381](https://github.com/otaviobarros/hobbots/issues/1381)). You split with Split here on a message and merge with Merge with previous on a divider ([#1382](https://github.com/otaviobarros/hobbots/issues/1382)), through `GET /api/threads/:threadId/chapters`, `POST …/chapters/split` (the new chapter's id is the request's `key`) and `POST …/chapters/:chapterId/merge`. Both answer the thread's chapters afterwards; a refusal is `ChapterChangeRefused` with its reason. Clients follow the chapter events. A hub rule may suggest; it never splits.
- The commands are `ChapterService.startChapter`, `splitChapter` and `mergeChapters` in `packages/agents/src/chapters.ts`, each refused on an archived or superseded thread. Their rules are the pure `planStart`, `planSplit` and `planMerge` in `@hobbots/domain`, run in the transaction that writes the result and journals one event: `ChapterStarted`, `ChapterSplit` or `ChapterMerged`. Starting and splitting take the new chapter's id as their idempotency key; a merged chapter's id is remembered, so merging it again changes nothing.
- Start ends the live chapter, which rests, and refuses an empty title or a live chapter with no message yet. Split cuts a chapter at one of its messages, not its first: the messages from there on make a new chapter right after it, live when the one it came from was. Merge brings a chapter's messages into the chapter before it, which keeps its id and title and is live when the merged one was. Both number the chapters again from 1.
- A runtime session belongs to one chapter: `RuntimeSession` is keyed by thread, runtime and chapter, and `liveSession` gives the one a turn resumes. A turn in a new chapter, after a start, a split of the live chapter or a merge into it, starts a new session in place of the old chapter's, which is never resumed, on Claude Code, Codex and every runtime alike. A new chapter's session starts from the context pack ([#1380](https://github.com/otaviobarros/hobbots/issues/1380)), and a brain switch is briefed with the live chapter's transcript alone. A merge into the live chapter makes it live again with a new session: each session records how many chapters had been merged into its chapter when it started (`chapterMerges`), and `liveSession` resumes it only while that matches `Thread.liveChapterMerges`. So a session a turn under way records after the merge, from a read before it, is never resumed, with no lock shared between the turn and the merge. The merge also drops the sessions the chapter held. A split or merge also drops the thread's briefing checkpoint and the summaries of the chapters whose messages it changes, and gives the messages it moves the revision of its event, so a client holding an older version takes the new one; a thread you had read stays read.
- Moving a chapter into a camp re-parents it with its messages, decisions, artifacts, open questions and the quests it started, in one transaction, and leaves a stub. A running quest moves whole.
- Migration (0099): each thread gets one live chapter holding its history, started when the thread was made, with no title; every message joins it, and every session the thread keeps belongs to it and goes on being resumed.
- Slices: [#1363](https://github.com/otaviobarros/hobbots/issues/1363), [#1364](https://github.com/otaviobarros/hobbots/issues/1364).

## Records

Each is written in the same transaction and journal as the message that made it, and carries an explicit `actor`.

| Record | Key fields | States |
| --- | --- | --- |
| Decision | text (at most 500 characters), actor, threadId, chapterId, sourceMessageId, supersededBy | [DecisionState](machines/decision-state.md): active, superseded; a changed decision is kept, crossed out |
| Artifact | kind (code, page, doc, email, image, PR, file), title, latestVersion, origin | a registry over what Attempts and Quests record; copies nothing |
| Brief | threadId, text, writtenBy (the hub), source (brain or rule), basis cursor, revision | one per thread, rewritten by the brief projector at chapter ends and quest steps; no lifecycle, the rule `briefChange` says when a rewrite writes |
| CampSuggestion | threadId, chapterId, reason codes and counts | open, kept, accepted, expired; at most one per chapter |
| CarriedOver (the ADR's CarriedItem) | fromThreadId, toThreadId, ref (Task, question, reminder or backpack item), label | written once by Start fresh |
| Claim | scope (sequence, path, branch), repository, key, holder Task, actor | [Claim](machines/claim.md): held, contested, released. A number is unique in its folder of a repository for good; an open path or branch once per Task |

A note to self is a message role that never wakes the dispatcher.

### The camp sheet, notes, pins and catch-up

Built in [#1387](https://github.com/otaviobarros/hobbots/issues/1387).

- **The camp sheet.** A camp's header has This camp, which opens its sheet beside the chat (`apps/web/src/components/camp-sheet/`): Overview with "Where we are" (`GET /api/threads/:threadId/brief`), the Quests started there with their progress strips, its chapters and its settings; Decisions, newest first, where you add one, change one, which records a new decision that crosses the old one out, or cross one out, and a crossed-out one stays with what changed it; Artifacts, one row per artifact at its latest version, filtered by kind, each opening to where it is, who made it and the message it was made at; and Mine, your pins and notes to self. Every list is the hub's, read again on its event (`DecisionRecorded`, `DecisionSuperseded`, `ArtifactRegistered`, `BriefWritten`, `MessagePinned`, `MessageUnpinned`) after cancelling a read on its way (STD-REACT-012).
- **Private from now on** ([#1377](https://github.com/otaviobarros/hobbots/issues/1377)). The Overview's Private camp switch calls `PUT /api/threads/:threadId/private`, and says that what memory captured before stays. Capture stops from the next change on, as the private-camp rule reads `private` when each entry is captured; nothing captured before is removed. A chat has no such setting (`409 ThreadNotCamp`).
- **Notes to self.** `POST /api/threads/:threadId/notes` writes a message with the `note` role, by you, under the client's `key`, which becomes its id: the same note sent again returns it, and a key that names anything else is refused (`409 MessageKeyReused`). It is written under the hob's lock, so it takes its place in the thread's order, and it wakes no hob. No hob reads one: every transcript a turn, a pack, a continuation, memory capture, the chapter and brief projectors or `read_message` reads leaves notes out (`hobReads`), and notes count toward no camp suggestion. The composer's Note to self writes one; the transcript shows it in a dashed box, under "Note to self · only you".
- **Pins.** `PUT /api/threads/:threadId/messages/:messageId/pinned` pins or unpins a message of the thread, kept in `message_pins` (migration 0107) apart from the message, so pinning leaves the message's revision and the thread's unread state as they are; a pin follows its message into a camp, and goes with it. `GET /api/threads/:threadId/pins` lists them, the newest first. A message's ⋯ menu has Pin and Unpin, with Split here where it can start a chapter.
- **Catch-up.** `GET /api/threads/:threadId/catch-up` is worked out by the pure `catchUpOf` from your own read marker, your member row's `readRevision`, and the thread's records: the replies that landed since, routine progress left out, the first of them, when you last read, and up to `CATCH_UP_MAX` (6) changes, what waits on you first, then the newest, with how many more there were. Your own decisions, uploads and notes are left out. The chat reads it at each visit to an unread chat, opening it or bringing its window to the front, before it marks the thread read, and shows "New since you left" before the first unread reply with "While you were away" until you fold it. Each visit reads its own catch-up, even after the chat view mounts again. A catch-up that cannot be read keeps the thread unread and offers Try again, or Skip, which marks it read.
- **The suggestion card.** A chat's open camp suggestions show as a card after its transcript, with why in chips. Make it a camp opens Make a camp with the chapter coming along, a switch you can turn off, which moves the chapter into the new camp; Keep it in my chat keeps it and says it won't come back. A chat chapter's ⋯ menu has Make a camp from this chapter.

### Decisions and artifacts

Built in [#1383](https://github.com/otaviobarros/hobbots/issues/1383): `Decision` and its [DecisionState](machines/decision-state.md) machine in `packages/domain/src/decision.ts`, `Artifact` and the registry's rules in `artifact.ts`, the store in `packages/persistence/src/records.ts` and `artifact-rows.ts` (migration 0101), and `Records` and `record_decision` in `packages/agents/src/records.ts`.

- **`record_decision`** is a hub tool on every runtime that serves hub tools, Claude Code, Codex and the fake one alike, offered to a turn that writes a reply in a chat or camp. It takes the decision's `text`, a `key` and, for a decision that changes an earlier one, `replaces` with its id. The decision is recorded by the hob, from the reply, in the reply's chapter, redacted as everything the journal holds is. A text over 500 characters, an empty one, or a closed chat or camp is refused, and nothing is written. The same key with the same input returns the first decision; with another input it is refused.
- **Replace and cross out.** A decision is never edited. A new one that replaces an earlier one crosses the old one out in the same transaction, which points at the new one. You can record a decision in the app, replacing one or not, and cross one out with nothing in its place. The routes are `GET` and `POST /api/threads/:threadId/decisions` and `POST /api/threads/:threadId/decisions/:decisionId/cross-out`. A crossed-out decision is kept and listed, and never comes back.
- **Artifacts.** The registry is filled in the transaction that journals what it indexes, by a pure rule as backpack items are: a Task's results as it completes (a file by its path, a link by its URL, a text by its id), an Attempt's settled changes that left a file, and the files a finished reply's tool steps wrote. Each artifact is one row in its chat or camp, by where it is, at its latest version: every record that made or changed it counts once, and the same record again changes nothing. Its kind comes from its name or URL: code, page, doc, email, image, a pull request, or another file. `GET /api/threads/:threadId/artifacts` lists them, the most recently changed first.
- **Reviews.** Built in [#1422](https://github.com/otaviobarros/hobbots/issues/1422): each artifact's review, held by its [ArtifactReview](machines/artifact-review.md) machine, waits for you until you review or dismiss it, once, with when and by whom (migration 0105, which gave every stored artifact a waiting review). `POST /api/threads/:threadId/artifacts/:artifactId/review` with `{ outcome: "reviewed" | "dismissed" }` settles it; the same review again answers it unchanged, and one settled the other way is refused (`409 ArtifactReviewChangeRefused`). A new version keeps its review. When a moved chapter's artifact joins the camp's at the same place, a review settled on the moved one is carried over to one still waiting, journaled as `ArtifactReviewSettled` with the move; one the camp already settled keeps its own, since a settled review is final. The move recounts the Quests whose Tasks made the artifacts it moved. The GitHub Charm asks GitHub every five minutes, with the sign-in of the hob that made it, how each pull request still waiting stands, and reviews one GitHub reports merged or closed, by `{ kind: "hub", id: "github" }`; asking GitHub happens before the command, never inside it. The camp sheet's Artifacts tab tags each artifact waiting for you To review; opening one says where its review stands, and who settled it and when, with Mark reviewed and Dismiss while it waits. `ArtifactReviewSettled` reads the camp's artifacts again.
- **Versions and the viewer.** Built in [#1434](https://github.com/otaviobarros/hobbots/issues/1434): every file is kept at one canonical place. A Task's result given by a relative path is resolved against its Attempt's folder (where it changed a file at that path, else the first folder it scanned), and `complete_task` stores the placed absolute path. Before this, a member that returned `social.md` and also wrote it made two rows; migration 0108 moves each stored file to its one place and merges two rows of one camp there, as a moved chapter's artifact joins the camp's (the newer fields, a name a record gave, a settled review carried over), and fixes the find index and each Quest's ready-for-review count. Each record that saw an artifact says which version it made, which Attempt's work it is and when the hub saw it, and the records of one Attempt are one version. `GET /api/threads/:threadId/artifacts/:artifactId/versions` lists them newest first, how the artifact is shown (document, diff, page, image, link or none) and where each version's contents are: kept by the Attempt, read now (the latest version of a file), or not kept. `GET …/versions/:version` serves one version's bytes, read only: what the hub kept, or the file as it is now, only inside the folders of the hob whose camp it is in, never through a link out of them nor a file named as a secret's, text redacted as a turn's tool output is and cut to the preview size (`404 ArtifactContentUnavailable` with the reason). The camp sheet's Artifacts tab previews each row (its first lines, an image's thumbnail), shows only the kind filters the camp has, and opens an artifact drawn by its kind, in the sheet or a full viewer: a document rendered with its source a click away, code as a diff against the version before, a page in a frame without scripts or network, an image, a link as a card, with its older versions to pick from.
- **Events.** `DecisionRecorded`, `DecisionSuperseded`, `ArtifactRegistered` and `ArtifactReviewSettled`, version 1, each with the whole record. An `ArtifactRegistered` journaled before reviews reads as waiting.
- **Authors.** Every message names its author: you (`{ kind: "user", id: "owner" }`, the hub's one person until shared camps) or the thread's hob, set as the hub stores it. Migration 0101 gave every stored message and every journaled `MessageUpserted` and `MessageQueued` one, and the database refuses a message without one. Decisions, artifacts and claims carry theirs.
- **The pack.** `RecordPackSource` gives the context pack `Records.activeDecisions` and `Records.artifactsOf`, so a new chapter's first session starts from the decisions that hold, newest first, and the artifacts index, and never from a crossed-out decision ([#1380](https://github.com/otaviobarros/hobbots/issues/1380)).
- **Chapters.** A split moves the decisions and artifacts of the replies it moves to the new chapter, and a merge moves all of the absorbed chapter's into the one it joins, in the transaction that moves their messages.
- **Find.** `GET /api/find?q=&in=&kind=` finds decisions, artifacts and chapters by every word typed, from the find projector's index, beside the settled messages that say them, in one chat or camp or, with no `in`, everywhere but private camps. Each row is checked against where its record is now, so a record moved since it was indexed, such as into a private camp, is left out until the projector catches up, and a decision's state is read live. A crossed-out decision is found and marked. `POST /api/find/ask` answers a question from the records that match it on the hub's brain, citing each by the message it came from; under No AI, or when the brain gives no usable answer in time, it returns the matches with the reason, and the Find box lists them in the answer card. Ask matches any word of the question, so it can find records that Find, which needs every word, does not. Both emit no events ([#1386](https://github.com/otaviobarros/hobbots/issues/1386)).

### Camp suggestions and moving a chapter

Built in [#1385](https://github.com/otaviobarros/hobbots/issues/1385): `CampSuggestion` and its [CampSuggestionState](machines/camp-suggestion-state.md) machine in `packages/domain/src/camp-suggestion.ts`, the pure move in `chapter-move.ts`, the store in `packages/persistence/src/chapter-moves.ts`, `camp-suggestion-rows.ts` and `camp-suggestions.ts` (migration 0104), and `CampSuggestionService` and the `CampDrift` projector in `packages/agents/src/camp-suggestions.ts`.

- **Moving a chapter.** `POST /api/threads/:threadId/chapters/:chapterId/move` moves a chapter into an open camp of the same hob (`{ _tag: "camp", campId }`) or a new one (`{ _tag: "new", key, title, goal, private }`), in one transaction: its messages, the decisions and artifacts recorded in it, its open questions, approvals and tool records, and the quests started in it with their open backpack items, and the approvals, web use and hob proposals their Tasks' turns made outside any reply. A running quest moves whole, and its `QuestSummary` names the camp from the move's transaction on. The chat keeps the chapter as a stub, `moved` with the camp it went to, and the chapter becomes the camp's live one: a new camp's empty first chapter takes it, and otherwise the camp's live chapter rests and the moved one follows it. Moving the chat's live chapter starts a new one there. Every session of both threads is dropped, since the records they started from moved, so both next turns start a new session from their pack, whichever chapter moved. A moved step's full tool log stays readable from the camp: the step names the thread its log was kept under (`loggedIn`). A client moves the messages it already holds to the camp's chapter at the move's revision, cancels any transcript read already on its way, and reads both transcripts and chapter lists again. A move while either thread has a reply under way or an approval its reply waits on is refused (a party member's approval waits in its own Task's session, so it moves with its quest instead) (`409 ChapterMoveRefused` with `reply-running`), as are a closed thread, a target that is not an open camp of the hob, a moved chapter and an empty one. The same move again answers with the first one. It is journaled as `ChapterMoved` (version 1: both threads, the stub, the chapter as it landed and each thread's chapters afterwards).
- **Which quests.** A top Task started in a chat or camp records the chapter it was started in (`tasks.chapter_id`, migration 0104), kept up to date by splits, merges, Start fresh and moves.
- **Suggestions.** A pure rule in the transaction that journals a chat's records raises a suggestion for its live or resting chapter once it reaches any named threshold: `CAMP_SUGGESTION_DECISIONS` (5), `CAMP_SUGGESTION_ARTIFACTS` (4), `CAMP_SUGGESTION_QUESTS` (2) or `CAMP_SUGGESTION_MESSAGES` (80 settled messages). Its reasons are codes and counts. A chapter gets one suggestion at most, held by a unique index, so a suggestion you kept in the chat never comes back. The drift projector can raise one too (see [state and events](state-and-events.md)). Moving the chapter accepts its suggestion; merging the chapter away, closing the chat or Start fresh expires it. `GET /api/threads/:threadId/camp-suggestions` lists the open ones, and `POST /api/threads/:threadId/camp-suggestions/:suggestionId/keep` keeps one in the chat (`409 CampSuggestionChangeRefused` for one settled otherwise or not there). They are journaled as `CampSuggested`, `CampSuggestionKept`, `CampSuggestionAccepted` and `CampSuggestionExpired` (version 1), each with the whole suggestion.
- **Not built yet.** The chat's chapter list keeps the moved chapter's stub, but its transcript leaves a moved chapter out, so the stub does not show there yet. The suggestion card and Make a camp from a chapter are built ([#1387](https://github.com/otaviobarros/hobbots/issues/1387)), above.

## The context pack

Built in [#1380](https://github.com/otaviobarros/hobbots/issues/1380). `buildPack(records, budget)` in `packages/agents/src/context-pack.ts` is pure and deterministic. It makes a new runtime session's starting context, on every runtime, from:

1. the memory brief (its own budget, ADR 028), sent beside the pack as before and counted against its budget,
2. the camp brief, as the brief projector last wrote it ([#1384](https://github.com/otaviobarros/hobbots/issues/1384)),
3. active decisions,
4. the thread's open work: its open Tasks with their last step, the questions in them still waiting for an answer, and the backpack items its turns carry, as Start fresh would carry them,
5. what Start fresh carried, until the hob first replies in the new chat,
6. the artifacts index,
7. one line per resting chapter,
8. the live chapter's turns before the prompt.

Each part has a share of the budget (`PACK_BUDGET`: 12,000 tokens, counted as four characters a token), and the shares add up to it. The pack never goes over its budget, even when the briefs and the active decisions alone would.

- **Which session.** A turn with no session to resume in its live chapter starts from the pack: a new chapter's first turn, a turn after a split or merge of the live chapter, and a brain switch, whose pack replays the live chapter. A resumed session hears only what other brains wrote in the live chapter since it last replied (ADR 017).
- **Over budget**, the parts with a fixed share are cut at it: the briefs at their share, and the parts that never drop silently fitted to theirs. What the others leave goes first to the live chapter, then the artifacts, then the resting chapter lines, so they trim in ADR 037's order: resting chapter lines, the oldest artifacts, the live chapter's oldest turns. Each trim leaves one line saying what was left out.
- **Active decisions and open work never drop silently.** Decisions: the newest in full while every older one still fits by title, newest first; past that, the newest titles and a count. Open work: what does not fit is counted.
- **A last turn too large for its share** is carried as its start and end with `[… N characters left out. Read the rest with read_message, message_id <id>.]` ([#1381](https://github.com/otaviobarros/hobbots/issues/1381)).
- **Resting chapters.** Each is one line with the summary the projector wrote. Until it has, the pack writes the plain one in its place (how many messages, and the first of yours), so a new chapter's first turn never runs without the last chapter's summary.
- **The summary projector.** `ChapterSummaries` reads the journal after its cursor in `projector_cursors`, and gives each chapter that came to rest its one-line summary (at most 280 characters), asked of the hub's brain with the plain summary as its rule, so under No AI it is the plain one. It writes each through `ChapterStateMachine`'s `Summarize`, journaled as `ChapterSummarized`, with the cursor, in one transaction.
- **The brief projector.** `CampBriefs` reads the journal after its own cursor in `projector_cursors` and writes the brief of each chat or camp where a chapter ended, a split or merge changed the chapters, or a Quest took a step (it started or ended, a Task in the thread ended, completed, failed or cancelled, a step or a member's Task with no Quest of its own included, or a milestone was reached). It asks the hub's brain (task `brief`) with the thread's goal, decisions, artifacts, open work, chapter summaries and the live chapter's last messages; its rule is the plain brief: the goal, the decisions that hold and what the thread made, newest first, with a count of what does not fit. Under No AI the plain brief is written and no model is called. The projector cuts every brief at its share of the pack (`CAMP_BRIEF_MAX`, 2,000 characters less the heading), so the pack carries it whole. It writes each through the rule `briefChange`, journaled as `BriefWritten`, with the cursor, in one transaction: a brief from no further along the journal than the stored one, or one that says the same, writes nothing. When the brain was asked and gave no answer that decodes (`HubDecider` answers `fallback`), or none within two minutes, a brief the brain wrote stays in place; one the rule wrote, or none yet, takes the plain one. When nothing the plain brief would say holds any more, such as after the last decision it named was crossed out, the brief is cleared to empty text and the pack carries none. A turn only reads the brief that is there, so a slow brain never holds it up. `GET /api/threads/:threadId/brief` reads it for the camp sheet ([#1387](https://github.com/otaviobarros/hobbots/issues/1387)).
- **Private camps.** A camp's pack reads only its own chapters and its own brief, so a private camp's summaries and brief reach no other camp's pack, and memory capture takes nothing from `ChapterSummarized` or `BriefWritten`.
- **`PackReport`** records each part, its share and size in tokens, and what it trimmed. Each pack a turn reads is logged with it, and `PackReports` keeps the last one per thread for the Focus chip. `GET /api/dev/threads/:threadId/pack`, served only by a hub run from a checkout, shows it with the pack the next new session would read.
- **The Focus chip** ([#1382](https://github.com/otaviobarros/hobbots/issues/1382)) reads `GET /api/threads/:threadId/focus`: the report `PackReports` kept of the thread's last new session (`last-turn`), or, when it kept none, as after a restart, the report of the pack the next new session would read (`next-session`). The client groups the parts into rows and shows the sizes as the report has them; it never measures anything itself.
- Slice: [#1363](https://github.com/otaviobarros/hobbots/issues/1363).

## Quests in camps

- A quest belongs to the thread that started it (`Quest.threadId`, `Task.threadId`). Its updates and questions land there: each backpack item for its lead is carried by the thread of the quest's top Task, so its lead's next turn about it runs in that chat or camp ([#1389](https://github.com/otaviobarros/hobbots/issues/1389)). A quest started outside any chat has no thread, and is routed as before.
- A quest moves with the chapter that started it, in the move's transaction, and a running one moves whole: its Tasks, its Quests, its open backpack items, and what its Tasks' turns made outside any reply (a member's approvals, web use and hob proposals). A crash midway leaves it where it was. Its next update, question or result then lands in the camp. A member's session that started before the move still asks in the right place: a request asked outside any reply is written in the thread its Task is in at that moment, and a decision saved after a move names the thread the request is in now, both read in their own transaction. Start fresh moves a chat's open quests the same way.
- A quest opens as a thread in its camp's sheet. ADR 027's records stand; its lanes layout is retired. Built in [#1390](https://github.com/otaviobarros/hobbots/issues/1390), in `apps/web/src/components/quest-sheet/`:
  - **The quest pill.** A camp's header counts its own quests under way from their `QuestSummary`: "2 quests · 1 ready for review · 1 needs you". It opens the camp's sheet, whose Overview lists the quests; a row opens its quest in the same sheet, with Back to the camp. A chat's quest opens in a sheet of its own from its ticket or header button, with no Back. The quest in the sheet is in the address (`?quest=`), so a link opens it.
  - **The quest's pane.** Its title, how far it is, each hob's work (its Tasks, your notes passed on and its cards), then the quest's thread: your request and the lead's plan, what you sent while it ran with its steer receipt, the lead's replies while it ran (a quiet one stays out), notes the lead passed on, and each member Task's result or failure, oldest first. Its composer writes to the lead in the quest's chat or camp, so a message sent while the work runs gets a receipt as in the chat. The chat's and camp's unread dot is the unread marker; the quest adds none of its own.
  - **The Workbench.** Show the work, or a hob's work, opens the quest's Workbench beside the chat (`?quest=&tab=`), with Back to the quest and Close; the chat folds away beside it as before.
- `QuestSummary` on the hub feeds the quest pill, the sidebar and Home. Built in [#1373](https://github.com/otaviobarros/hobbots/issues/1373): `QuestSummary` and its fold `questSummaryOf` in `packages/domain/src/quest-summary.ts`, the rows in `packages/persistence/src/quest-summary-rows.ts` (migration 0104).
  - **What it says.** Its Quest's lead, thread, parent Quest and state; how many Tasks under the Quest's own Task take each tone (`needs`, `working`, `waiting`, `done`, `problem`, `idle`, as `workTone` maps a Task's state); how many things need you while it runs (each question that climbed every lead and each pending approval on its Tasks, its own included, and each Task under it that failed, as the quest ticket counts them); and how many things are ready for review: the registered artifacts of a kind you review (`pr`, `doc`, `page`, `code`) that its completed Tasks, its own included, made, by a result they returned or their Attempts' file changes, and that still wait for your review, each once.
  - **When it changes.** A pure fold over the Task tree, run in the transaction of every change whose events touch the tree: a Task created or moved, a Quest started or ended, a question asked, escalated, answered or withdrawn, an approval requested or decided, an artifact a Task made registered or its review settled, a chat started fresh, which moves its Quests' thread, and a chapter moved into a camp, which moves the Quests started in it. Each summary that says something new is written with its `QuestSummaryChanged`, after the change's own events and what they call for; one that says the same is neither written nor journaled. No projector is involved, so a client never sees a Task's change without its Quest's summary.
  - **The snapshot.** `GET /api/quest-summaries` lists every active Quest's summary, and `?threadId=` every Quest followed in that chat or camp, ended ones included, with the stream cursor. The web client renders it ([#1374](https://github.com/otaviobarros/hobbots/issues/1374)): the quest pill, the quest's pane, the ticket, the finished banner, a hob's page and Home read their counts from it, the pill shows what is ready for review, and a `QuestSummaryChanged` replaces a Quest's summary when its revision is newer.
- Slice: [#1365](https://github.com/otaviobarros/hobbots/issues/1365).

## The claims register

Built in [#1388](https://github.com/otaviobarros/hobbots/issues/1388): `Claim` and its machine in `packages/domain/src/claim.ts`, the register in `packages/persistence/src/claims.ts` (migration 0098), and `claim` with the Task tools on every runtime.

- **`claim`** is a Task tool. It records a claim for the Task the hob works on, and in a chat with no Task yet it starts one, as `plan_steps` does. A claim names a folder of the hob's, inside a Git repository. The repository is known by its `origin` remote, so two clones or worktrees share their claims. The named folder is resolved, links and `..` taken as the kernel walks them, before it is checked against the hob's folders, and a hob given part of a repository claims paths and numbered folders only inside that part.
- **Sequences.** A `sequence` claim is the next number in a folder whose files start with one: migrations, ADRs, or any other numbered files. The hob names the folder whose files the numbers count, such as `docs/decisions`. The hub reads that folder on the repository's default branch as the clone has it (`origin`'s HEAD, else `origin/main`, else `main`), without running Git, and hands out one past every number `main` and the register hold. A number the hob already uses is kept when it is free; otherwise the hub settles on the next free one and says so. Concurrent claims take the journal's head in turn, so each gets its own number.
- **A released number is never handed out again** (decided in #1388). Reusing it would keep numbers dense, but a number seen in a closed branch would then mean two things. A number is unique in its folder of a repository for good, released or not.
- **Paths and branches.** A pure rule in the claim's transaction finds clashes with every other Task's open claim in the same repository: the same branch, or a path that is the other or inside it, comparing whole names. The new claim and each held claim it clashes with become contested. Each lead involved gets a `claim-clash` backpack item: the nearest lead still at work above the Task, or its owner when nobody leads it. Neither Task is stopped. A claim of the same path or branch by the same Task again changes nothing. It calls no model.
- **Release.** A Task's claims are released in the transaction that ends it, completed, failed or cancelled, at any depth; a contested claim that clashes with nothing left goes back to held. A retry that reopens a failed Task does not bring its claims back, and the retried Task may claim the same paths and branches again.
- **The Heads-up.** A chat or camp shows a Heads-up for each group of open claims that clash, when a Task of its own holds one of them: who holds each side, on which path or branch, a note when a side's work is in another chat or camp, and who claimed last, as "Spotted by the hub". It sits in the transcript where the last of those claims was made, and goes once the clash is gone. `GET /api/threads/:threadId/clashes` reads them from the register (`ClaimRegister.clashesIn`, the groups `clashGroups` finds); the client reads them again on each Claim event. It calls no model ([#1390](https://github.com/otaviobarros/hobbots/issues/1390)).
- **Next.** Claims beyond the repository: spaces from connectors, four clash shapes, read or write, how hard a clash bites, and claims the hub makes on its own ([#1413](https://github.com/otaviobarros/hobbots/issues/1413), ADR 037 amendment).
- Slice: [#1365](https://github.com/otaviobarros/hobbots/issues/1365).

## The hub's brain

One model for the hub's own judgments, chosen in Settings and onboarding, extending ADR 028's memory model. It writes briefs and summaries and judges topic drift and quest clashes in meaning, only in projectors, through `HubDecider`. Under No AI every judgment falls back to its rule ([#1367](https://github.com/otaviobarros/hobbots/issues/1367)).

- **Settings.** `MemorySettings` in `@hobbots/domain` is the brain: provider, model, effort and fallback, with a model per task. The hub's own tasks are `brief`, `chapters` and `judgments`, beside the memory tasks; a settings file saved before them reads each as `same`. `hubTaskModel` says which model a task asks for, or `none` under No AI.
- **The port.** `HubDecider` in `@hobbots/agents` takes a `Judgment`: the task, the question, the input, a `Schema` of the choices and the caller's rule. It returns a `Decided`: the choice, a confidence from 0 to 1, and who made it: the brain, the rule (no brain is chosen for the task), or the rule as a `fallback` (the brain was asked and gave no answer that decodes), so a caller such as the brief can keep what the brain wrote before. `HubDecider.rules` answers every judgment with its rule.
- **The brain.** `HubBrainDecider` in `@hobbots/memory` runs each judgment as one turn through the hub's model endpoint, on Claude Code or Codex, with no tools and no session. It reads the settings on every judgment, so a change applies to the next one. A runtime that cannot run it passes it to the `other` fallback; a reply that does not decode, or none at all, leaves the rule as a `fallback`. The endpoint counts these turns for Usage, since the memory engine never sees them.
