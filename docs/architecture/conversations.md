# Conversations, threads and runtime sessions

**Decided.** Threads are durable discussion contexts; executions are runtime work. Each agent has multiple threads. Selecting a different thread, collapsing a panel or disconnecting the UI does not cancel tasks.

A thread stores title, owning agent, timestamps, messages, links to Quests and tool activity, and session bindings. Persist user input before dispatch and correlate streamed deltas with stable message/turn IDs. A partial response remains distinguishable from a completed response or interrupted turn.

The UI restores an agent's last selected thread and keeps relevant side-panel state. A pinned Quest may remain visible while the user discusses another topic. The server owns durable work regardless of client focus. Search titles and persisted messages with links to the correct thread.

## Session mapping

Adapters create or resume sessions using supported vendor mechanisms. Record runtime/executor/session binding and capability evidence. A resumed native session and a reconstructed context are different recovery modes; show that distinction. Never claim exact resumption when only message replay is available.

Within a session, serialize prompts if required by that runtime. Across independent supported sessions, schedule concurrent work within policy and capacity. New inbox results received while an agent is busy are persisted and coalesced for a safe continuation; do not inject concurrent prompts into a session that cannot accept them.

## Message categories

User conversation messages, assistant text, tool events, structured task results and inter-agent messages share correlation links but retain different semantics. A chat transcript is not the responsibility ledger. Questions have explicit reply obligations; progress updates normally update visibility without demanding a model turn.

## Interrupt and reconnect

Stopping a turn requests adapter interruption and records acknowledgement/outcome. It does not delete history or silently cancel every delegated child. The user must be able to distinguish stopping the current turn from canceling a task or Quest.

A reply records the stop in two steps. Stop moves a streaming reply to `stopping` and emits `TurnStopRequested`; the reply still counts as in progress, keeps any text the runtime sends, and may still complete if the turn finishes first. Once the adapter confirms the turn has ended (for Claude Code, once its process has exited, killed if it outlives a grace period), the reply becomes `stopped` with its partial text and `TurnStopped` follows. Repeated stop requests, or a stop with no turn running, change nothing. A turn Hobbots ends itself (a restart, pause or retirement) is `interrupted`, not `stopped`; on restart a reply left `stopping` becomes `stopped` and one left `streaming` becomes `interrupted`. Each event follows the reply's `MessageUpserted`.

A reply the runtime cuts off after it started writing is also `interrupted`, with `error` saying why; one cut off before any text is `failed`. A reply the provider's usage limit ends is `limited`, with `resetsAt` when the provider says the allowance refills. Continue (`POST /api/threads/:threadId/messages/:messageId/continue`) resumes an `interrupted` or `limited` reply in the same message: only the thread's latest reply, only while its hob is active and nothing else runs in the thread. The reply streams again on the thread's current brain, and the runtime is asked to continue from the end of the text it kept. A limited or cut-off reply can also continue on another brain: the thread switches first, then the reply continues in place with a briefing. Waiting for the refill is not built yet.

A thread keeps one runtime session per runtime, each with the last message it has seen, and may name its own brain (runtime, model, effort) instead of the hob's ([ADR 017](../decisions/017-switching-brains.md)). `PUT /api/threads/:threadId/brain` sets or clears it, and with `makeDefault` saves it as the hob's next configuration version instead. Switching never moves a session: a runtime new to the thread starts a fresh one, and one used before resumes its own. When a session missed replies from another brain, its turn carries a briefing the hub builds from the stored transcript, without asking any model. A chat turn also carries the hob's memory brief in the same briefing ([ADR 028](../decisions/028-memory.md)): everyone's rules, then the hob's own pages, then its projects', pinned first within each, quoted as reference data within about 8,000 characters, the lowest-priority pages dropped first. A session gets it when it starts and again only when it changed, since the thread keeps a fingerprint of the brief each session last received, counted only once the runtime answered the prompt that carried it. When memory does not answer, the section says so and the turn goes on. A Task step's or party member's session gets the same brief by the same rule. Its sessions live on Attempts, so the hub keeps what each received by session while it runs, and after a restart each is told the brief once more. Each reply records the runtime and model that produced it.

## Archiving

A thread the user is done with can be archived (CH-009). `POST /api/threads/:threadId/archive` sets its `archivedAt`; `POST /api/threads/:threadId/restore` clears it. Repeating either returns the thread unchanged, and neither changes `updatedAt`, so a restored thread goes back to its place. Archiving is refused with `ThreadArchiveRefused` while a reply runs or a message waits in the thread's queue (`reply-running`), while an approval waits (`approval-pending`, which wins when both apply), or when the hob is retired (`hob-retired`, which also refuses a restore). The check runs under the hob's lock, so no message or turn slips in while the thread is archived. An archived thread is read-only: a new message, Continue or brain switch fails with `ThreadArchived`. `GET /api/agents/:agentId/threads` leaves archived threads out; `?archived=true` lists only them, most recently archived first. Each thread it lists, like one read on its own and the one `ThreadUpserted` carries, has a `lastLine`: the last message the transcript shows, as one line of at most 140 characters, or null. Queued messages and ones with no text, such as a reply made only of tool calls, are skipped. It is the transcript's own text, worked out on read and never stored. Clients update it from each `MessageUpserted`. Search still finds them, with `thread.archivedAt` set. Retiring a hob leaves its archived threads as they are.

A thread can be renamed and pinned to the top of its hob's chats. `PUT /api/threads/:threadId/title` takes a `title` that is trimmed, not empty and at most 60 characters. `PUT /api/threads/:threadId/pinned` takes `pinned`, which sets or clears the thread's `pinnedAt`. Repeating either returns the thread unchanged, and neither changes `updatedAt`, so the thread keeps its place by last activity. Both run under the hob's lock and fail with `ThreadArchived` for an archived thread. `pinnedAt` travels in `ThreadUpserted`; older entries decode as not pinned.

The hub keeps how far you have read each thread ([ADR 027](../decisions/027-quest-room.md)), as the newest message revision you have seen in it, so a thread's unread state agrees on every device. Each thread a read returns, like the one `ThreadUpserted` carries, has `unread`: the hob wrote since then, in a reply that ended with text or failed. A reply continued in place after you read it, as Continue does, takes a new revision and so is unread again once it ends. A reply still under way waits until it ends, and your own messages never count. Like `lastLine`, it is worked out on read, and clients set it from each `MessageUpserted` of a reply that just ended. `PUT /api/threads/:threadId/read` takes the `messageId` you read through and the `revision` you saw, and the marker takes the newest revision of the messages up to it, no later than that. The marker only moves forward: a message you had read past, or one from another thread, returns the thread unchanged and journals nothing. A move journals `ThreadUpserted` with the thread's new revision and leaves `updatedAt` as it was. It needs no hob lock, and an archived thread takes it too. A thread from before the marker counts as read through its last message (migration 0053). The open chat marks itself read through its last message that is not under way, with the newest message revision it showed up to there, while it is in view on a page in front; a chat folded away beside the Quest room reads nothing. The marker never passes the revision the client sent, so a late read from a device that saw a reply before it was continued leaves the rest unread.

Reconnect from an authorized snapshot plus durable event cursor ([ADR 013](../decisions/013-event-journal.md)). Deduplicate messages/deltas, recover missed events, and display stale/unverified activity honestly. Cursor expiry or compaction requires a fresh snapshot, not silent data omission.

Thread fork/context-snapshot behavior, message retention limits, and exact search indexing remain open.
