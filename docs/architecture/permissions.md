# Permissions and autonomy

**Decided:** autonomy-first Trusted Workspace default, enforced boundaries, exceptional approvals, narrowing delegation, separate computer permission and human approval authority. The preset mapping, folders, sandbox and Charms are decided in [ADR 014](../decisions/014-tool-policy-and-enforcement.md), and the GitHub Charm in [ADR 020](../decisions/020-github-charm.md), with a hob's own GitHub App in [ADR 022](../decisions/022-hob-github-app.md). Approval lifetimes and standing grants are decided in [ADR 015](../decisions/015-approval-lifetimes-and-grants.md), and where the user session comes from once devices exist in [ADR 021](../decisions/021-devices-and-remote-access.md).

Autonomy is how often an agent proceeds without interruption. Authority is which resources/actions it may use. High autonomy inside a narrow workspace is the default objective. Repeated confirmation for routine authorized edits/tests would violate the product direction.

## Policy presets

Trusted Workspace is the default. The [design](../decisions/008-design.md) names the onboarding presets **Careful**, **Balanced** (Trusted Workspace, the default) and **Trusting**. [ADR 014](../decisions/014-tool-policy-and-enforcement.md) maps them onto the MVP operations; it owns the table and the onboarding wording.

| Operation | Careful | Balanced (Trusted Workspace) | Trusting |
|---|---|---|---|
| Read files | Allow | Allow | Allow |
| Create and edit files | Ask | Allow | Allow |
| Delete files (checked) | Ask | Ask | Allow |
| Run commands | Ask | Allow | Allow |
| Local Git | Ask | Allow | Allow |
| Push (a Charm) | Ask | Ask | Allow |
| Push with force, or to the default branch | Ask, once only | Ask, once only | Ask, once only |
| Use the web | Ask, per host | Allow | Allow |
| Search the web (the runtime's own search) | Allow | Allow | Allow |
| Read GitHub (a Charm) | Allow | Allow | Allow |
| Open pull requests (a Charm) | Ask | Ask | Allow |
| Comment on GitHub (a Charm) | Ask | Ask | Allow |
| Open issues (a Charm) | Ask | Ask | Allow |
| Search memory | Allow | Allow | Allow |
| Save to memory (the hob's own memory) | Allow | Allow | Allow |
| Search skills | Allow | Allow | Allow |
| Ask for a skill in the library | Ask | Ask | Allow |
| Propose a skill (always waits for you) | Allow | Allow | Allow |
| Note a problem with a skill | Allow | Allow | Allow |
| Read other hobs | Allow | Allow | Allow |
| Anything outside the hob's folders | Deny | Deny | Deny |

The skill rows are Hobbots' own tools ([ADR 029](../decisions/029-skills.md)): a proposal is let through to your Inbox under every preset, but nothing it holds reaches the library until you add it. Read other hobs is the hob directory ([ADR 032](../decisions/032-hob-directory.md)): the roster each turn carries and `read_hob`. Under an override of Ask the roster is left out and `read_hob` asks once each time; under Never neither is offered.

Careful keeps investigation automatic and asks before modifications and consequential work. Trusting is deliberately broad inside the hob's folders and the sandbox, with clear disclosure of actual runtime privileges; it never grants self-approval or Hobbots administration. Per-hob overrides only narrow the table; a widening needs a separately recorded user grant. The UI says **Never** for Deny.

A rule is **enforced** when a runtime or OS boundary holds it whatever the hob does, and **checked** when Hobbots recognizes and decides the operation but a permitted command could perform it another way. Delete files is checked, and so is a push to a remote that accepts pushes without credentials when commands and the web are both allowed; pushes needing credentials are enforced. Local Git is checked where its answer is narrower than Run commands, since any permitted command can run Git another way. The Permissions tab says so. Commands are recognized through assignments and wrappers such as `env` and `timeout`, and in the folder a `cd` earlier in the line moved to; [ADR 014](../decisions/014-tool-policy-and-enforcement.md) has the details.

## Folders

The folders approved in setup are shared by every hob, and each hob can have its own folders on top, added only by the user. Paths are compared canonically: absolute, with `..` and symlinks resolved, a not-yet-existing path through its nearest existing parent, following the volume's case sensitivity. A symlink inside a folder that points outside it is outside. `.git/hooks` and `.git/config` inside a folder are read-only for hobs, and the Hobbots data folder is never reachable from the sandbox.

A hob's own folders, the shared folders it hides and its per-operation overrides are part of its configuration, so changing them creates the next configuration version and a running turn keeps the version it started with. A change that narrows its tools, here or in setup, stops the running turn instead, so no turn keeps authority the user took away. Folders are stored canonical, and so is a hidden folder, whatever spelling of the shared folder the user picked; a folder missing from the hub, such as one on an unmounted drive, keeps its spelling until it returns. A shared folder is hidden when a hidden entry names the same folder now, compared canonically each time the hob's folders are worked out, so canonicalizing a shared folder later, at hub start or when setup is saved, never shows a hidden one again. An override is rejected when it would allow more than the installation's preset; the effective answer is always the narrower of the preset and the override, so an override saved under one preset cannot widen a stricter preset picked later.

## Effective policy

Evaluate the applicable user, executor/environment, receiving agent, thread/Quest/task and specific-action constraints as an intersection. Delegation adds task restrictions; it never unions unrelated privileges. Permission to invoke an agent is distinct from permission to access that agent's resources. Thread overrides normally narrow scope; an expansion requires a separately recorded user grant.

Resource categories include filesystem, terminal, network, Git, GitHub/external apps, browser, computer, delegation and Hobbots APIs; the MVP operations and their normalization are in [ADR 014](../decisions/014-tool-policy-and-enforcement.md). Keep concurrency/cost/time budgets distinct from security permissions. Evaluate Allow / Ask / Deny for a normalized operation and concrete resource, not for the model's description of intent.

## Trusted engineering example

Automatically allow authorized repository reads/searches/edits, tests/builds, local branches/commits and permitted delegation. Dependency installation is automatic only when covered by environment policy. Protected pushes/merges require additional approval under the reference policy. Personal/out-of-scope files are denied. Host desktop control requires separate explicit permission. Integrations can have standing scoped authorization, so “external” does not universally mean “ask every time”.

## Approval contract

Show the requesting agent, operation, target system/resource, concrete arguments/constraints, expected changes and impact. Bind a decision to identity, executor, action digest, resource scope, policy version, expiration and revocation. Retain durable evidence of the request, the decision and what ran.

The approval lifetimes are **just this once**, **for this Quest** and **always for this site** (a standing permission bounded in scope, removable from Inbox history). High-risk actions offer once only and need a confirmation check box. Deny takes an optional reason that goes back to the hob. The hob never sees the approval request itself, so an approved call's result tells it that the user was asked and the lifetime they picked, and a call a saved grant let through says so too; without that the hob cannot tell an approved call from one that needed no approval. Expired or stale requests cannot be approved late; the hob asks again with fresh facts. Each decision records the approved device it came from and where it was made, the chat card or the Inbox; an expired request records that it expired, with no decider. These replace the six proposed choices (Allow once/for task/for thread, Always allow, Deny, Always deny). Matching and expiry for Approve once and Deny are decided in [ADR 014](../decisions/014-tool-policy-and-enforcement.md#asking-the-user). An approval for a test command is not approval for arbitrary shell commands or a changed target. Revalidate immediately before the action runs, and deduplicate decision/application operations.

[ADR 015](../decisions/015-approval-lifetimes-and-grants.md) decides the Quest and site lifetimes:

- **A grant** is saved by This Task or Always. It belongs to one hob and names one operation and one site: a folder for file operations (the files directly in it), an exact command in a folder for Run commands and Local Git, an exact host for Use the web, Push to a remote and branch from a folder, and a `CharmSite` for a Charm action: the Charm, its operation, the folder and only the site fields the operation declares, such as the repository and base branch for `github.open-pull-request` or the repository for `github.comment` ([ADR 031](../decisions/031-charm-actions-and-registry.md)). Delegation never passes a grant on.
- **The rule is shown before it is saved** and can be narrowed. It is never broader than the request: approving `pnpm test` in a folder matches only `pnpm test` in that folder. Only literal commands can be granted: a command with a glob, variable, `~` or substitution in any word, or with `sh -c`, `cd` or a redirection, offers once only.
- **Precedence:** always-denied targets first (changes to the protected Git paths, not reads), then Never from any layer, then high risk (which asks even where the layers allow), then safety Asks, then Allow. A grant answers only the preset's Ask. An Ask from the hob's override or a thread, Quest or task restriction still asks.
- **High risk** (a force push, a push to the default branch, a Charm action its Charm marks high risk) is once only with the check box and never granted.
- **A pending request** stays open for at most 24 hours, and expires sooner when its turn ends.
- **Revocation:** removing a rule asks first and makes the next matching call ask. Removing or hiding a folder, narrowing an operation to Ask or Never, ungranting a Charm or retiring the hob revokes the grants that relied on it; giving the authority back does not restore them. Grants are checked on every call; revoking a host grant also stops the hob's running turns.
- **This Task** is bound to the top Task of the request's tree and to the hob that asked ([ADR 018](../decisions/018-tasks-and-quests.md)). The card says This Task for a Task without a party and This Quest once a party joins; a grant given before the party joined still applies, it covers every step, and it ends with the top Task. A request made outside any Task offers none. The Inbox groups requests by their top Task, and requests outside any Task by hob and thread. Standing rules are listed in Inbox History and Settings › Permissions.

Agents may request authority but cannot manufacture human approval, access user credentials, or call administrative grant routes. Agent MCP credentials are distinct from user sessions and limited to authorized orchestration operations. Approval denial is enforced even if the runtime continues requesting the action.

## Enforcement honesty

Hobbots-managed tools pass through the permission broker. Native runtime tools use verified provider approval/sandbox hooks or an isolated environment. Arbitrary shell commands run unsandboxed can escape a nominal workspace; a system prompt is not a filesystem boundary. Each adapter declares what it can enforce, observe or cannot guarantee. Block operations requiring unavailable enforcement rather than showing a reassuring but false Trusted badge.

[ADR 014](../decisions/014-tool-policy-and-enforcement.md) sets the mechanism. Two layers are both required before a hob gets tools:

- **The runtime's permission hooks** decide every tool call through the policy engine (for Claude Code, a `PreToolUse` hook that sees every call before the SDK approves any on its own, with `canUseTool` only waiting for approvals and nothing loaded from settings on disk).
- **One OS sandbox around the whole runtime process**, Anthropic's sandbox-runtime (Seatbelt on macOS, bubblewrap on Linux), generated per turn from the effective policy. It denies reads of the user's data outside the hob's folders, allows writes only in the hob's folders and a private temporary folder, and sends all network traffic through a proxy that asks the policy engine about each new host. Child processes inherit it. The runtime's own sandbox stays off inside it.

**Commands get no more than the hob's file tools.** A command reads and writes without a call per file, so commands, Git's included, are offered only with Read files Allow and Edit files Allow or Never. With Edit files Never they are **read-only**: the sandbox closes every folder, `.git` included, to every write of the turn, and Git runs with `GIT_OPTIONAL_LOCKS=0`. A read-only command can still read anything in the folders, run Git commands that only read (`git status`, `git diff`, `git log`, `git show`), run tests and builds that write only to the turn's own `$TMPDIR`, and reach the network where Use the web allows it, so it can still send what it read to an allowed host, as any command can. It cannot commit, switch branches, stash, format files or keep a cache in the folders; those fail in the sandbox, and the hob is told so. With Edit files Ask commands stay closed, since a command would write without asking. The Permissions tab says which applies under Run commands and Save versions with Git, and `delegate_task` names a member's commands as read-only ([ADR 014](../decisions/014-tool-policy-and-enforcement.md#amendment-read-only-commands-1344), [#1344](https://github.com/otaviobarros/hobbots/issues/1344)).

A sandbox that cannot start fails the turn; it never falls back silently. Where the sandbox is unavailable (Windows until sandbox-runtime's backend there matures, or a hub missing its prerequisites), commands, local Git and the web are blocked and labeled "Needs the sandbox"; file tools still work through the permission hooks.

The sandbox is on by default for every hob. The user can turn it off for one hob, as a recorded grant with a confirmation check box, or let new hobs start without it when picking Trusting. An unsandboxed hob is labeled **Unsandboxed** wherever it appears, and its folder and network rules become checked rather than enforced.

## Charms

A **Charm** is a connection that gives a hob abilities beyond its runtime's own tools: an integration with another app or service such as GitHub, Slack, Google Drive or any MCP server. The user connects a Charm on the hub once and grants it per hob; each of its actions is Allow, Ask or Never per hob. The MVP ships the built-in GitHub Charm on the user's own GitHub account, connected through the Hobbots GitHub App and kept in the hub's OS keychain. It reads the repository, issues and pull requests of the hob's folders (#317), pushes, opens pull requests and issues and comments, and never sends a write twice by mistake ([ADR 020](../decisions/020-github-charm.md)). A hob can also get its own GitHub App, made from a manifest under the user's account: its private key stays in the hub's OS keychain like the user's tokens, the hub signs in as the app only with short-lived JSON web tokens it never stores, the hob acts with installation tokens the hub mints for one repository and the action's permissions and keeps only in memory, and disconnecting the app or retiring the hob removes its installations and its key. The user can instead link an app they already have, with its ID and private key, from the hub's own computer only; the hub checks the key with GitHub before it keeps it in the keychain, and disconnecting a linked app deletes only its key and leaves its installations ([ADR 022](../decisions/022-hob-github-app.md), [#1321](https://github.com/otaviobarros/hobbots/issues/1321)). A Charm runs in the hub process outside the runtime sandbox, is offered to the runtime over its control channel rather than the network, and goes through the policy engine with Allow / Ask / Never on its exact arguments. Credentials a Charm needs stay on the hub and never enter the sandbox, so the Charm is the only route to effects that need them; a push to a remote that accepts pushes without credentials is a checked rule. A Charm never runs workspace code: Push runs no repository hooks or configured programs. It fetches the hob's branch into a staging repository the hub owns, reading the hob's folder through `git upload-pack` inside the hob's own read-only sandbox, and pushes the commit the approval card showed from there, with the token passed on a pipe to a credential helper of the hub's or over SSH through the user's agent against GitHub's pinned host keys ([#323](https://github.com/otaviobarros/hobbots/issues/323)). A `git push` command in one of the hob's folders whose origin is on GitHub is refused with a pointer to `github_push`; any other push is decided as Push. The hub sets who a hob's commits are made as: its bot when it has its own app, otherwise the user. A command that sets its own author or committer is refused before it is decided: Git's `-c` or `--config-env` with `user.*`, `author.*`, `committer.*` or an include, `git config user.*` writes, `git commit --author` or `-C` without `--reset-author`, and the `GIT_AUTHOR_*`, `GIT_COMMITTER_*`, `EMAIL` or Git config variables, whether set, exported or dropped with `unset` or `env -i`, also inside `eval` or `sh -c`. The hob is told the identity it commits as ([#700](https://github.com/otaviobarros/hobbots/issues/700)). Every Charm write is a recorded call with a key the hob chooses: a retried key returns the first answer, and a write whose answer is lost is read back on GitHub, stays uncertain until it is found or the user settles it from its step, and blocks another write of that tool on the same site meanwhile. The sandbox never blocks a Charm the user granted. Hobbots' coordination tools (delegation, messages between hobs, results) are not Charms and keep the control-plane exclusions below.

[ADR 031](../decisions/031-charm-actions-and-registry.md) decides how every hub tool call is decided and run, and how Charms are declared:

- **One pipeline.** Every hub tool call the policy decides, from a Charm, Local Git, Memory or Skills, runs through the hub action pipeline: decode, read the hob's access again, plan, decide, ask or grant, record the step before anything is sent (EX-004), the keyed never-twice record for a Charm write, send, read back, then redact the answer and, for a Charm's read, label it as outside data. A Charm write is planned on its input redacted, and the plan redacts again any text it builds from it. An action only plans and sends; it never sees approvals, grants or the recorder.
- **Declared operations.** The built-in operations stay a closed list. A Charm declares its own operations as `<charm>.<operation>`, each with its words, its answer per preset and a once-only flag. A Charm call is the request `Charm { charm, operation, folder?, site }`, and a grant for it is the rule `CharmSite { charm, operation, cwd?, site }`. A Charm action plans its own Charm's request, or a built-in request its Charm declares it takes over, as the GitHub Charm takes over Push.
- **Reads can ask.** A Charm read is decided like a write, so an Ask asks. A grant answers it only when the preset asks, never an Ask from the hob's override or a restriction (the precedence above). Read GitHub is Allow under every preset, so an override of Ask asks once each time.
- **Grants per hob.** A hob holds a set of Charm ids and its overrides for Charm operations, which only narrow. Taking a Charm away revokes its grants and stops the hob's running turns.
- **No escalation.** No Charm action can widen what any hob may do. An action that applies a change runs only one narrower than or equal to its caller's authority, and refuses a wider one as `authority-wider`, naming the field. A wider change can only be proposed, as an Inbox item that only a user session applies. No grant and no Allow covers a widening change. A Summoning manager changing a hob whose authority is wider than its own is asked on every field ([ADR 034](../decisions/034-summoning-charm.md)).
- **Where Charms come from.** Reviewed built-in code, or an MCP server running outside the hub's process. No third-party code is loaded into the hub. An MCP tool marked `readOnlyHint` defaults to Allow, and any other to Ask.

Credentials remain scoped to the hub's execution environment or secrets provider and are excluded from messages/events. Hobs act only on the hub; a connected device never exposes its own files or apps. Device tokens, attempt grants and agent tool credentials are separate boundaries ([deployment](deployment.md), [ADR 021](../decisions/021-devices-and-remote-access.md)).

Verify denial, grant scoping/expiry, policy changes during waits, child privilege escalation attempts, duplicate decisions, changed arguments after approval, unsupported enforcement and separate computer opt-in. Full Access does not remove application-level authentication or create administrative agent APIs.


## The web

[ADR 036](../decisions/036-web-search-and-pages.md) decides how hobs search and read the web, as built-in operations rather than a Charm:

- **Search the web** is the runtime's own search, settled per turn by the hub: Claude Code's `WebSearch`, decided by the policy hook, and Codex's search in cached mode, never live or indexed. Allow under every preset, Never per hob or Quest, with no Ask, since Codex's search cannot pause. A runtime with no search of its own shows it as not offered. A runtime whose search can open pages, as Codex's can, searches only where Use the web answers Allow and no site is blocked, since those pages cannot ask.
- **Reading a page** is `web_fetch`, a hub tool decided as Use the web for the page's host, with the same presets, overrides and site grants as a command's host. Claude Code's `WebFetch` stays closed. GET only, no cookies or credentials, a `Hobbots` user agent; the answer is labeled as outside data.
- **Egress.** Every address is resolved once, checked and pinned. Loopback, link-local, cloud metadata and the hub's tailnet addresses are refused; a private network address asks, with Once or Always for its host; each redirect is decided again.
- **Provenance.** A URL from text you wrote, a reported search result or a page read in the session follows the site rules. A URL the hob wrote itself asks under every preset, also when it reaches another hob's session through a Task brief, a step brief or a message: a hob's text never makes a URL found. Each session's found set is kept in `web_found_urls`, by its chat or, outside a chat, by its Task, and a brief passes on only the URLs its writer had found. A step has no conversation to ask in (ADR 018), so a URL it may only read with your approval is held for you rather than read.
- **The read-the-web mark.** Once a session has searched or read a page, a URL the hob wrote, a new host from a command, Charm writes, pushes and shared memory saves ask until the session ends, even where a saved grant would answer, except Always for a command's host. Local work and found links do not. The hub marks the session from its own record of the search or the page, and the turn's approvals carry the mark to every call, so the policy hooks, the sandbox proxy and the hub's own tools all read it (`PolicyContext.readWeb`). The proxy cannot ask, so it refuses a new host while the mark holds. A chat keeps the mark on its thread's runtime session, and an Attempt in `attempts.read_web_since` and `read_web_source`.
- **Limits and blocked sites.** Settings › Web sets how many searches and pages a turn may make and how many searches a hob may make in a day, with per-hob overrides, and the sites `web_fetch` refuses, each with every name under it. The hub enforces them on every runtime: a search or page past a limit is refused with words that name it, and Codex, whose search cannot be stopped inside a turn, has search off on its next turn instead. Only you set them, from a user session.

## The hob directory

[ADR 032](../decisions/032-hob-directory.md) decides what a hob sees of the others:

- **Public cards only.** Another hob sees a hob's name, role, good at, status, brain and the connected Charms it holds, and who summoned it once that is recorded. Never its instructions, memory, threads, Tasks, folders, overrides, grants, credentials or GitHub app.
- **A display setting, not authority.** "Visible to other hobs" keeps a hob out of other hobs' rosters and `read_hob`, but delegation by name still reaches it. Seeing a hob's Charms grants nothing: a hob that lacks a Charm forwards the work.
- **Outside data.** Good at, names and role titles reach other hobs quoted, labeled as data and never instructions, and redacted with the reading turn's redactor, best effort like all redaction below. Good at is public to every hob, so nothing private belongs in it.

## Secrets in tool activity

Tool calls and their results reach the hub, the event journal, the database and every client, and builds and scripts often print tokens. Hobbots redacts secrets from what it stores and shows before a tool step or approval request is saved, journaled or sent, so a client that resumes later never receives the raw value. A redacted value becomes a marker that says what it was, such as `[redacted: GH_TOKEN]` or `[redacted: private key]`, never the value.

- **Known values.** The hub redacts each credential it knows by value: every variable in its environment whose name says it holds one (a token, secret, password or credential, or a name with a `KEY` or `AUTH` part such as `ANTHROPIC_API_KEY`), provider keys among them, and the sign-in an adapter puts in a turn's environment. Charm credentials join them when Charms store any. A known value shorter than 8 characters or a plain number is not redacted, and neither is a variable that names where a credential lives, such as `SSH_AUTH_SOCK` or one ending in `_FILE` or `_PATH`.
- **Secret shapes.** Values Hobbots does not know are recognized by shape: private key blocks (one cut short is redacted to its end), bearer tokens, passwords in URLs, credential assignments such as `API_TOKEN=…` (a quoted value to its closing quote), and well-known provider key prefixes (Anthropic, OpenAI, GitHub, GitLab, Slack, AWS, Google, Stripe, npm and JSON web tokens).
- **What it covers.** A tool step's label, targets, reason and output, a refused hob tool call's record (its key, tool, input and message), a tool call's full log, an approval request's arguments, label, targets and reason, and the error a runtime reports when a turn fails. A label is redacted before it is shortened, and a tool's output before it is cut to its start and end, so a cut never leaves part of a secret behind. The full log is written already redacted, so the raw output is never stored. An approval's action digest is still taken over the call exactly as it would run, so an approval matches only that call.
- **What it leaves alone.** The runtime's own session, which the model sees inside its sandbox. The user's own messages. The reply's text, which is the model's writing: a model that quotes a secret it read is not redacted yet.
- **Limits.** Redaction is best effort and never a boundary. A secret Hobbots does not know and that has no recognized shape, one split or encoded by a command (such as base64), or one spread across streamed pieces passes through. An approval's action digest is an unsalted hash over the raw call, so someone holding the journal could test guesses at a weak secret in it. Keeping credentials out of the sandbox (above) remains the protection; redaction only keeps what does leak out of Hobbots' records and screens.

## Agent control-plane exclusions

The agent-facing MCP control interface excludes **approval grants, credentials, deletion, and computer lifecycle operations**. Keep this boundary for agent-facing Hobbots controls: no administrative record deletion, credential administration, or creating/destroying computer environments through agent MCP credentials. Human-authorized management uses a separate user control path.

Only a user session decides approval requests, saves grants and removes them, and only a user session changes what hobs may do (a hob's folders, overrides and signing, and the setup's preset and folders), so a refused decision cannot be sidestepped by widening the policy instead (PE-006, [ADR 015](../decisions/015-approval-lifetimes-and-grants.md)). The one exception is the Summoning Charm ([ADR 034](../decisions/034-summoning-charm.md)): a hob you grant it to may summon, change, pause, wake and retire hobs within the scope and field answers you set, never wider than its own authority, and anything that asks becomes a proposal only a user session applies. It never reaches the sandbox switch, signing, credentials, a hob's GitHub app, approvals, grants or the Summoning Charm itself. A user session is an approved device ([ADR 021](../decisions/021-devices-and-remote-access.md), DP-004). Every API route but the health endpoint and pairing, and the event stream, sit behind the hub's device middleware, which reads the device token (a bearer token, or the `HttpOnly` device cookie) before any handler runs and provides the user session the services require to decide or revoke; only that middleware provides one, so a hob tool, a Charm or an agent-facing control added later cannot call them without it, and a test fails when any other code names it. The hub's window is trusted without asking through a key the hub writes to its data folder on every start; every other client asks once. A request without an approved device's token gets `401 DeviceRequired`, one from a revoked device `401 DeviceRevoked`, and a cookie request another page could have sent (a change without its own `Origin`, a read marked cross-site or same-site) `403 ForeignOrigin`; the hub's log records each attempt with its route and peer, never the token. A decision, a saved grant or a removed one checks in the same transaction that its device is still approved. A sandboxed hob cannot read the data folder, the browsers' cookie stores or the keychain, and never reaches the hub's address, so it has no device token to present; an unsandboxed hob could read the window key file, so for it the rule is checked, not enforced, like its other rules. The hub sends no CORS headers. A hob's own tool calls aimed at Hobbots' controls are unknown tools, or a loopback address the policy never allows, and are refused, recorded as denied steps in its reply.

This is a control-plane restriction, not a blanket prohibition on ordinary authorized workspace edits/removals. Workspace operations still follow the concrete resource/tool policy. The optional computer viewing/control capability and its separate permission do not grant agents authority to administer host computers or their lifecycle.

## Snapshots and changing authority

Keep the original configuration/policy snapshot for provenance. A historical snapshot is not a permanent authorization grant: re-evaluate applicable current restrictions, revocations, grant expiry and action-specific approval immediately before the next effect or continuation. A newly narrowed policy cannot be bypassed by continuing an older attempt or replaying an earlier approval. Exact interruption of an already-running native tool is adapter-dependent and must be recorded honestly; new disallowed effects must be prevented.
