# Persistence, journal and durable work

**Decided:** one SQLite database per installation, PostgreSQL-compatible SQL tested on both, PostgreSQL optional for a later server edition ([ADR 011](../decisions/011-sqlite-storage.md)), SQL-backed durable records with Effect integration, and Effect's built-in SQL migrator. The transaction/outbox/lease design below is a draft; the physical schema evolves through migrations.

Persist agents/configuration versions, threads/messages/session bindings, Quests/tasks/dependencies/delegations, attempts, inbox/delivery/processing state, responsibilities, approvals/policy versions, executor identity/health, artifact metadata and event sequences. Store large artifacts outside relational rows with authorized stable references as appropriate; exact remote object storage is not locked.

Use validated current-state projections plus an append-only event journal ([ADR 013](../decisions/013-event-journal.md)). This does not require full event sourcing for every entity. Each state change appends its events to the journal in the same transaction, with a gap-free sequence from a counter row, so the journal is also the outbox for clients. Notify in-process subscribers and SSE clients after commit; the journal, not the bus, defines order.

Use unique idempotency keys for commands and message/effect handling. Enforce expected versions for competing transitions. Claims have owner, expiry and fencing/version semantics. Reclaim abandoned work without allowing an older worker to overwrite a newer result. Ordering is per documented durable stream/aggregate; do not infer global causality from timestamps alone.

Runtime tool side effects are not inside a SQL transaction. Record intent and reconcile actual outcome using provider idempotency where available. Unknown outcomes need explicit state; automatic replay is restricted to safely retryable operations.

Back up relational state and artifact storage consistently. [ADR 026](../decisions/026-backup-export-diagnostics.md) decides the backup, the restore and the export: a scrubbed online copy of the database plus the content files, never a credential, and a restore that revokes every device and holds work until you resume it. Define retention and redaction policy before release. Each installation has one database; there are no replicas to synchronize. Test duplicate handling, crash boundaries, leases, migrations and restore against SQLite, and against PostgreSQL before offering it.

The journal keeps 7 days and at least the latest 10,000 entries; an older cursor gets an explicit snapshot refresh. It serves client resume and memory capture: durable work keeps its own records, so compaction never discards what open responsibilities need, and it keeps every entry after memory's capture cursor ([ADR 028](../decisions/028-memory.md)). Exclude secrets from payloads ([redaction](permissions.md#secrets-in-tool-activity)) and restrict artifact access through executor/workspace policy. A tool step's full log is a file in the data folder's `tool-logs` folder, which no hob can reach, named by a digest of its thread, reply and step ids. The hub writes it already redacted, owner-only, without following links and without emptying a file it has not checked first, and reads it back only for a step that says it was logged, and only when it is a regular file with one name that the hub's own user owns, so a planted link or file is never served.


## Memory

Memory is a second data store beside the database ([ADR 028](../decisions/028-memory.md)). The hub runs the bundled ai-memory as a child process on loopback, with its pages, their history and their index in `<data folder>/memory`, and reaches it only through the `MemoryStore` service. A capture worker sends journal entries after its cursor to ai-memory, keyed by entry id, and a hob's `memory_save` is journaled first and sent the same way, so an outage loses nothing. ai-memory skips a resent key for 30 days, which bounds the deduplication: the cursor is saved as each batch is acknowledged, so in practice only a crash in between resends, and only that batch. The database never shares a transaction with memory.

Skills keep their records in the database and their files beside it ([ADR 029](../decisions/029-skills.md)). The `skills`, `skill_revisions`, `skill_sources`, `skill_assignments` and `skill_opt_outs` tables hold the library, and every change to them is journaled in its transaction. A revision is named by the SHA-256 of a canonical listing of its files, and its files live once, read-only, in `<data folder>/skills/objects/<hash>/`, written into a staging folder and moved into place whole, so they never change once written. A removed skill keeps its rows with `removed_at` set and frees its name. A hob's proposals wait in `skill_proposals`, one row per hob, work and key, with a partial unique index that keeps one open proposal per hob and name, and its notes on a skill in `skill_feedback`; a proposal reaches the library only as an import you accepted ([#1063](https://github.com/otaviobarros/hobbots/issues/1063)). A backup copies every revision folder into its `skills/` entry, each file keeping whether it runs, and a restore puts them back read-only; the tables come with the database. It holds only the revisions the snapshot names for skills not from `~/.agents/skills`, which stay in that folder; the hub reads it again after a restore, and `restores.skill_moves` records the assignments that moved to the folder's revision then (migration 0072, [#1139](https://github.com/otaviobarros/hobbots/issues/1139)). Deleting a data folder, as a restore's put-back, deleting a set-aside folder and Start over do, opens those read-only folders first. An export of skills is not a backup: it is a folder with each skill's revisions and a `skills.lock.json`, written outside the data folder ([#1064](https://github.com/otaviobarros/hobbots/issues/1064)).

## Workbench records

Migration `0036_attempt_activity` keeps what each Attempt did, for the Workbench ([ADR 023](../decisions/023-workbench.md)). `attempt_commands` holds one row per command a runtime ran (unique per Attempt and runtime step): its redacted line, folder, whether it ran in the sandbox and showed output live, its state (running, succeeded, failed, uncertain), exit code, the start and end of its output, and its log when the output was long. `attempt_file_changes` holds one row per Attempt, folder and path: added, edited, deleted, moved or a link, with the before and after versions (hash, size, kind, the kept content or why none is kept) and the other Attempts that worked in the same folder meanwhile. A later scan in the same turn rewrites a folder's rows, and a file put back drops its row. `attempt_folder_scans` holds each start and end scan, with how many files it read and why it stopped, if it did. Each row takes its Task from its Attempt and commits with its journal event (`CommandRecorded`, `FileChangesRecorded`, `FolderScanned`); a row for an Attempt that is not there is not written.

The contents themselves, redacted text and images, and long command logs folded to their first and last 2 MiB, are files in the data folder's `activity` folder, once per hash. An Attempt keeps at most 256 MiB of contents across all its folders, reserved before each content is stored at its redacted size, and a version a later rewrite replaced is freed during the turn; and at most 64 MiB of logs. After a restart, a command still recorded as running is recorded as uncertain, with its `CommandRecorded` entry, since no turn of the earlier run still runs it. Thirty days after a Task tree ends, the hub clears the content references of its records, which then say `cleared`, and deletes every kept file no record names. It does so at startup and every hour, and never touches a hob's folders.

## Backup and restore

Migration `0038_backup_restore` adds what a restore leaves ([ADR 026](../decisions/026-backup-export-diagnostics.md)). `devices.revoked_reason` is `restore` for a device a restore revoked, so Settings › Devices shows who to pair again; a device you revoked yourself has none. `restores` holds one row per restore this database came back from: when, when and by which version the backup was made, the data folder set aside beside the restored one, the hob folders the backup named that this computer lacks, and `resumed_at`. While the latest row has none, work is held: the dispatcher skips every backpack item as not ready, and no queued message or Task step starts, until Resume work records it and drains every active hob.

A backup is a folder named `Hobbots backup <date>.hobbots-backup`, owner-only throughout. The hub copies its database with SQLite's online backup API on its own connection, so writes wait for the copy and the copy is one consistent moment. The copy is then scrubbed of every device token hash and pairing request, rewritten with `VACUUM` so no deleted row stays in a free page, left without a write-ahead log, and checked with `PRAGMA integrity_check`. The default workspace, the `activity` contents and the `tool-logs` follow, then `memory/ai-memory.tar.gz`, memory as its engine backs it up and checked to hold no memory bearer ([ADR 028](../decisions/028-memory.md)), then `settings/network.json` with the port only and `settings/memory-settings.json` with the memory model you chose, and `manifest.json` last with each file's size and SHA-256. A folder without a manifest is not a backup. While it runs, the backup holds cleanup, so no Workbench content is deleted under it, by the scheduled prune or by a turn that drops unnamed content (a deletion already under way finishes first, and what a held deletion skips stays until a later cleanup finds it unnamed), and holds the default workspace from before the database copy until the workspace is copied: replies that can write there wait, and the backup waits up to ten minutes for those already running. Hobs with folders of their own keep working. Both holds live in memory, so a hub that stops releases them.

A restore reads and checks the backup first: the manifest, every file by size and SHA-256, no link anywhere in it, a schema no newer than this Hobbots knows, and a database included. Nothing changes until it is confirmed. The hub then stops serving, moves its own entries of the data folder into `<data folder>.before-restore-<date>` beside it, copies the backup in, unpacks memory into `memory/`, writes a new installation ID, new memory keys and a `restore.json` marker, and starts again on the restored data. The desktop app keeps its window's own files in the same folder, and they stay. Any failure puts the earlier entries back: the hub removes only what the restore wrote and moves back what it had moved, and it never reuses a set-aside folder that is already there. On that start, before anything is served, the hub applies the marker in one transaction: a new journal epoch, every device but the hub's window revoked by the restore, every token hash blanked and every pairing request deleted, and the `restores` row. Then it deletes the marker; applying the same restore twice changes nothing. With no hub running, `pnpm --filter @hobbots/server restore <folder> --yes` does the same from the command line. Before the migrator applies a new migration on an update, the hub makes the same backup into `backups/` in the data folder and keeps only the latest. It reads only the tables and columns the older schema has, so a database from before devices or hob folders existed backs up too.

## Search

Thread titles and settled messages are searchable (CH-006). Migration `0011_search_index` adds the index: FTS5 tables with triggers on SQLite, GIN expression indexes on PostgreSQL ([ADR 011](../decisions/011-sqlite-storage.md)). The index changes in the same write as the thread or message, a message joins it once it settles (a queued message once its turn starts, a reply once it stops streaming or stopping), and the migration indexes what was already stored. Threads of retired hobs are left out. `GET /api/search?q=` returns one hit per thread, most recently active first, with its newest matching messages as snippets; it emits no events.

Migration `0039_task_tool_refusals` records refused Task tool calls ([ADR 018](../decisions/018-tasks-and-quests.md)): one row per hob, scope and key, with the tool, its input as stable JSON cut to 4,000 characters, the Task the calling turn worked on when the hub knew it, the refusal's reason and message, how many times it was tried and when it was first and last refused. A call with no usable key has a NULL key and a row of its own. `task_tool_calls` keeps only calls that were done, so a refused key stays free. Each refusal commits with its `ToolCallRefused` journal event, and a Task's tree carries its refusals.

Migration `0028_charm_calls` records Charm writes (ADR 020): one row per hob, scope and key with the tool, its input, the site it acts on, the plan the hub decided, its state (sending, applied, refused, not sent, uncertain) and the reply step it showed as. A new call is inserted under the journal lock, so two calls with the same key never both send, and a call on a site that has one sending or uncertain is blocked. Each sending of a key has its own `attempt`, and an outcome settles a call in one conditional update on that attempt and an unsettled state, so of two racing outcomes only the first lands, and an outcome for an earlier sending of a reused key never lands on a later one. `GET /api/threads/:threadId/charm-calls` lists a thread's calls, and `POST /api/threads/:threadId/messages/:messageId/steps/:stepId/settlement` lets the user settle an uncertain one as applied or not sent.

Migration `0045_call_key_scopes` keys `task_tool_calls`, `task_tool_refusals` and `charm_calls` by hob, scope and key ([#660](https://github.com/otaviobarros/hobbots/issues/660)). `scope` is `task:<Task id>` for a turn on a Task, or `reply:<message id>` for a chat turn that started on none, so a key is reused only within its own work. SQLite cannot change a primary key, so the migration rebuilds the three tables on both databases. A chat turn's retry also looks in its reply's scope, so Continue on a reply whose first run started its Task still finds that run's calls. A call that starts a chat turn's Task moves that turn's rows into the Task's scope in the same transaction. A Charm call is settled, and read back while uncertain, by its `attempt`, so a call that moved this way still settles. Stored calls keep the scope their input or reply names, and lose that turn from their input, and stored refusals, whose input names no turn, keep an empty scope.

Migration `0046_state_checks` makes the `state` columns of `tasks`, `attempts`, `quests` and `questions` refuse any state outside the domain's ([#683](https://github.com/otaviobarros/hobbots/issues/683)). PostgreSQL gets a named CHECK constraint. SQLite can't add one to an existing table, so it gets triggers that abort an insert, or an update of `state`, with the same message. Before it adds them, the migration stops if a stored row already holds an unknown state, and names that row. The allowed states are written out in the migration. `[TC-DP-221]` fails when a domain state list changes, so a new state also needs a new migration.
