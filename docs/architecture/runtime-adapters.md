# Runtime adapters

**Decided:** reuse existing runtimes, starting with Claude Code and Codex, with an ACP-compatible adapter foundation. Hobbots owns orchestration, durable responsibilities and UI; it does not recreate the runtime's reasoning/tool loop.

## Integration targets

| Target | Planned route | Status in this foundation |
|---|---|---|
| Codex | Codex App Server over stdio, 0.166.0 or later ([ADR 024](../decisions/024-codex-adapter.md)) | Selected; App Server behavior, the policy on its tool calls and a whole turn in the sandbox on macOS verified with a stand-in model; the sandbox on Linux and a real sign-in still need verification. |
| Claude Code | The host's `claude` through the Claude Agent SDK, 2.1.301 or later | Built; the [status page](../STATUS.md) lists what is proven on real Claude Code. |
| ACP agents | ACP client adapter with capability negotiation | Foundation selected; per-agent interoperability is not yet demonstrated. |
| Other CLIs/local-model runtimes | Individually validated future adapters | Outside initial support guarantees. |

ACP describes client/agent interactions; it does not supply Hobbots' multi-agent delegation, responsibility ledger or durable inbox. MCP exposes scoped tools; it is not interchangeable with ACP.

## Common internal contract (draft names)

`detect`, `listModels`, `createSession`, `resumeSession`, `sendPrompt`, `subscribeEvents`, `respondToApproval`, `cancel`, `getCapabilities`, `close`. These are Hobbots interface concepts, not claims that vendor APIs expose identical methods. Detect installation/version/authentication availability without reading or logging credentials.

Normalize text/tool/status/approval/result events into Hobbots envelopes while retaining useful runtime provenance. Tool calls become `ToolStarted` (id, the runtime's tool name, the policy operation, its targets and a short label), `ToolFinished` (whether the tool failed), `ToolAwaitingApproval` (the call waits for the user's decision on an approval request) and `ToolDenied` (the reason, and who refused it: the policy, the user or the sandbox). A call the policy answers Ask for is asked through the turn's approvals and decided again under the current policy before it runs. Today only the policy, or the user through it, refuses a call before it runs; a command the sandbox stops ends as a failed `ToolFinished`. A call the policy allows is recorded durably before it runs: the adapter hands its `ToolStarted` to the turn's `recordToolStart` and waits, and refuses the call if Hobbots could not record it, so no call ever runs without a record (EX-004). A command's `ToolStarted` also carries its line, the folder it runs in and whether it runs in the sandbox, and its `ToolFinished` its exit code when the runtime reports one; a runtime that streams output reports it as `ToolOutput` while the command runs. Claude Code reports output only when a command ends. A command Claude Code runs in the background returns its call at once with a background task id and no exit code, so its `ToolFinished` waits for that task's `task_notification`, with its status, the exit code its summary states and the output file it names; one still running when the turn ends has no `ToolFinished`, and the hub records it as cut off ([#1018](https://github.com/otaviobarros/hobbots/issues/1018)). Claude Code keeps the turn open until such a command ends, then wakes the session with its end. Codex answers a command's call once its wait (10 seconds by default) is over, and keeps the command running after the turn completes, so a Codex turn that completes while a command it started still runs has not ended the reply: the adapter keeps the App Server running, records the command's real end and exit code once Codex reports it, and tells the hob how it ended in a follow-up turn on the same thread. The reply ends once a Codex turn completes with no such command left ([#1048](https://github.com/otaviobarros/hobbots/issues/1048)). The hub records these for the Workbench the same way for every runtime ([ADR 023](../decisions/023-workbench.md)). A turn that finishes ends with `Completed`, which carries what the turn took and used when the runtime reports it: milliseconds until the runtime sent its first model request, until the response stream opened and until the first complete message, and its input, output, cache-read and cache-write tokens. Any field can be null for a runtime that does not report it. The hub keeps them on the reply next to the runtime and model its turn ran on ([#398](https://github.com/otaviobarros/hobbots/issues/398)). Claude Code's figures come from its result message and count the main session only, without subagents. A turn that fails records none yet. Record terminal outcome and uncertainty. Effect scopes own process/connection cleanup; closing one client must not kill unrelated work.

## Skills

A turn carries its skills as `PromptRequest.skills`, a list of mounts: each skill's name, its revision, the read-only folder that holds that revision, and whether the hob may pick it on its own ([ADR 029](../decisions/029-skills.md)). The adapter writes them once into `<runtime folder>/skill-mounts/<hash>/`, named by the SHA-256 of the mounts, with a plugin manifest and one `skills/<name>/` per skill. An Only when asked skill gets `disable-model-invocation: true` in its `SKILL.md` and `policy.allow_implicit_invocation: false` in `agents/openai.yaml` there, never in the stored revision. Overlapping turns with the same mounts share the folder, and the last to end removes it. The sandbox lets the turn read it and write nothing under `skill-mounts`.

- **Claude Code** loads the folder as a local plugin with `skipMcpDiscovery`, and `skills` names each skill as `hobbots-skills:<name>`, so the model's listing holds only those and the Skill tool refuses any other. With skills, the turn offers the Skill tool, approved by its own hook and shown as a step. Every turn, chat-only turns included, sets `strictMcpConfig`, an empty `skills` list without mounts, and settings that turn off claude.ai connectors, synced claude.ai skills and plugins, bundled skills and shell commands in a skill's text.
- **Codex** gets the folder's `skills/` as its only root through `skills/extraRoots/set`, and the App Server starts with `-c skills.bundled.enabled=false` and one `skills.config` rule with `enabled = false` for each `SKILL.md` under `~/.agents/skills`, the hob's `CODEX_HOME/skills`, and each `.agents/skills` and `.codex/skills` from the repository's root to the turn's folder. Before the thread opens, `skills/list` must show every enabled skill inside the turn's folder or with scope `admin`; otherwise the turn does not start. Administrators' skills are reported on `SessionStarted` as `organizationSkills`.
- **The fake runtime** answers the prompt `/skills` with the mounted skills.

The clean-runtime contract tests (`packages/runtimes/test/clean-runtime-*.test.ts`) run each adapter against one fixture: a fake home and repository holding skills, MCP servers, a plugin, hooks and instruction files in every place each runtime reads. A new runtime adapter is not accepted until it passes them ([evidence](../evidence/2026-11-06-skills-delivery.md)).

## Hub tools

A turn's hub tools reach the runtime as `HubTools`: `tools`, the list it offers the model, and `call`, which the hub decides and runs ([ADR 031](../decisions/031-charm-actions-and-registry.md)). Claude Code serves them through an in-process MCP server, and Codex as dynamic tools (ADR 024). `call` takes the call's `HubCallStep`, whose `record` the adapter wires to the turn's `recordToolStart`: the hub records the step before it sends anything, and a call whose step cannot be recorded does not run. A Charm that takes over a built-in request, such as the GitHub Charm's `github_push` for a `git push`, declares it; `approval.ts` steers the call from that declaration for every runtime, and no adapter imports a Charm.

## Capability matrix to fill with evidence

For each runtime/version/executor, verify native session persistence/resumption versus reconstruction; concurrent sessions versus serialized turns; streaming and cursor semantics; interruption acknowledgement; approval interception; sandbox/filesystem/network restrictions; terminal/artifact/diff visibility; browser screenshots versus live browser control; computer opt-in; model discovery; usage reporting; MCP support and scoped credentials.

Each adapter also declares its enforcement capabilities (tool interception, process sandbox, hub tools, tool events, tool interruption) and what is blocked without each; [ADR 014](../decisions/014-tool-policy-and-enforcement.md) owns that table. The declaration travels with provider health and the hob's permissions, so Settings and the hob profile show it, and the profile blocks rather than shows as safe what an unsupported capability leaves unheld (PE-005). A process sandbox that is unsupported or not yet verified on this hub counts as missing, as ADR 014 requires: commands, local Git and the web are blocked, and the profile says which applies and why. An unverified sandbox that starts still wraps the runtime for file tools. Hobbots wraps the whole runtime process in its own sandbox and turns the runtime's sandbox off inside it, so a runtime's native sandbox modes are not part of the contract.

An adapter may also report its plan's meters for the Usage screen (`planUsage`, OP-002), as the provider sends them and without spending any of them; without it, the plan shows as not reported. Claude Code's come from its `/usage` report, a local command that makes no model request, read at most once a minute. Claude Code 2.1.316 was seen answering `/usage` in about a second with no model request and, signed in without a claude.ai plan, with no meters; a claude.ai plan's meters are unverified.

Classify each capability as verified supported, unsupported, conditional or unverified, with runtime version, test date and evidence. The Claude Code adapter's enforcement capabilities were verified on macOS in October 2026 (Claude Code 2.1.301, sandbox-runtime 0.0.81): tool interception, the process sandbox, tool events and tool interruption. Hub tools were verified on macOS in November 2026 with Claude Code 2.1.316 ([#893](https://github.com/otaviobarros/hobbots/issues/893)): the adapter serves a turn's coordination tools as an in-process MCP server on Claude Code's control channel, approved by its own hook rather than by name in `allowedTools`, so the permission callback stays unshadowed, and decided by the hub rather than the policy hook, and each call shows as a step. Chat turns and steps offer them ([#272](https://github.com/otaviobarros/hobbots/issues/272)), and chat turns, party members and steps also offer the GitHub Charm's read actions ([#317](https://github.com/otaviobarros/hobbots/issues/317)) and `git_init` ([#699](https://github.com/otaviobarros/hobbots/issues/699)). Only chat turns offer its push ([#323](https://github.com/otaviobarros/hobbots/issues/323)) and other writes, whose lost answers are settled on their reply step. A hub tool call carries the step Claude Code announced it as in the PreToolUse hook, so a Charm can ask for approval on that step and mark it uncertain (`ToolUncertain`) when a write's answer is lost; this has not been verified with an installed Claude Code. The evidence is in ADR 014. Every other live Claude Code capability entry is still **unverified**. The Codex column above says which Codex entries are verified. The selected integration strategy is not proof that a runtime supports every product feature.

Evidence so far: a resumed Claude Code session (2.1.301) keeps the system prompt it started with and ignores the one passed with a new turn, including `--append-system-prompt`, a full `--system-prompt` and `--fork-session`. So when a hob's instructions change after a thread's session started, the adapter carries the new instructions inside the next turn instead of the system prompt, which keeps the session's context.

Expose unsupported previews and unavailable safe policies honestly. A text URL is not a live browser. A process exit is not necessarily a closed Quest. Cancellation acknowledgement and session resume must be checked rather than inferred.

## Verification strategy

Build a deterministic fake adapter when implementation is authorized. Exercise nested delegation, delayed results, busy recipients, permission denial, crashes, unknown side-effect outcomes and late events without model/API costs. Then test minimal real Codex/Claude sessions and selected ACP peers. Record runtime versions and evidence before claiming cross-runtime support.

Versioned capability contracts isolate protocol differences from domain services. Vendor-specific session identifiers, errors or permission modes must not become the canonical Agent or Quest model.
