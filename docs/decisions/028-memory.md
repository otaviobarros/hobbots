# ADR 028 — Memory

Status: **Accepted.** Adds an exception to the journal retention of [ADR 013](013-event-journal.md), a second data store beside the database of [ADR 011](011-sqlite-storage.md), a Memory group to the tool policy of [ADR 014](014-tool-policy-and-enforcement.md), a memory brief beside the briefing of [ADR 017](017-switching-brains.md), and a `memory/` entry to the backups of [ADR 026](026-backup-export-diagnostics.md). Records the design of [#937](https://github.com/otaviobarros/hobbots/issues/937) for the Hobs remember slice ([#951](https://github.com/otaviobarros/hobbots/issues/951)), and refines it in the places listed under Rationale.

## Context

Hobs forget everything between threads. A lesson one hob learns, such as how a repository runs its tests or how you like pull requests written, is gone in its next thread and never reaches the other hobs. Each runtime has its own memory (Claude Code's in `CLAUDE_CONFIG_DIR`, Codex's in `CODEX_HOME`), but it is per runtime, so a thread that switches brain (ADR 017) loses it, and nothing in it can be read, edited or shared from Hobbots.

#937 chose [ai-memory](https://github.com/akitaonrails/ai-memory) (MIT) as the engine: a local server that keeps memory as a git-versioned wiki of markdown pages with a SQLite index, works without a model, searches by full text, entities and links, ages unused pages and flags contradictions. This ADR decides how Hobbots runs it and, above all, where the boundaries sit, so that memory depends neither on a runtime (Claude Code, Codex, the next one) nor on a model provider, and so that ai-memory itself can be replaced.

The evidence for ai-memory's behavior is its documentation for 3.4.0. Every route and setting below is checked against the bundled version by the contract tests of [#953](https://github.com/otaviobarros/hobbots/issues/953) before anything relies on it.

## Decision

### Three boundaries

Memory touches the rest of Hobbots in three places, and only there:

1. **Hub tools.** Hobs reach memory only through hub tools (`HubTools`, ADR 018), the runtime-neutral channel Task tools and Charms already use. Every adapter that serves hub tools serves memory with no change.
2. **The context block.** The memory brief travels inside the context the hub already composes for a turn (below). Adapters deliver it as they deliver the ADR 017 briefing today, with no new field.
3. **The `MemoryStore` port.** Everything else in Hobbots (the tools, capture, the brief, the Memory page, Settings, backups) talks to memory through one Effect service in Hobbots' own words. ai-memory sits behind it.

So memory never runs a turn, never reads a runtime's session or files, and never knows which brain or model a thread used. A new runtime gets memory by serving hub tools and delivering the briefing, which it must do anyway.

### The `MemoryStore` service

`MemoryStore` is a `Context.Service` in `@hobbots/agents`, beside the other ports. Its types live in `@hobbots/domain` (`memory.ts`) and use Hobbots' terms:

- **Scope:** `Hob` (one hob's own memory), `Project` (a repository or folder) or `Everyone`. A thread is not a scope: what happened in a thread is a session page in its hob's scope, tagged with the thread. Quests are tags too.
- **Actor:** who a call is made for: a hob, with the project identities of the folders it works in, or you. The hub builds it from what it knows, never from a tool's input.
- **Page:** a path, its markdown, tags, its version, its author (a hob or you) and whether it is pinned.

It offers what its first callers need, and nothing that mirrors ai-memory's routes, projects or keys. Policy is built on top of it, never inside it:

| Group | Operations | Used by |
| --- | --- | --- |
| Recall | `search` over a set of scopes | `memory_search` |
| Writes | `write` a page as an actor when it is as expected (new, a given version, or anything), `forget` (answering the version that brings the page back), `restore` a version when the page is as expected | `memory_save`, approved shares, the Memory page |
| Browse | `page`, `history`, `versionChanges` (what a version changed against the one it replaced), `list` a scope up to a limit (pinned first, then the most recently changed), `changes` since a time, `scopes` that hold pages | The brief, the Memory page, What changed, Export |
| Health | `health` | Diagnostics, the outage banner |

- **The brief is not an operation.** Its rules (Everyone first, then the hob's own pages, then its projects', pinned first, within a budget) are Hobbots policy, so they are a pure function in `@hobbots/agents` over `list` and `page`, and every engine gets them unchanged. `list` takes a limit, so a brief never loads a hob's whole memory.
- **No idempotency key.** ai-memory's page write has none, only "create only" and "expected version". The key a hob gives `memory_save` lives in the hub's record of the tool call, as Task tool calls already keep theirs, so a retried call returns its first answer without reaching `MemoryStore` again.
- **Pinning is a write** with `pinned` set, against the version the caller read.
- **One guard for every engine.** Every `MemoryStore` layer is built through `guardMemoryStore`, which refuses a call before the engine sees it when its actor may not touch a scope it names: a hob reaches its own scope, the projects of its folders and `Everyone`, never another hob's scope or another project, and only you `forget` or `restore`. Its callers only name scopes the hub worked out, so a refusal is a defect.
- **Each later operation arrives with its first caller.** `capture` and `endSession` come with capture ([#956](https://github.com/otaviobarros/hobbots/issues/956)), and `check` (contradictions and stale pages) with Check now ([#960](https://github.com/otaviobarros/hobbots/issues/960)), each one more method on the same service, added to the shared `MemoryStore` tests then.

Two errors: `MemoryUnavailable` (the engine does not answer) and `MemoryConflict` (a write lost to a newer version). Callers treat the first as an outage (below) and show the second.

A later operation, such as `feedback` for the Curator, is one more method on the same service. A second engine, or connecting to an existing ai-memory server, is another `Layer` for the same service.

### The ai-memory adapter

A new adapter package, `@hobbots/memory`, holds the only code that knows ai-memory:

- **The process.** The server starts the bundled `ai-memory serve` as a child process (`effect/process`), on loopback on a random port, with its data in `<data folder>/memory`, waits until it answers, restarts it with a capped exponential backoff (`Schedule`), and stops it with the server's scope. It never runs `ai-memory run`, hooks or the agent installers: the hub owns the lifecycle, and hob runtimes load no hooks or settings from disk (ADR 014), so an ai-memory the user installed for themselves never sees hob sessions.
- **The client.** A small typed client over `effect/http`'s `HttpClient`, with every response decoded by `Schema`. It uses `/hook/batch` for capture, `/api/v1` for reads, `/admin` for restoring a version, and `/mcp` for search, hob writes and your edits, which it sends with the root bearer. ai-memory makes a project on its first write and logs a warning for every `/mcp` call on one it does not hold, while a `/api/v1` read of one is a quiet 404, so a read-only tool call goes only to a project that `/api/v1/projects` lists ([#1032](https://github.com/otaviobarros/hobbots/issues/1032)). ai-memory 3.4.2's `/admin` page write and delete take no expected version and no forget day, so an edit through them could overwrite a hob's save made meanwhile; over `/mcp` they are refused instead ([#959](https://github.com/otaviobarros/hobbots/issues/959)). No ai-memory SDK until one is published on npm.
- **Scopes to ai-memory projects.** One workspace per installation. `Hob` is the project `hob-<hob id>`, `Project` is `repo-<identity>` and `Everyone` is ai-memory's reserved `_global`. A project's identity is its Git `origin` remote, normalized, so two clones of one repository share it; a folder with no remote uses its folder name. The project's name ends with a hash of its identity, so the adapter keeps each identity in a `hobbots-scopes` project, which names no scope, before the project's first page; `scopes` reads it back, and a project it cannot name is an outage rather than memory left out.
- **One hub key, acting as each hob.** The hub configures two credentials of its own: ai-memory's root bearer, for setup and your edits, attributed to you through `root_username`, and its separate trusted-proxy bearer, for everything a hob does. A hob's call sends the proxy bearer with `X-Memory-Actor-User: hob-<hob id>`, so every page and audit row says which hob wrote it, and the Memory page shows that hob's current name. Both bearers, and the model bearer, are random and kept owner-only in `<data folder>/memory-keys`, outside ai-memory's own data folder so its backup never holds them. The hub hands them to the ai-memory process in its environment, never in its config file: the root bearer as `AI_MEMORY_AUTH_TOKEN`, and the proxy bearer as `AI_MEMORY_AUTH__ACTOR_PROXY_BEARER_TOKEN`, which ai-memory 3.4.0's `AI_MEMORY_` environment layer maps to `[auth].actor_proxy_bearer_token`, the setting that has no file form. The config file the hub writes for ai-memory holds neither, and the process gets no other credential than the model bearer for the hub's own memory model endpoint (below). #953 checks both mappings against the bundled version, and that a sandboxed command cannot read the process's environment. They never leave the hub and never reach a sandbox. There are no per-hob ai-memory users or keys.
- **The hub is the boundary.** In proxy mode ai-memory does not enforce restricted projects, so the hub alone decides which scopes a call may touch, as it already decides every tool call. Hobs never hold a key or learn the server's address, so nothing in a sandbox can call ai-memory directly.
- **A fake.** `@hobbots/memory` also exports an in-memory `MemoryStore` for tests, so the tools, capture, the brief and the page can be tested on the fake runtime without the binary.

### The memory tools

Two hub tools, offered on every turn that offers Task tools:

- **`memory_search`** searches the hob's own scope, the projects of the folders it works in and `Everyone`, and nothing else. The hob cannot name another scope.
- **`memory_save`** saves a page with a `scope` of `mine`, `project` or `everyone` and a key. `mine` writes the hob's own scope. A share (`project` or `everyone`) is decided by the hub under the safety preset (below). A retried key returns the first answer.

Hobs get no delete tool. Both tools join a **Memory** group in the tool policy (ADR 014) with Allow, Ask or Never per hob. A refused call never reaches `MemoryStore`.

- **Where a share goes.** A `project` share names, with `folder`, the folder whose project it is for when the hob works in more than one; the hub maps that folder to its project, and refuses a folder that is not the hob's. A hub with no share record refuses a share and tells the hob to save it as `mine`.
- **The save record.** A save to the hob's own memory is recorded in the hub's database by the SHA-256 of its key and of its input, never their text, and journaled (`MemorySaveRecorded`), in one transaction before it is sent, with its markdown and tags already redacted. The record is keyed by hob, work and key digest, as Task tool calls are (#660), and moves with the turn's other calls into a Task its reply starts. It settles as `saved`, `queued` (memory did not answer, so the capture worker sends it) or `refused`, journaled as `MemorySaveChanged`.
- **In the chat.** A save memory has, or the hub kept for later, shows as a quiet line under the reply it was made from, with Open and Undo while it stands. Undo is yours: while the save is still the page's latest version, the hub restores the version it replaced, or forgets a page it made, as you, and marks the save undone (`MemorySaveChanged`); a page changed since is never overwritten, and Undo says so. The restore or forget is itself conditional on the save's version, so a change that lands after Undo looked is refused too. ai-memory 3.4.2's `/admin/restore-page` takes no precondition, so a restore that must find the page at a version never uses it: the adapter rebuilds the earlier version from the latest one with the engine's line diff between them and writes it back as you with `expected_page_id`, which the engine checks against every writer, its own summaries included. Such a restore keeps the page's current tags and pin, since the engine answers them only for the latest version, and one whose diff is cut short is refused. A restore with no expected version, as the Memory page's Restore, still goes through `restore-page`, which brings the version back whole.

### Sharing

Hobs never write a shared scope themselves. A share from `memory_save` is handled by the preset (ADR 003):

- **Careful and Balanced:** it becomes a review item, a new Memory kind in the Inbox that counts in its badge and follows When a hob needs me. Approve, edit then approve, or decline.
- **Trusting:** a share to a project goes through and shows in Memory › What changed with Undo.
- **About you** (`Everyone`) asks under every preset.

On approval the hub writes the page as the hob, with you as the approver in its history. Pages that disagree or look stale, from Check now, wait only in Memory › To review, never in the Inbox. The Memory sidebar item never has a badge.

- **The share record.** A share is recorded and journaled (`MemoryShareRequested`) before anything is written, keyed by hob, work and key digest as a save is, so a retried key answers where the first share stands. Every later change is one conditional update journaled as `MemoryShareChanged`, so of two decisions racing for one share only the first lands. A decision claims the share (`sending`) and records what it is about to write (`pending`: share, keep or undo), the version it replaces and that version's page, before memory is touched. When memory does not answer, or the hub stops, partway through, the share stays `sending` and the hub finishes it once memory answers, at start and every 30 seconds. It knows its own write in the page's history by the version that replaced the one it recorded (memory names the version each one replaced) holding exactly the page it wrote, line for line and in order, never by who memory says wrote it, since memory names an author only for the latest version: a write by the same hob for another share, or your edit, is not taken for it. An older version's text is rebuilt from a version whose text the hub holds and ai-memory's line diff between them; a diff cut short proves nothing either way, so the share stays `sending` until memory answers it whole. So nothing is written twice, and a share that landed is never offered back for review. A write memory refuses because the page changed meanwhile sends the share back, by the step it has reached: a share or keep waits for you again, an undo stays shared, and an undo past its restore stays `sending` until the hob's own copy is written.
- **What the record keeps.** Whether your review or the preset let it through, whether you edited it, the version it wrote and the one it replaced. That record is the approver in the page's history: What changed shows a version a share wrote as shared after you approved it, or under Trusting.
- **Undo** writes the replaced version back, or forgets a page that was new, as you, only while the page is still the version the share wrote: the store's restore and forget are conditional on it, so a change that lands between Undo's read and its restore is refused, not overwritten. On ai-memory that restore is a write the engine itself checks (`expected_page_id`), so it holds against the engine's own writes too. The shared memory being back as it was is recorded (`restored`) before the hob's own copy is written, so a later edit never strands an Undo half done. Undo keeps the page in the hob's own memory. A page changed since it was shared is never undone over: you sort it out on the page. Keep it private writes the page to the hob's own memory instead.
- **Check now** runs ai-memory's `memory_lint` as a dry run, so the engine keeps no report page among yours, over every scope that holds pages. Contradictions show as pages that disagree; stale pages and pages a hob flagged as stale or wrong show as out of date; ai-memory's other findings are left out. The hub keeps the last check in memory only, so a restart clears it.

### Capture and summaries

- **Capture is a cursor over the journal.** The event journal is already the outbox (ADR 013). A capture worker reads journal entries after its cursor, sends a thread's messages and tool steps, already redacted when they were stored, to `/hook/batch` under the hob's scope with `thread:<id>` and `quest:<id>` tags, and moves its cursor when ai-memory acknowledges them. Each item's ingest key is derived from its journal entry's id under the producer name `hobbots`, within ai-memory's key rules (1 to 64 letters, digits, `_` or `-`).
- **Replays are deduplicated for 30 days, not forever.** ai-memory skips a key it has seen, but forgets ordinary keys after 30 days, and its own contract calls this bounded retry protection, not exactly-once. The cursor is saved as soon as a batch is acknowledged, so the only resend is the last batch, after a crash between the acknowledgement and the save: on the next start, normally minutes later. A resend more than 30 days after its first send, which needs the hub to have stopped in that gap and stayed down a month, can add a repeated observation to a session, or a second identical version of a saved page. Both are visible and harmless, nothing is lost, and the worker logs that it resent entries older than the window. Hobbots does not reconcile beyond that window.
- **One ai-memory session per Hobbots thread,** not per runtime session, so a brain switch never splits a thread's memory.
- **One ai-memory session per Attempt outside any chat** ([#1012](https://github.com/otaviobarros/hobbots/issues/1012)). A party member's Task, a sub-Quest's lead included, and a step run as Attempts with no thread, so a thread's session never sees them. Each such Attempt, of any Task below the top one, is a session of its own in the memory of the hob that ran it, named by the Attempt's id: its start, the Task's goal as its prompt, its finished tool steps, and the reply of each turn that ended it. A member works on its own Task with its own instructions and memory brief, so its work is its memory, never its lead's; the lead keeps what it did itself, such as the delegation, in its own session. The top Task's turns are its thread's, so they are never captured twice. Work delivered again, or a step that finishes after the session ended for quiet, goes on in the same Attempt and the same session, and a retry is a new Attempt with a session of its own.
- **What wakes a hob is in its session** ([#1028](https://github.com/otaviobarros/hobbots/issues/1028)). A turn Hobbots starts, or work that rides along your message, carries backpack items: an answer to the hob's question, a question from its member, a note, a hand-off, a Task's result or failure, a checkpoint, an approval's outcome, a deadline. Once the runtime accepts that turn (the item's `BackpackItemChanged` to `acknowledged`), each item goes to the session of the turn its last delivery names, a thread's or a member's Attempt's, in its recipient's memory, as a `user-prompt-submit` in plain words, what it says first, so a summary written without a model keeps it. The instructions Hobbots wraps the turn's prompt in stay out, and so do a Task's own assignment, which is its goal already, and routine progress (IN-005). Its key is the item's id, so a redelivered or retried turn writes it once.
- **ai-memory writes the summary.** When a session has been quiet for 30 minutes, its thread is archived, or its Task ends, the worker ends it, and ai-memory consolidates it into `sessions/<session id>.md` with the memory model (below), or into its model-free summary when there is none. A thread or an Attempt that goes on later continues the same session. No runtime turn is spent on summaries, so an expensive brain never pays for them.
- **What capture sends, on ai-memory 3.4.2.** Hobbots is the producer and the agent (`agent=hobbots`, `extension=hobbots`), whichever brain wrote a reply, and the thread's id is the session's id. A message of yours is a `user-prompt-submit` once it is no longer queued, a reply that ended is a `stop` with its text, after its finished tool steps, which are `tool-step` events of Hobbots' own vocabulary, and a top Quest the thread's hob leads there is a `quest` event. An Attempt's session is the same, with its Task's goal as its `user-prompt-submit`, and its turn's reply journaled with the Attempt's end (`TaskStateChanged.reply`), the only place a reply outside any chat is kept. ai-memory's hook route keeps no tags, so the session's first event, `session-start`, carries `thread:<id>`, or `attempt:<id>`, `task:<id>` and its Quest's `thread:<id>` for an Attempt, and each `quest` event carries `quest:<id>`, as text a search finds. Every text is redacted again on its way out, a reply's included, which the journal keeps as written. An item's key is the journal entry's id for a reply, and the identity it stands for otherwise (your message, a step of a reply or an Attempt, a Quest, a Task's goal, the session's start), so a message saved again, a step kept when Continue resumes its reply, or an Attempt's step that each change of its steps carries again is skipped as a replay; the worker also leaves out what it already sent to an open session, so an Attempt's steps go once; the adapter derives the 64-character ingest key from it under the producer name. A session ends with `auto_handoff=false`, so it writes its page and leaves no handoff behind.
- **The worker's own record.** The cursor and the open sessions (each a thread's or an Attempt's, with its hob, the time of its last captured entry and the key of its last item, which names its end) are one row and one table in the hub's database, saved in one transaction once memory acknowledged a page of the journal. Quiet is measured by the time of a session's last entry, and only once the worker has caught up, so a backlog sent after an outage ends each session once. While memory is on the cursor holds and compaction keeps every entry after it; with memory turned off, or no engine in this copy of Hobbots, it is released, and memory starts again at the journal's head when it is next on.

### The memory brief

- At the start of a runtime session, the hub builds the hob's brief from `MemoryStore.list` and `page`: `Everyone` rules first, then the hob's own pages, then its projects' facts, within a budget of about 8,000 characters, dropping the lowest-priority pages first. Pinned pages come first within their scope.
- The hub puts it in the turn's context block, beside the ADR 017 briefing, as a labeled section that says it is reference data, not instructions, with each page quoted as the briefing quotes messages.
- It is sent again only when it changed since the session last received it, so a long thread does not pay for it on every turn.
- When memory does not answer, the section says memory is unavailable instead, and the turn goes on.

### The memory model

Memory work that runs outside a chat (summaries, Check now, later the Curator's tidy and answers about memory) uses one model you choose in Settings › Your data › Memory: a provider, a model, an effort, a fallback (plain summaries or the other provider's smallest model) and optionally a model per task. No AI is a valid choice, and memory still works. In a chat, a hob saves what it learns as it works, with no extra model call. Hobbots stores the choice in its own terms and the adapter writes it into ai-memory's provider settings, so the choice does not depend on a hob's brain. ai-memory reads its provider settings only at start, so a change restarts the ai-memory process, never the app; work in flight is retried by its own queues, and captures wait in the journal meanwhile. The default is the runtime's smallest model at low effort. Usage gets a Memory line from ai-memory's call and token counts.

- **Through the runtime adapters, on your connected sign-ins.** A provider is a runtime you already connected: Claude runs on Claude Code and ChatGPT on Codex, on the sign-in that runtime already has, so a subscription runs memory and no API key is needed. ai-memory never gets a provider of its own: its only model is the hub's memory model endpoint, an OpenAI-compatible endpoint the hub serves on loopback, at `<endpoint>/<runtime>/v1`. Each request is one turn on that runtime's own adapter, with no tools, hub tools, approvals or folders, no hob's instructions, and no session to resume or keep (`ephemeral`, which Claude Code runs with no session persistence and Codex as an ephemeral thread). Only the Codex adapter touches the Codex sign-in, and only the Claude Code adapter the Claude one. ai-memory presents a third managed bearer, the model bearer, kept with the other two and given as `LLM_API_KEY` in its environment.
- **The runtime's models, efforts and state.** Settings offers exactly the models and efforts the runtime's adapter lists, as the brain picker does, and there is no model list of Hobbots' own. The smallest is the model the runtime names for quick work, else its last main model. The endpoint resolves the model when it runs a task, so a model the runtime stopped offering runs on its smallest, and Settings says so. A runtime that is signed out, outdated or unavailable shows its state, as provider health reports it, and so does a plan whose limit refused a memory task, with when it refills. The endpoint answers those as transient failures (`503`, and `429` with `Retry-After`), so ai-memory's fallback applies: plain summaries or the other provider.

### When memory is down

Hobs keep working without recall. `memory_search` answers that memory is unavailable, and the brief says so. `memory_save` is journaled first and sent by the same worker that sends capture, so a save made while ai-memory is down answers "kept, saved when memory is back" and arrives once it answers, with the same key. Before it writes a kept save, the worker reads the page: a page that already holds the save, from a hub that stopped before settling it, settles it with nothing written again, and a page written after the save was made, by a later save or by you, is newer, so the older save is refused and never replaces it. Of several kept saves of one page, only the newest is written, and the older ones are refused the same way. A write that lands between that read and the save's own loses the same way, because the save is written on the version read. Once a save settles, the session of the turn that made it, its thread's or, outside any chat, that of the Attempt it was made in, which the save records, gets one more event that says whether memory has the page, so a session page never reads a kept save as lost. Every capture event carries the time it happened, so one sent after an outage keeps its own time, not the time it reached memory. Journal compaction keeps every entry after the capture cursor, however old, as [ADR 013](013-event-journal.md) now allows, so a long outage costs disk, not memory. The Memory page shows the pages it last loaded under a notice banner.

### A second data store

ADR 011's single database stays the store for everything Hobbots decides and journals. Memory pages, their history and their index live in ai-memory's own data folder, `<data folder>/memory`, written only by its process. The database refers to memory only by scope and page path, and never in a transaction with it: the capture cursor and the journaled saves are what keep the two in step.

### Backups

A backup gains a `memory/` entry, made with ai-memory's own backup while the hub runs, and listed in the manifest with the others. The bearers are managed credentials and never in a backup: they live outside `<data folder>/memory` and reach ai-memory only through its environment, and the backup refuses an ai-memory config that holds a bearer value. A restore writes new bearers, so a restored memory answers only the restored hub. Export includes each scope's pages as markdown.

- **The archive is kept whole.** `memory/ai-memory.tar.gz` is ai-memory's own archive: its wiki with its Git history, a consistent copy of its database, and the config the hub wrote. Before it is kept, the hub reads it through and refuses it when any entry is not a file or folder under those three, when a config in it holds a credential setting, or when any bearer appears anywhere in it.
- **Memory is in every backup.** While the engine starts or restarts, Back up now stops and says memory is not answering, rather than leave memory out. With the engine off, nothing writes its folder, so the hub packs that folder in the same shape, as it also does for the backup it makes before a migration, when no engine runs yet.
- **The hub restores it itself.** A restore checks the archive the same way and unpacks it into `<data folder>/memory`, owner-only, in the same step that copies the rest, so a failure puts everything back. It does not run `ai-memory restore`, which refuses while any other ai-memory process runs on the computer, such as one the user runs for themselves. The engine opens the restored wiki and database at its next start.
- **New bearers.** The old `memory-keys` file is set aside with the rest of the hub's data and a restore writes new keys, which the engine gets in its environment at its next start.
- **Export.** An export of everything holds each scope's pages as `memory/everyone/`, `memory/hobs/<name>/` and `memory/projects/<project>/`, and a hob's export holds its own. Pages are redacted like every other string. Memory that does not answer leaves the rest of the export as it is, and its README says so.

### Out of scope

The Curator routine, skill distillation into `procedures/`, `memory_feedback`, automatic rewrites and the recall test that gates them; using an existing ai-memory server; native Windows, which ai-memory marks experimental.

## Rationale

- **Boundaries over abstractions.** Hub tools and the context block already make runtimes interchangeable, so memory adds no runtime contract. One port with Hobbots' words keeps ai-memory's projects, keys and routes in one package, and keeps the port small enough that another engine (#937 names Hindsight) is one more layer.
- **ai-memory writes summaries, not the thread's brain.** #937 had the thread's current brain write the session page. That spends a turn of the thread's model, often the most expensive one, with the whole conversation in context, on the cheapest job, and it would tie memory to each runtime. ai-memory consolidates from what capture sent, with a small model or none.
- **One `memory_save` instead of `memory_save` and `memory_propose`.** Whether a write goes through or is reviewed is the preset's call, not the hob's, so the hob says where and the hub decides. `memory_feedback` waits for the Curator, which is its only reader.
- **One hub key acting as each hob, instead of a user and key per hob.** Scopes come from projects and tags whichever key is used, so separation is the same. Hobs never hold a key, so per-hob keys would only repeat a boundary the hub already holds, at the cost of provisioning, keychain items and new keys on every restore. Proxy mode keeps what per-hob users gave: history that names the hob.
- **A port of plain reads and writes.** The brief's rules, write retries and Check now's findings are Hobbots policy or belong to later callers, so the port keeps none of them. Each engine then implements less, and each later operation is shaped by the issue that first needs it, not guessed ahead of it.
- **The journal as the queue.** It is already the outbox, so capture and offline saves need one cursor, not a second queue. Its cost is a retention exception in ADR 013 and a deduplication bound of 30 days, which the cursor's prompt save makes practically unreachable.

## Consequences

- A new package, `@hobbots/memory`, in the adapter layer, which `@hobbots/server` composes. `@hobbots/domain` gains the memory types, `@hobbots/agents` the port.
- The ai-memory binary is bundled, checksum-verified, signed and notarized inside Hobbots.app, pinned to an exact release and raised on purpose, with contract tests for every route above ([#953](https://github.com/otaviobarros/hobbots/issues/953)). Upstream releases often, so a failing contract test, not a user, finds a changed route.
- The hub runs a second long-lived child process, reported in Diagnostics.
- The policy engine gains a Memory group; the Inbox gains a Memory kind; the context block gains a memory section; journal compaction learns the capture cursor, an exception to ADR 013's retention.
- ai-memory's sweep hard-deletes expired pages and old tombstones, so it stays conservative and memory is in every backup.
- If proxy mode does not behave as documented on the routes above, #954 falls back to an ai-memory user and key per hob, kept as managed credentials, with no change to `MemoryStore`.
