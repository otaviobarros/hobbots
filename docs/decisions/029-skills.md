# ADR 029 — Skills

Status: **Accepted.** Adds a Skills group to the tool policy of [ADR 014](014-tool-policy-and-enforcement.md), a third thing a turn carries beside the briefing of [ADR 017](017-switching-brains.md) and the memory brief of [ADR 028](028-memory.md), a `skills/` entry to the backups of [ADR 026](026-backup-export-diagnostics.md), and a clean-runtime rule that every runtime adapter, Claude Code's and Codex's ([ADR 024](024-codex-adapter.md)) included, must pass. Records the design of the Skills library slice ([#1057](https://github.com/otaviobarros/hobbots/issues/1057)) for [#1058](https://github.com/otaviobarros/hobbots/issues/1058). Amended with skill sets in [#1143](https://github.com/otaviobarros/hobbots/issues/1143).

## Context

A skill is a folder with a `SKILL.md` (a name, a description and instructions) and any files it refers to. Claude Code and Codex both load skills in this format: the model sees each skill's name and description up front and reads the rest only when a task matches. Hobs need the same know-how, such as how a repository releases or how you like pull requests written, and today each runtime finds skills on its own, in its own folders, so a Claude Code hob and a Codex hob see different skills, and Hobbots can neither show nor control them.

The other tools that run local bots on these runtimes have adopted the same format, and almost none manage skills once installed: none pins a revision per agent, reviews an update before it applies, or records which skill a reply used, and one runtime's skills do not reach another's.

This ADR decides how Hobbots keeps one library of skills, how each runtime gets a hob's skills, and where the boundaries sit, so that skills depend on no runtime and no Charm, and nothing installed in a runtime's own setup reaches a hob.

The evidence for how each runtime loads skills is a probe of Codex 0.166.0 and of Claude Code 2.1.311 through the Agent SDK 0.3.311, run with fake home folders and stand-in models that recorded what each runtime offered the model, and a reading of the Codex 0.166.0 source ([evidence](../evidence/2026-11-06-skills-loading-probe.md)). What it could not show is marked **unverified** below, with the issue that checks it.

## Decision

### Two seams

Skills follow the shape of Memory (ADR 028): one port in Hobbots' own words, one package that holds everything skill-specific, and two places where the rest of Hobbots meets skills, and only there:

1. **Delivery.** `PromptRequest` gains `skills?: ReadonlyArray<SkillMount> | null`. A mount is a skill's name, a read-only folder that holds it, and whether the hob may pick it on its own. The hub resolves a hob's skills before the turn and hands the adapter its mounts; the adapter alone decides where they go. Adapters never know the library, a revision or a scope.
2. **Hub tools.** The skill tools (below) are one more `HubTools` set, combined with the others as Memory's are.

Adapters report a generic `SkillUsed { name, explicit }` from the runtime's own events. The hub maps the name to the revision it mounted for that turn and journals it.

So a new runtime gets every skill feature by mapping mounts to its own loading path and reporting `SkillUsed`, and no runtime code changes when the library does.

### Packages

| Package | Owns | Depends on |
| --- | --- | --- |
| `@hobbots/domain` (`skills.ts`) | The types: skill, revision (content hash), assignment (scope, pin or held), source, proposal, use; the `SKILL.md` front matter schema | Nothing |
| `@hobbots/agents` | The `SkillLibrary` port, and pure policy: `resolveSkills` (scope union, clashes, opt-outs), rollout rules and proposal rules | `domain`, `api` |
| `@hobbots/skills` (new) | The file store, import from a folder, an archive or Git, the checks and flags, the update checker, the `skill_*` hub tools, and a fake for tests | `agents`, `domain`, `permissions` |
| `@hobbots/persistence` | Tables for skills, revisions, assignments, sources, proposals and uses, with their journaled events, on SQLite and PostgreSQL | `agents`, `domain` |
| `@hobbots/runtimes` | Delivery per runtime, from the list of mounts | `agents`, `domain` |
| `apps/server` | Composition: the only place that wires skills to the hub | everything |
| `apps/web` | The Skills page, a hob's Skills tab and the use line | `api` |

No other module imports `@hobbots/skills`, and it imports no runtime and no Charm. The layer check (`lint:layers`) holds this.

### Delivery per runtime

A hob uses its skills the way its runtime already does. Hobbots never pastes a skill into the prompt, so 30 skills cost their names and descriptions, not 30 documents.

- **One folder per set of mounts, never rewritten.** The hub builds a turn's mounts into `<runtime folder>/skill-mounts/<hash>/`, named by the SHA-256 of the mounts (each name, revision and Only when asked), with a plugin manifest and `skills/<name>/` copied from the revisions' objects. Once written it never changes, and a turn records the hash it was given. A hob runs more than one turn at a time (a Quest's steps run two at once by default), so two overlapping turns with different revisions each read their own folder, and a turn still on r4 never reads r5's files. A folder is removed once no turn that recorded it is running or waiting, its follow-up turns for commands still running (ADR 024) included. The folders are read-only to the sandbox, like the hob's Codex home.
- **Claude Code.** The adapter passes the turn's folder as `plugins: [{ type: "local", path, skipMcpDiscovery: true }]` with `skills: ["hobbots-skills:<name>", …]`, so the model's listing holds only the hob's skills and the Skill tool refuses any other. `settingSources: []` stays, so neither your `~/.claude` nor a repository's `.claude` loads anything. Verified in the probe: the plugin's skills were listed as `hobbots-skills:<name>`, its `.mcp.json` was skipped, and with a stand-in for the API the model was offered only the listed skills, Claude Code's built-in ones left out, while the Skill tool answered "Unknown skill" for one that was not listed. The `skills` list is a filter on what the model sees, not a sandbox (the SDK says so), which is enough here because the only skills on disk that Claude Code loads beside the plugin's are its own built-in ones (below).
- **Codex.** Each turn has its own App Server process (ADR 024), so the adapter gives that process the turn's folder with `skills/extraRoots/set` (`<folder>/skills`) right after `initialize`, before the thread starts or resumes, and turns off every root it does not use (below). Verified in the probe: the root's skills were listed with scope `user` and offered to the model. The hob's `CODEX_HOME/skills` stays empty, since every turn of a hob shares that home; its source calls that folder a location kept for backward compatibility anyway. Anything found there is turned off like any other root.
- **A runtime without native skills** gets each mount's name and description in the turn's context block, labeled as reference data like the memory brief, and a hub tool `skill_read` that returns a mounted skill's files. Design only, until such a runtime exists.

- **Only when asked.** A mount the hob may not pick on its own is written with `disable-model-invocation: true` in its `SKILL.md` for Claude Code, and with `policy.allow_implicit_invocation: false` in `agents/openai.yaml` for Codex. These are written into the turn's folder from the mount, never into the stored revision. Verified in the probe with stand-in models: on both runtimes such a skill was left out of what the model was offered. That a mention still runs it is checked in [#1061](https://github.com/otaviobarros/hobbots/issues/1061).
- **Picked on its own.** A runtime picks a skill from its name and description alone, so the description decides whether a hob uses a skill it was not asked for. A description that names the requests the skill is for and says to load it before answering them gets picked; one that only restates what the skill does often does not, above all on a fast model at low effort. Verified on Claude Code 2.1.316 and Codex 0.166.0 with real models ([#1201](https://github.com/otaviobarros/hobbots/issues/1201), [evidence](../evidence/2026-11-07-skill-picked-on-its-own.md)): each runtime offered a mounted skill the way it offers its own, and a native install missed as often as a hob did.
- **Explicit use.** Picking a skill with `/` in the composer writes `/<name>` at the start of your message. The hub records it as the message's `askedSkill` when the hob has a skill of that name, and otherwise leaves the text as typed. The turn gets it as `PromptRequest.askedSkill`, with the `/<name>` taken off the prompt, and each adapter turns it into the runtime's own mention: `/hobbots-skills:<name>` ahead of the prompt on Claude Code, and a `skill` input item (`{ type: "skill", name, path }`, the mounted `SKILL.md`) beside the text on Codex. Writing `$<name>` in Codex's text does not load a skill; only the item does. Verified with stand-in models on both runtimes ([#1096](https://github.com/otaviobarros/hobbots/issues/1096)): the skill's instructions reached the model, an Only when asked one included.
- **The use line.** A reply that used a skill shows a quiet line under it, such as "Used Release steps (r4)", like the line for a memory save. Adapters report `SkillUsed { source, name, explicit }` from the runtime's own events, `source` saying whether the runtime loaded a mount (`library`) or an administrator's skill (`organization`), so the two never mix when they share a name, with no extra turn: on Claude Code from the Skill tool call the hook approves and from the skill you picked, once the session starts; on Codex from the skill you picked, once `turn/start` has taken it, and from a finished command whose actions read a mounted skill's `SKILL.md` or the `SKILL.md` of an administrator's skill that admission let through (another file of the skill, or any other `SKILL.md`, is no use). The hub maps a library use to the revision the turn was given, and an organization use to a skill the session reported, so any other name records nothing; a skill from an administrator's settings is recorded with the source `organization` and no revision. Each skill shows once per reply (`Message.skillsUsed`), and each use per turn is a row of `skill_uses`, journaled as `SkillUsed` with the hob, and the thread and reply when it came from a chat; a Task step's use names neither. A chat's use is saved with its reply's line in one transaction, and the reply the turn holds takes the line only once both are committed, a save once started running to its end before the turn stops, so a stop, a crash or any other end never leaves a count without the line or the line without the count. The `/` list follows the hob's own and shared folders as another window changes them. The skill's Activity counts them per hob and thread, in one database statement, so the total and each hob's and thread's counts agree, rather than by reading every use; the scope lists show the week's count, and a hob's Skills tab its last-used skills. Verified with stand-in models on Claude Code 2.1.311 and Codex 0.166.0 ([#1096](https://github.com/otaviobarros/hobbots/issues/1096)).

### The clean-runtime rule

No hob loads anything installed in a runtime's own setup. Hobbots is the only thing that gives a hob skills, MCP servers, hooks or plugins. On every turn, chat-only turns included:

- **Claude Code** loads no skills, plugins, MCP servers, hooks or claude.ai connectors from `~/.claude`, `~/.claude.json` or a repository's `.claude` and `.mcp.json`. `settingSources: []` and the plugin above cover skills, plugins, hooks and file MCP servers. Verified in the probe with a fake home that held a skill, a hook and an MCP server, and a repository that held skills and an MCP server: none was listed, the hook did not run, and no MCP server was reported. **Unverified:** the claude.ai connectors a subscription sign-in can bring, which a fake home cannot show. Today `strictMcpConfig` is set only on turns with tools; [#1061](https://github.com/otaviobarros/hobbots/issues/1061) checks a chat-only turn on a real sign-in and closes it with whatever setting the probe proves.
- **Codex** loads no skills, MCP servers or configuration from `~/.codex`, since each hob has its own `CODEX_HOME` (ADR 024), and none from the roots it would otherwise scan. The probe found that, with `CODEX_HOME` set, Codex 0.166.0 still lists `~/.agents/skills`, a repository's `.agents/skills` and `.codex/skills` (even with the folder marked untrusted), and its own bundled skills. So for each turn the adapter starts the App Server with `-c skills.bundled.enabled=false` and `-c skills.config=[…]`, one rule with `enabled = false` for each `SKILL.md` it finds under `~/.agents/skills` and under each `.agents/skills` and `.codex/skills` between the repository's root and the hob's folder, and in the hob's `CODEX_HOME/skills`. They are given on the command line rather than in the shared `config.toml`, so overlapping turns in different folders never overwrite each other's rules. Verified in the probe, both on the command line and in `config.toml`: `skills/list` showed the bundled skills gone, each of those skills disabled, and only the turn's own enabled. Codex 0.166.0 has no switch that turns a whole root off, so the adapter then checks `skills/list` before `turn/start`. Every enabled skill must be one it mounted or one with scope `admin` (below); a turn that would see any other does not start and says why.
- **A skill written during a turn.** Codex watches its roots, so a skill a hob writes into a repository's `.agents/skills` mid-turn can load in that turn. That is text the hob wrote itself, in the same turn; the next turn's rules turn it off, and Hobbots offers it for import like any repository skill.
- **Built-in skills.** Claude Code lists its own built-in skills and plugins whatever the settings (the probe saw them with an empty home); the `skills` list above keeps them out of the model's listing. Codex's bundled skills are turned off above.
- **Admin policy still applies.** Settings an administrator installs for a runtime (Claude Code's managed settings, Codex's system configuration) are the organization's call, and Hobbots leaves them in force. That includes skills: Codex lists those from its system configuration folder with scope `admin`, and the admission check above lets them through. The adapter reports them to the hub with the turn, which shows them on the hob's profile as From your organization, outside the library: they have no revision, no scope and no opt-out, and a use of one is journaled as `SkillUsed` with the source `organization` and no revision. Whether Claude Code's managed settings can add skills, and how the adapter would then learn their names for its `skills` list so both runtimes treat them alike, is **unverified** until [#1061](https://github.com/otaviobarros/hobbots/issues/1061).
- **Repository instructions** (`AGENTS.md`, `CLAUDE.md`) are not covered by this ADR and load as they do today.

**`~/.agents/skills` stays, through Hobbots.** The shared folder is yours, not a runtime's, so its skills are kept, but no runtime reads it: the hub reads it itself, lists its skills under Everyone marked "from ~/.agents", and delivers them as mounts like any library skill, so every runtime gets the same set and a hob can opt out of one. The folder is a source: when its content changes, the hub makes a new revision of each changed skill, which rolls out like your own edit (below). A skill there that fails the import checks is listed with the rule it failed and is not delivered.

**The folder is the only source of its skills** ([#1139](https://github.com/otaviobarros/hobbots/issues/1139)). Other tools use `~/.agents/skills` too, so a skill from it is read-only in Hobbots: an edit in Hobbots would become a revision the folder never had, which other tools would not see and the folder's next change would replace without asking. Its page says which folder holds it and has no editor and no Remove. The library refuses any revision of it that the folder did not make with `SkillReadOnly`, whichever way it comes: an edit or a revision from the web app, the desktop app or the API, an import of another source's content under its name, and a hob's `skill_propose` with `basedOn`, which is refused with a hint to propose a copy under a new name. Holds, Roll back, Only when asked and opt-outs keep working, since they choose between revisions the folder made. **Make a copy** makes a skill written in Hobbots under a new name (`<name>-copy` unless you change it) with the same files at r1, its `SKILL.md` renamed and nothing else changed, no source, and no assignment unless you pick who gets it. It copies the revision the folder holds now, which is an earlier one when the folder was put back to an earlier copy. The original stays as it is; to have a hob use the copy instead, turn the original off for that hob.

**One test for every runtime.** A clean-runtime contract test, in `@hobbots/runtimes`, runs each adapter, the fake included, against a fake home folder and a repository that hold a skill, an MCP server, a plugin, a hook and instruction files in every place that runtime reads, plus a skill in `~/.agents/skills` and, where the runtime has one and the test can write it (as in CI's container), an administrator's skill. It passes only when the runtime reports none of the user's or the repository's, the `~/.agents` skill reaches the turn through Hobbots, a mounted skill reaches it too, and the administrator's skill reaches it as the organization's without stopping the turn. On Claude Code it reads what the model is offered from a stand-in for the API (`ANTHROPIC_BASE_URL`); on Codex from `skills/list` and a stand-in model provider, as the ADR 024 probe did. A new runtime adapter is not accepted until it passes.

### Scopes

A skill lives once in the library. Where it applies is an assignment, with the scopes Memory uses:

- **Everyone:** every hob, hobs summoned later included.
- **Project:** any hob while it works in a folder of that project. A project's identity is its normalized Git `origin`, as in ADR 028, so two clones share it.
- **Hob:** one hob.

A hob's skills for a turn are Everyone's, plus each project of the folders it works in, plus its own, resolved by `resolveSkills`:

- **The narrower scope wins a clash.** A hob's own skill replaces an Everyone or Project skill of the same name for that hob, and its profile shows the replaced one struck through.
- **Two projects that define one name** in the same turn are a warning on the hob, and neither loads until you pick one.
- **Opt out per hob.** A hob can turn off an Everyone or Project skill without removing it from the scope. That is a hob setting, so it survives updates.
- **Repository skills are a source, not a fourth scope** ([#1098](https://github.com/otaviobarros/hobbots/issues/1098)). Hobbots finds a repository's `.claude/skills` and `.agents/skills` and offers once per project to import them into that project's scope. They never load from the checkout, where a branch or a pull request could change them under a running hob.

### Storage and revisions

- **Immutable revisions.** A revision is a whole skill folder, identified by the SHA-256 of a canonical listing of its files (sorted relative paths, each file's mode and contents), and shown as r1, r2, r3. Its files live in `<data folder>/skills/objects/<hash>/`, written once and never changed. The files are read-only and their folders stay writable to their owner, so a data folder can be removed with a plain `rm -rf`; no turn can write there, since the sandbox keeps the data folder and each turn's skill folder out of reach ([#1196](https://github.com/otaviobarros/hobbots/issues/1196)). Importing the same content again returns the existing revision. A version the source carries (a Git tag, `metadata.version`, a plugin's version) is shown as a label only.
- **The database** holds skills, revisions, assignments, sources, proposals and uses, and refers to a revision only by its hash.

### Import

Adding a skill to the library and assigning it to a scope are two acts.

- **Sources:** written in Hobbots, a folder or an archive (`.zip`, `.skill`), copied and never linked, a Git repository resolved to a commit and kept as the source (a repository with many skills lists them to pick from), a repository a hob works in, a hob's proposal, and `~/.agents/skills`. Import reads a `skills-lock.json`, the lock file of the `skills` CLI, so a project that uses it keeps its versions.
- **Checks before anything is written:** valid front matter (a name in lowercase letters, digits and hyphens, and a description of at most 1,024 characters), no link or path outside the skill (outside the set, for a skill of a set, below), no symlink, at most 5 MB and 200 files a skill. A failure names the file and the rule. No install script ever runs.
- **What is dropped:** a Claude Code plugin's hooks, commands, agents and `.mcp.json`, `allowed-tools` in the front matter, and the tool dependencies in Codex's `agents/openai.yaml`, each with a note, because they would add authority. A dependency on a Charm becomes a hint instead (below).
- **Flags** for what deserves a careful look: a script, a URL, and text hidden from view, such as zero-width characters. They show on an import and on every update.

### Skill sets

Many plugins are mostly skills that share files: rules in a `references/` folder at the plugin's root, and links from one skill to another, such as `../../references/workflow-contract.md` and `../plan-change/SKILL.md`. The import check above refuses every such link, so a skill set is how they come in whole ([#1143](https://github.com/otaviobarros/hobbots/issues/1143)). The probe for it is in the [evidence record](../evidence/2026-11-07-skill-sets-probe.md).

- **What counts as one.** A Claude Code plugin (a folder with `.claude-plugin/plugin.json`), a Codex plugin (`.codex-plugin/plugin.json`, or a `plugin.json` at its root, which Codex reads too) that holds at least one skill, and a folder of a repository that holds several skills that share files: skills side by side, where one of them links outside its own folder. Such a folder's set reaches up to the folder that holds them, or the one above it when that folder is named `skills`, so `<set>/skills/<name>/` and `<set>/references/` make one set. Each is offered as one set, never as loose skills.
- **Its name and label.** A plugin's set is named by its manifest's `name`, and a repository's by the set's folder. The name follows a skill's rules, is unique in the library like a skill's, and is never `hobbots-skills`, which Claude Code delivery uses for loose skills. The manifest's `version` is the set's label and its `description` the set's, or else one that lists its skills.
- **What it keeps.** Its skills' folders and the files they link to, inside the set's root, laid out as they are: a link to a folder keeps that folder, and the files those files link to are kept too. A link can go anywhere inside the set's root, a link to a file that is not there is left alone, and a link outside the root is refused, with the file and the rule. Everything else in the plugin, such as its README or images, is left out. Every other check applies to every file it keeps: the front matter of each skill, no symlink, the flags, and the limits, which count the whole set (at most 5 MB and 200 files). Two skills of one name in a set are refused. Hooks, commands, agents, MCP servers, `allowed-tools` and Codex's tool dependencies are dropped with a note, as for any skill.
- **One unit.** A set is one entry of the library, with one source and one revision per distinct content: the SHA-256 of all its files, as for a skill, and the revision lists the skills it holds, each with its name, description, folder and Charms. Assigning it to a scope, the pin, the rollout, Keep on, Roll back, update checks and Remove all apply to the whole set, so a new plugin version arrives as one update and a held hob stays on the old one. Its files are read-only: a skill inside a set is changed only through a new version from its source, or by making a copy, which is a loose skill of its own. The copy holds the skill's folder at its top and every file of the set it links to, directly or through those files, under `linked/` as the set lays them out, with another skill's `SKILL.md` named after its folder so no runtime lists it as a second skill. When the skill has its own `linked` folder, the set's files go under `linked-2/` (or the next free number), and a renamed `SKILL.md` that would land on a file already there takes the next free name (`plan-change-2.md`), so no file is lost; a file that is not UTF-8 text, or that no link in it changes, is copied byte for byte; the links that lead to those files are pointed at their new places, since a loose skill may not link outside itself, and every other link is left as written. A set itself is never copied whole. A hob's proposal never revises a set.
- **One skill off.** A hob can turn off a single skill of a set it gets, like any Everyone or Project skill, and the opt-out names the set and the skill.
- **Names.** Each skill of a set keeps its own name, so you type `/deliver-change` like any skill, and `/agent-engineering:deliver-change` works too, the way Claude Code and Codex write a plugin's skill. A skill of a set clashes like any skill: the narrower scope wins its name, and two projects that define one name load neither. Two skills of one name in the same scope, from two sets or from a set and a loose skill, both load, and then the bare name picks neither: the `/` list shows both with their set, and picking one writes the prefixed form. The hub records the prefixed form as the message's `askedSkill` when a skill comes from a set, and `TurnSkill` records the set with the skill.
- **Delivery.** `SkillMount` gains `set`, the set's name and the skill's folder inside it, and its `folder` is then the set's whole revision. A turn's folder holds each set it mounts in `sets/<set>/`, copied as it is stored, beside `skills/` for the loose skills, and only the mounted skills' `SKILL.md` files are kept in it, so a skill the hob turned off is listed by no runtime. Nothing in a set's files is rewritten, so its links resolve on every runtime. On Claude Code each set is one more local plugin, named after the set with a manifest Hobbots writes, whose `skills` paths name the folders its skills are in, and the `skills` list names `<set>:<name>`; the adapter always mentions the prefixed name, since the probe saw Claude Code load the first plugin's skill for a bare name two plugins share. On Codex each set's folder is one more extra root beside `skills/`, its skills listed by their own names, and the `skill` item names the mounted `SKILL.md`, whose path picks between two of one name. Codex's own plugin install is not used, since it writes the configuration every turn of a hob shares. The admission check counts each set's folder as mounted. A use is reported with its set, and the hub maps it to the set's revision. A runtime without native skills gets the same folder and the set's name with each skill.
- **The screens** show a set as one row of the library, tagged with how many skills it holds, that opens on the set's page: its skills, each with its uses, the files they share with how many of them link to each, its version and source, and the set's Who uses it, History and Activity. An import shows the set, its skills and the files they share before you add it; a skill of a set opens read-only, with Make a copy, like a `~/.agents/skills` skill; and a hob's skills list shows each skill of a set it gets, with a switch to turn one off.
- **Backups, exports and Diagnostics.** A set's revision is a folder of the object store like any other, so backups hold it. An export writes a set's folder as it is stored, with a plugin manifest that names it, so an import of the export takes it as the same set, and `skills.lock.json` names the skills each set revision holds. Diagnostics name a hob's skills of a set with the set's name and revision.

### Pins and rollout

- **Pins per assignment.** "Everyone uses Commit style r3", "Pip uses Release steps r5". A change to the library never moves a pin by itself.
- **Your edits roll out automatically**, and say so before and after: the button reads "Save and roll out to 4 hobs", and What changed shows the rollout with Roll back. An assignment set to Keep on r4 is held and shows that r5 is available.
- **Rollback** is a rollout to an older revision, from History.
- **Running work keeps its revision.** The hub resolves a message's skills when it accepts the message and records them with it, so a queued message keeps the revisions it was accepted with through a rollout, and a running turn keeps its mounts to its end, its follow-up turns for commands included. A turn with no message of yours (a continuation, a Task step's or a party member's turn) resolves them as it starts, so each turn of a Quest's Attempt gets the revisions assigned then. Amended in [#1061](https://github.com/otaviobarros/hobbots/issues/1061). The next turn gets the new revision. Both adapters start a new runtime process for each turn and resume the session there, and both list the session's skills again at that turn. Verified in the probe with stand-in models: after a session's first turn had r1 of one skill and a second skill, a resumed turn given r2 of the first and a third skill was offered a new listing with exactly those, on Claude Code as a new system message and on Codex as a new skills block. The first listing stays in the session's history, and the removed skill is simply missing from the new one; on Claude Code the Skill tool refused it ("Unknown skill"). Codex's files for the removed skill are gone with its turn's folder.
- **Every pin change is journaled** with who made it (you, or an approved proposal), and **each reply records the revisions its turn used** with the message, so the hob's History shows "Release steps r4 → r5" from the journal and every reply says exactly which revision it had. Pins are not part of the hob's versioned configuration: one Everyone rollout would otherwise make a new version of every hob. Amended in [#1061](https://github.com/otaviobarros/hobbots/issues/1061).
- **A rollout happens once per revision.** Saving a revision rolls it out in one transaction that rereads each assignment, so a Keep on rN that lands meanwhile stays, and marks the revision rolled out. Saving the same content again finishes a rollout the hub stopped in the middle of, and a source that still holds a revision never rolls it out a second time, so a rollback stays.

### Updates from a source

For a Git source the hub looks once a day and on Check now, and never changes the library on its own ([#1097](https://github.com/otaviobarros/hobbots/issues/1097)). An upstream change shows as Update available, with a review: the `SKILL.md` diff, files added, removed and changed, and the flags. Accept makes a new revision and opens the rollout.

- **By hand by default.** Updates show on the Skills page under Updates, with a count.
- **Update automatically**, per skill you trust: each upstream revision is accepted and rolled out like your own edit, then shown in What changed with Roll back, and the skill says "Updates automatically from" its source.
- **A flagged update never applies on its own.** One that adds or changes a script, adds a URL or hides text waits for you with the flag shown, whatever the skill's setting.

### Proactive hobs

Every hob may suggest, but new skill content only enters the library through you, the same rule as Memory's shares, so an injected instruction cannot make itself a skill other hobs load ([#1063](https://github.com/otaviobarros/hobbots/issues/1063)).

| Tool | What it does | What happens |
| --- | --- | --- |
| `skill_propose` | A new skill, or a revision of one naming the revision it read, with why | A Skill card in the Inbox and in Skills › To review: Add, Edit then add, or Not now. A stale revision is shown against the newest one. Always asks |
| `skill_request` | Asks for a skill already in the library | Follows the preset: a review card under Careful and Balanced, through under Trusting, shown in What changed with Undo |
| `skill_feedback` | Says a skill is wrong, outdated or unclear, with a line | A note on the skill's page, counted, no Inbox card. Three notes suggest a revision |
| `skill_search` | Searches the library's names and descriptions | Never returns another hob's assignments |

- The tools are Hobbots' own, like Memory's, so they form a built-in **Skills** group in the tool policy (ADR 014), with Allow, Ask or Never per hob. They are not Charm tools. A refused call never reaches the library.
- **No spam.** At most one open proposal per hob per skill name, a retried key makes one card, and a hob with three proposals waiting is told to wait for your answer.
- **Origin.** A proposal keeps the hob, the thread and the memory pages it came from, shown as Learned from on the skill.
- **Try in a chat** opens a new chat with that hob where only the draft is loaded, before anyone else gets it ([#1099](https://github.com/otaviobarros/hobbots/issues/1099)).
- Later, the memory Curator turns procedure-like memory pages into proposals ([#1100](https://github.com/otaviobarros/hobbots/issues/1100)), and a memory page gets Turn into skill.

### Safety

A skill is instructions and files, never authority:

- **A skill grants nothing.** Its scripts run as the hob's own commands, under its tool policy and sandbox (ADR 014), and front matter that would grant tools is dropped on import.
- **Skill files are read-only to the turn.** The delivered folders are outside every folder a hob may write, and a hob changes a skill only by proposing a revision.
- **Only the hob's mounted skills load**, by the clean-runtime rule above.
- **New content waits for you.** A hob's proposal, and a flagged upstream update, never apply without your review under any preset.
- **A skill that needs a Charm** says so, and a hob without it sees a warning on its profile instead of a skill that fails halfway.

### Skills and Charms

A Charm is a connection with authority: it acts on an outside service, with policy operations, grants and credentials ([ADR 020](020-github-charm.md)). A skill is know-how with none. They are separate concepts, packages and pages, and neither imports the other.

- A skill can name the Charms it needs as `metadata.hobbots.charms` (for example `[github]`), and the tool dependencies in Codex's `agents/openai.yaml` are read into the same field on import. `resolveSkills` compares it with the Charm ids in the hob's configuration, which it already has, with no call into the Charms package.
- A future marketplace lists items of kind `charm` or `skill` and hands each install to the module that owns that kind through a small installer port, so adding skills to it changes no Charm code. There are no starter skills until then.
- They meet only on screens: a hob's profile shows its Charms and its Skills side by side, and a skill's page links to the Charm it needs.

### The Skills page

A Skills item in the sidebar, separate from Memory and built on its layout and parts: Overview, What changed, To review (proposals, requests and available updates, with a count) and Updates, then Everyone, each project and each hob. A skill opens with Instructions, Who uses it, History and Activity. A hob's page gets a Skills tab beside Memory. Memory and Skills link both ways (Turn into skill, Learned from). The screens are designed in [#1059](https://github.com/otaviobarros/hobbots/issues/1059) and built in [#1062](https://github.com/otaviobarros/hobbots/issues/1062).

### Journal events

`SkillRevisionAdded`, `SkillAssigned`, `SkillRolledOut`, `SkillHeld`, `SkillUpdateFound`, `SkillProposalRequested`, `SkillProposalChanged`, `SkillUsed` and `SkillRemoved`. Removing a skill that something still pins is refused with the list of who pins it; Unassign everywhere is one step, and a removed skill goes to the Archive.

### Backups, exports and Diagnostics

- **Backups** gain a `skills/` entry with every revision's files, kept as the store keeps them, including which files run, and the database rows (sources, assignments, holds and pins) come with the rest. A restore puts the revision folders back read-only ([#1064](https://github.com/otaviobarros/hobbots/issues/1064)).
- **Skills from `~/.agents/skills` stay in that folder** ([#1139](https://github.com/otaviobarros/hobbots/issues/1139)). A backup holds none of their files, only their rows: which hobs use them, opt-outs and holds, by skill name. Otherwise a restore could bring back a skill you have since changed or deleted there, and a backup would hold files Hobbots does not own. After a restore the hub reads the folder again: a skill still there gets its current content, and an assignment pinned to a revision the folder no longer has, a held one included, moves to the folder's current revision, which the restore summary lists with who moved (migration 0072). A skill gone from the folder is listed in the summary as not on this computer and is not delivered. An export leaves them out of `skills.lock.json` and says that another hub reads its own `~/.agents/skills`; Make a copy first to take one along.
- **Export** of the library, or of a chosen set, is a new folder `hobbots-skills-<date>` in your Downloads folder, never inside a folder hobs work in. It holds each skill's newest revision in `<name>/`, any older revision an exported assignment pins in `.revisions/<name>/r<n>/`, and a `skills.lock.json` (format `hobbots.skills`, version 1) that names each skill's source, revision hashes and, when you keep them, its assignments. A hob's assignment carries the hob's name.
- **Import** of an export, as a folder or a `.zip`, reads the lock, so another hub gets exactly the same revisions, in order, and the same assignments. A hob's assignment goes to the same hob when that hub has it, or else to the one hob with that name; a project's goes to a project that hub's hobs work in, or one its library already gives skills to. One with no such hob or project is left out and the skill stays in the library. Older revisions come only with a skill the library does not have yet, and the scan shows what each is worth a look for and what it left out, as for the newest. The import is bound to what was scanned: the lock's SHA-256 as well as each skill's hash, and an older revision whose files are not the hash its lock names is refused, so a changed export imports nothing.
- **Diagnostics** name each hob's skills by name, revision number and hash, and the scope that gives them, never their content.

### Out of scope

The skills marketplace and starter skills; drafting a skill by watching you work; skills for runtimes other than Claude Code and Codex, beyond the fallback above.

## Rationale

- **The library, not the runtimes, decides.** Each runtime finds skills in its own folders, and each folder can change under a hob. One library with immutable revisions makes the same skill reach every runtime, and makes what a hob loaded something you can see, pin and roll back.
- **Native loading over the prompt.** Both runtimes already list skills by description and read them on demand, so mounting them keeps the cost small and lets the runtime's own matching work. The context-block fallback exists only for a runtime that has none.
- **A plugin folder on Claude Code, an extra root on Codex, one immutable folder per set of mounts.** Each is a place the runtime reads per process while Hobbots' isolation holds, so overlapping turns of one hob can hold different revisions. The slice's first plan wrote into `CODEX_HOME/skills`, which every turn of a hob shares, and a later turn would have replaced files an earlier one was still reading.
- **Turning roots off on Codex instead of moving `HOME`.** Codex finds `~/.agents/skills` through the home folder, but a different `HOME` would also change what the hob's commands see, such as Git's configuration. Per-skill rules, checked with `skills/list` before each turn, change nothing else. The hub reading `~/.agents/skills` itself is a refinement of the slice's first plan, made so both runtimes see the same skills and you control them.
- **Skill tools as a built-in group, not a Charm.** They act on Hobbots' own library, as Memory's tools act on memory, and grant nothing outside it. This drops the slice's dependency on the Charm registry.
- **Our own installer over the `skills` CLI.** The `skills` CLI has no library API, installs into the runtime folders hobs are kept from loading, takes the latest commit, keeps no revisions and sends telemetry by default. Reading its lock file keeps a project's versions without depending on it.
- **Review for content, the preset for requests.** A new or changed skill is instructions every hob that loads it follows, so it always waits for you. Asking for a skill already in the library changes no content, so the preset decides, as for any other tool call.

## Consequences

- A new package, `@hobbots/skills`, in the adapter layer, which `@hobbots/server` composes. `@hobbots/domain` gains the skill types, `@hobbots/agents` the port and `resolveSkills`, and `PromptRequest` gains `skills`.
- Each runtime adapter gains a skill delivery, a `SkillUsed` report and the clean-runtime contract test. The Codex adapter starts each App Server with its turn's skill rules and root, and checks `skills/list` before each turn.
- The hub keeps a skill-mount folder per set of mounts in use, and removes it when its last turn ends.
- The policy engine gains a Skills group, the Inbox a Skill kind, and backups a `skills/` entry.
- The hub watches `~/.agents/skills` and keeps a source for it.
- A set is one library entry whose revision lists its skills; an opt-out can name one skill of a set, `SkillMount` and `TurnSkill` gain the set, and each adapter mounts a set's folder whole: one more plugin on Claude Code, one more extra root on Codex.
- Contract tests pin the skill behavior of each runtime's probed version, so a release that moves a root or a flag fails a test before it reaches a hob.
