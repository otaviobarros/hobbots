# packages/memory

Memory for hobs, as [ADR 028](../../docs/decisions/028-memory.md) decides it. This package is the only code that knows [ai-memory](https://github.com/akitaonrails/ai-memory), the engine Hobbots bundles. It holds the engine's process and `MemoryStore` on top of it, plus an in-memory `MemoryStore` for tests.

## The engine

- `src/engine/release.ts` pins the ai-memory release and the SHA-256 of each platform's archive, copied from the release. Raise it on purpose, then run the contract tests.
- `scripts/fetch-engine.ts` (`pnpm --filter @hobbots/memory fetch-engine [--target darwin-arm64]`) downloads that archive, checks it against the pin, takes out only the binary and its license, and writes the binary's own `ai-memory.sha256` beside it, in `engine/<target>` (not committed). `pnpm package:mac` runs it for both Mac architectures; packaging then signs the binary with the app's identity and writes the signed binary's checksum into `Hobbots.app/Contents/Resources/memory`.
- `verifyEngine` checks that checksum and the binary's version before every start, restarts included. A missing or changed binary turns memory off, never the hub, until the hub starts again.
- `loadOrCreateMemoryKeys` keeps the hub's two bearers, the root bearer and the trusted-proxy bearer, owner-only in `<data folder>/memory-keys`, outside the engine's own data folder.
- `renderEngineConfig` writes the engine's `config.toml`, which holds no credential: loopback hosts only, no embedding model, and `[auth].root_username = "you"`, so your own edits say you wrote them.
- `MemoryEngine.layer` runs `ai-memory serve` on a free loopback port with its data in `<data folder>/memory`. Its environment holds the two bearers (`AI_MEMORY_AUTH_TOKEN`, `AI_MEMORY_AUTH__ACTOR_PROXY_BEARER_TOKEN`) and only what a process needs; the hub's own environment is not passed on. It waits until the engine answers, starts it again with a capped exponential backoff when it exits or stops answering, restarts only the engine when its settings change (`reconfigure`), and stops it with the hub. `health` is what Settings › Diagnostics shows. It never runs `ai-memory run`, hooks or the agent installers.

- `MemoryEngine.backup` writes the engine's own backup (`POST /admin/backup` with the root bearer) to a file, and with the engine off packs its folder in the same shape (`packStoppedMemory`). `checkMemoryArchive` reads an archive through before a backup keeps it or a restore unpacks it: only the wiki, the database and the config, no link, no credential setting and neither bearer anywhere. `restoreMemoryArchive` unpacks it owner-only into `<data folder>/memory`, and `replaceMemoryKeys` gives the restored hub new bearers.

A hob never reaches the engine: it has no address or key for it, and the OS sandbox keeps its commands from reading the engine's environment.

## The store

- `MemoryStoreAiMemory` provides `MemoryStore` (from `@hobbots/agents`) on the running engine, through `MemoryEngine`'s endpoint. While the engine is not running, every call that needs it fails with `MemoryUnavailable`; a search with no words answers nothing without asking.
- `src/store/scopes.ts` maps scopes to ai-memory projects in the installation's one workspace: `hob-<hob id>` for a hob's own memory and `repo-<identity>-<hash>` for a project. `Everyone` maps to ai-memory's reserved `_global`. A scope with no project yet is empty. A project's identity is kept in the `hobbots-scopes` project before its first page, so `scopes` names it again; a project it cannot name fails `scopes` as an outage.
- A hob's searches and writes go over `/mcp` with the trusted-proxy bearer and `X-Memory-Actor-User: hob-<hob id>`, so ai-memory stamps the hob in each page's `last_modified_by`. Your edits and every read use the root bearer. ai-memory records the author only in a page's frontmatter, so `history` names the author of the latest version alone.
- Writes take ai-memory's preconditions (`create_only`, `expected_page_id`), and a lost one is a `MemoryConflict`. ai-memory removes a page's versions when it deletes it, so `forget` answers the Git revision from before the delete, and `restore` takes either that or a version id.
- Your edits and deletes go over `/mcp` with the root bearer, not `/admin`: ai-memory 3.4.2's `/admin/write-page` and `/admin/delete-page` take no expected version, and its page write no forget day. A draft's `forgetOn` is sent as `expires_at`, a date ai-memory reads as the end of that day in UTC; a page past it leaves `list`, `search` and `changes` while `page` still reads it, until ai-memory's sweep deletes it and its history. Pinning does not keep it.
- `restore` uses `/admin/restore-page`, which copies the old version's frontmatter, author included, so the adapter writes the restored page once more as the actor over the version it made: a restore is always a version by you.
- ai-memory writes a session's page again at every session end, pinned or not, so `endSession` sends nothing while `sessions/<thread id>.md` is pinned.
- Every request is decoded with `Schema`. A refusal that is not a conflict or a missing scope reads as an outage, never as data. `restore` reads any refusal as a version it cannot bring back, a conflict naming the page's current version.
- `changes` follows ai-memory's cursor to the end, so an export reads every page of a scope as changed since the epoch.
- `versionChanges` reads ai-memory's own diff of a version against the one it replaced from the page's history route; a version it cannot find answers nothing.
- `list` and `changes` mark pins from ai-memory's pinned-first search, which answers at most ten; a prefix that fills the answer is split by the next character of the scope's paths until each part answers in full, so no page body is read for it. `history` reads the versions page by page.
- `capture` and `endSession` (`src/store/capture.ts`) send a thread's items to `/hook/batch` as one ai-memory session, the thread's, with `agent=hobbots` and `extension=hobbots`: your message as `user-prompt-submit`, a reply as `stop`, a tool step and a Quest as Hobbots' own `tool-step` and `quest` events, and the end as `session-end` without a handoff, which has ai-memory write `sessions/<thread id>.md`. Each ingest key is a SHA-256 of the item's key under the producer name, and `capture` answers how many of the first items ai-memory acknowledged.
- `@hobbots/memory/testing` exports `MemoryStoreFake`, which keeps pages in memory and can be taken down.

## Tests

- `test/engine.test.ts` runs the supervisor against a stand-in binary: the environment it gets, restarts after a crash and a hang, a settings change, a failed checksum, a backup.
- `test/backup.test.ts` packs, checks and unpacks memory archives, and refuses one that holds a bearer, a credential setting, a link or anything else.
- `test/engine-contract.test.ts` runs every route and setting Hobbots relies on against the real binary: both bearers from the environment, the hob a proxy call asserts, `/mcp`, `/hook/batch` and its ingest keys, `/api/v1`, `/admin`, a backup with no credential inside, and that backup restored with new bearers. It needs `fetch-engine` first; with `HOBBOTS_MEMORY_CONTRACT=1`, as in CI, it fails without the engine instead of skipping.
- `test/capture-contract.ts` holds the capture worker's tests (`MemoryCapture` in `@hobbots/agents`): a brain switch, redaction, an archived and a quiet thread, a Quest, a crash between acknowledgement and the cursor's save, an outage longer than the journal keeps entries, the warning for entries past the 30-day replay window, and the saves kept through an outage: one memory took before the hub stopped is not written again, one a newer write replaced never overwrites it, and of several of one page only the newest is written. `test/capture-fake.test.ts` runs them on the fake and `test/capture-ai-memory.test.ts` on the real engine, which an outage stops and starts again.
- `test/store-contract.ts` holds the `MemoryStore` tests every engine passes. `test/store-fake.test.ts` runs them on the fake, and `test/store-ai-memory.test.ts` runs them on the real engine, each case on fresh data, with a second run that restarts the engine on the same data.
